# Phase 2 — Data Models & Storage Engines

Phase 1 covered how bytes move between machines. Phase 2 goes one layer down into what happens once those bytes need to be *kept* — how a database decides where on disk a value lives, how it finds that value again in microseconds instead of scanning the whole file, and what tradeoffs it silently made to get there. This is DDIA Part I territory (Chapters 1–4), and it's the material that makes "why did you pick Postgres over Cassandra" a real technical question instead of a coin flip.

## 2.1 Reliability, scalability, maintainability — the three pillars

DDIA opens with these three words because almost every subsequent design decision in the book — and in a real interview — is really an argument about which of the three you're optimizing for at another's expense. They sound like fluffy adjectives until you attach concrete failure modes to each one.

### Reliability — the system keeps working correctly when things go wrong

"Reliable" doesn't mean "never fails" — it means the system continues to perform the function the user expects *despite* faults, and that faults are anticipated and handled rather than treated as surprises. DDIA is precise about separating a **fault** (one component deviating from spec) from a **failure** (the system as a whole stops providing the required service to the user). Good reliability engineering is fundamentally about building **fault-tolerant** mechanisms that prevent faults from cascading into failures. Three categories of fault, each demanding a different kind of defense:

- **Hardware faults** — disks fail (annual failure rates of a few percent per drive are normal at scale, meaning a datacenter with tens of thousands of disks sees failures *daily*, not as an edge case), RAM develops errors, a network switch dies, a whole rack loses power. The classic response is redundancy: RAID for disks, dual power supplies, ECC memory for bit-flip detection/correction, and — the modern shift DDIA highlights — as fleets scale into the tens of thousands of machines, **software fault-tolerance** (replicating data across independent machines, designing for a machine to just die at any moment) increasingly matters more than making any single machine ultra-reliable, because at that scale hardware failure becomes a statistical certainty every single day rather than a rare event.
- **Software bugs/errors (systematic faults)** — these are worse than hardware faults precisely because they're *correlated*: a bug doesn't fail one random disk, it fails every server running that code simultaneously, at the same trigger condition. Examples DDIA calls out: a leap-second bug that hung many Linux systems simultaneously in 2012; a runaway process that consumes a shared resource (CPU, memory, disk, network bandwidth) and starves everything else on the box; a cascading failure where one slow/failing service causes retries that overload a downstream service, which then fails too. Defenses are process-level, not redundancy-level: thorough testing, process isolation, allowing processes to crash and restart cleanly, monitoring that catches divergence between expected and actual behavior in production, not just in tests.
- **Human error** — configuration mistakes by operators are, empirically, a leading cause of real-world outages (DDIA cites studies putting operator error above hardware faults as an outage cause). The mitigation isn't "hire people who don't make mistakes" — it's designing systems that minimize the *opportunity* for error: well-designed abstractions and APIs that make the easy path also the safe path, sandbox/staging environments to try risky changes with real data but without affecting real users, easy and fast rollback of config changes, good telemetry (dashboards, alerting) so a mistake is caught in seconds rather than discovered by users hours later, and gradual/canary rollouts rather than instantaneous fleet-wide deploys.

The interview-relevant point: when a design mentions "we replicate data across 3 nodes," the *why* is reliability against hardware faults specifically — it does nothing to protect against a software bug that corrupts data before replication, or an engineer who fat-fingers a `DELETE` with no `WHERE` clause. Different failure classes need different, sometimes completely unrelated, defenses — an interviewer who asks "what if the bug is already replicated to all three nodes before anyone notices" is testing whether you understand this distinction.

### Scalability — the system keeps working as load grows

Scalability isn't a single number ("this system scales" or "this doesn't") — it's a question of "if the system grows in a particular way, what are our options for coping with the growth." That framing forces you to first **describe load precisely**, then **describe performance precisely**, before you can even discuss what "coping" would mean.

**Describing load with parameters, not adjectives** — DDIA's running example is Twitter's timeline problem, which is genuinely the cleanest illustration of why "how many users" is the wrong question. Twitter (circa the case study) had two ways to implement "show me my home timeline":

1. **Fan-out on read:** when a user opens their timeline, query for every person they follow and merge their recent tweets on the fly. Cheap on write (posting a tweet is a single insert), expensive on read (a query has to touch every followee, every time, for every home-timeline view).
2. **Fan-out on write:** when a user posts a tweet, immediately push it into the precomputed home-timeline cache of every one of their followers. Expensive on write (one tweet fans out into potentially millions of writes), but reading your timeline is now just "read my own precomputed list" — cheap and O(1) in the number of people you follow.

Twitter actually uses a hybrid: fan-out on write for almost everyone, but celebrities with tens of millions of followers get fanned out on read instead (or a merged approach), because pushing one tweet into 50 million follower caches synchronously would be a catastrophic write amplification event. This is the concrete lesson behind "describe load with parameters": the *relevant* number here isn't "average tweets per second," it's **the distribution of followers per user** — a system designed around the average will fall over on the tail (celebrity accounts), because the load-generating operation (fan-out) scales with follower count, not with tweet count. This exact fan-out-on-write-vs-read tradeoff resurfaces almost verbatim in Phase 5.10 (notification systems) — it's not a Twitter-specific quirk, it's a general pattern for "one write, many potential readers."

**Describing performance precisely — percentiles, not averages.** Response time isn't one number; it's a distribution, and the *shape* of that distribution matters more than any single point on it. The **average** is actually a poor way to characterize "typical" response time because it's dragged around by outliers and doesn't tell you what any given user actually experienced. What matters:
- **p50 (median)** — the actual typical experience: half of requests were faster, half slower.
- **p95, p99, p999** — tail latencies. The p99 is "the response time below which 99% of requests fall" — meaning 1 in 100 requests is *worse* than this number. This matters enormously in practice because a user's page load often depends on multiple backend calls in parallel or in sequence, and if any one of them is a tail-latency straggler, the whole page is slow — DDIA calls this **tail latency amplification**: the more backend calls a single user request fans out to, the higher the chance *at least one* hits a slow p99, so the overall page's effective latency distribution is worse than any individual service's.
- Percentiles are also the natural basis for **SLAs (Service Level Agreements)** — e.g., "99% of requests complete in under 200ms" is a percentile commitment, not an average one, precisely because averages can hide a bad tail while looking fine in a dashboard.

**Coping with load** — the two levers are the ones Phase 1.4 already introduced (scaling up vs scaling out), but DDIA's addition is that **elastic** systems (auto-scaling in response to load) are convenient for unpredictable/spiky load but introduce their own complexity, whereas manually-scaled systems are simpler to reason about but require humans to anticipate growth. Neither is universally correct — it's a genuine tradeoff between operational simplicity and responsiveness, which connects directly to the third pillar.

### Maintainability — the system stays workable for the engineers who touch it after launch

DDIA is explicit that most of the cost of software isn't the initial build — it's the ongoing maintenance: fixing bugs, keeping systems running, investigating failures, adapting to new use cases, paying down technical debt, adding features. Three design principles minimize this pain over the system's life:

- **Operability** — make it *easy for operations teams to keep the system running smoothly*. Concretely: good monitoring/observability (this is exactly what Phase 5.13 goes deep on), providing good documentation and a good operational model, avoiding dependency on individual machines so any one can be taken down for maintenance without drama, providing good defaults while allowing overrides, self-healing where possible but also giving admins manual control when automation is wrong.
- **Simplicity** — managing complexity so new engineers can understand the system, not just the original authors. DDIA's specific target here is **accidental complexity** — complexity that arises not from the inherent problem being solved, but from the implementation (leaky abstractions, tangled dependencies, special-cased hacks accumulated over time). The tool for fighting this is good **abstraction**: hiding implementation detail behind a clean interface (a SQL query language is an abstraction over B-tree/LSM-tree internals; TCP is an abstraction over unreliable IP packets) so engineers can reason about the system at a higher level without re-deriving the low-level mechanics every time.
- **Evolvability (a.k.a. extensibility, modifiability, plasticity)** — how easily the system can be adapted for unanticipated future use cases as requirements inevitably change. This is where **schema evolution** (2.7 later in this file) and loose coupling between components directly serve maintainability — a system that requires a synchronized, coordinated, all-at-once deployment across every producer and consumer every time a field is added is far less evolvable than one where old and new code can coexist during a rolling deploy.

The interview-relevant framing: when you're asked to "design X," reliability/scalability/maintainability are the lens for *evaluating* your own proposed design out loud, not boxes to check off in a monologue. "This adds a single point of failure" is a reliability critique. "This works at today's load but the write path doesn't scale past N" is a scalability critique. "This requires every service to redeploy in lockstep" is a maintainability critique. Naming which pillar you're trading off, and against what, is what separates a senior-sounding answer from a junior one.

## 2.2 Data models: relational vs non-relational

Every data model is fundamentally an answer to the question "how do I take the tangled, nested, object-shaped reality of an application and lay it out so a machine can store and query it efficiently?" That translation is never free, and the friction it produces is worth naming precisely before comparing models.

### The impedance mismatch

Application code, especially in object-oriented languages, works naturally with objects — nested structures, references between objects, collections inside a single logical entity (a `User` object that has a list of `Address` objects, say). Relational databases work with flat tables of rows and columns with no native concept of nesting. The gap between these two representations is called the **object-relational impedance mismatch**, and it's the entire reason ORMs (Object-Relational Mappers — Hibernate, ActiveRecord, SQLAlchemy, Entity Framework) exist: they're translation layers papering over the fact that your in-memory object graph and your on-disk relational schema are shaped completely differently. Storing a résumé with one `user`, several `education` entries, several `positions`, arbitrary `contact_info` fields is awkward in a strictly relational model (it wants a `users` table joined against `education` and `positions` tables via foreign keys) and completely natural in a document model (the résumé *is* one JSON blob, structurally). This mismatch is precisely the historical motivation for document databases — MongoDB's core pitch was literally "store your objects the shape they already are in your code."

### Relational databases (Postgres, MySQL, Oracle, SQL Server)

Data lives in **tables**: fixed sets of typed columns, rows conforming to that schema, relationships expressed via **foreign keys** referencing another table's primary key. The strength is precisely that rigidity: a **schema-on-write** system enforces structure and referential integrity *before* bad data ever lands in the table, joins across normalized tables are a first-class, heavily-optimized operation (query planners exist specifically to make multi-table joins efficient), and a mature transaction model (ACID, Phase 3.5) gives strong correctness guarantees for multi-step operations. The cost is exactly the impedance mismatch above, plus schema migrations on a huge table being a real operational event (though modern Postgres/MySQL have gotten much better at online, non-blocking schema changes).

### Document databases (MongoDB, Couchbase)

Data lives as self-contained, semi-structured documents (JSON/BSON), typically one document per logical entity, with no enforced schema across documents by default (**schema-on-read** — the structure is interpreted by the application when it reads the data, rather than enforced by the database when it's written). This is a natural fit when an entity is mostly self-contained and read/written as a whole unit (the résumé example above, a product catalog entry, a blog post with embedded comments) — you fetch one document and you have everything, no joins required. The weakness shows up exactly where relational shines: **many-to-many relationships** are awkward, because documents naturally handle "one document containing many nested things" (one-to-many, via embedding) but don't have a native, efficient way to represent "this entity relates to many other independent entities that also need to be queried independently" (you either denormalize the related data into every document that needs it — creating update-consistency headaches — or you store a foreign-key-like reference and do the join yourself in application code, since most document databases historically had weak or no server-side join support).

### Wide-column stores (Cassandra, HBase, Google Bigtable)

Data is modeled as a giant sparse table addressed by (row key, column family, column key), physically stored so that a **row's data is grouped and sorted by row key**, and each row can have a wildly different set of columns from every other row — hence "wide" and "sparse." Practically, teams model a wide-column table around a specific query pattern rather than around normalized entities: the row key is chosen to match how data will be read (e.g., `user_id` as the partition/row key so all of one user's data is colocated on disk and readable in one lookup), and columns within a row are often used almost like a mini time-series or list (e.g., a row per user with a column per event, column name = timestamp). This shape is built for very high write throughput and horizontal scale across a cluster of commodity machines (Cassandra's leaderless replication is Phase 3.1 material), at the cost of needing to know your query patterns upfront — you generally can't ask ad hoc questions the schema wasn't shaped for.

### Key-value stores (Redis, DynamoDB, Memcached, Riak)

The simplest possible model: a unique key maps to an opaque value, retrieved only by exact key lookup — no querying by value content, no joins, no secondary indexing in the simplest implementations (though DynamoDB and Redis both offer secondary indexes/query capabilities beyond pure key lookup in practice). This simplicity is the whole point: O(1) or near-O(1) lookups with minimal overhead, trivial horizontal partitioning (hash the key, route to the owning node — this is exactly where consistent hashing, Phase 5.11, comes from), and a natural fit for caching (Redis in front of a slower primary store), session storage, or any access pattern that's fundamentally "give me the thing with this ID." Redis specifically layers rich in-memory data structures (lists, sets, sorted sets, hashes) on top of the basic key-value idea, which is why it's used for far more than caching — leaderboards (sorted sets), rate limiters (Phase 5.6), pub/sub messaging.

### Graph databases (Neo4j, Amazon Neptune, JanusGraph)

Data is modeled explicitly as **nodes** (entities, each with properties) and **edges** (relationships between nodes, also with properties and a direction), optimized specifically for traversal — "find all of this node's neighbors," "find the shortest path between these two nodes," "find everything reachable within 3 hops." This is the natural model when the relationships *between* things are as important as the things themselves and the relationships are highly variable/interconnected rather than a few fixed one-to-many links: social networks (friend-of-friend), fraud detection (following chains of transactions to detect rings), recommendation engines, knowledge graphs. Relational databases can technically model a graph (an edges table with `from_id`, `to_id`), but multi-hop traversal in SQL requires repeated self-joins that get exponentially uglier and slower per additional hop — graph databases store adjacency natively (each node effectively holds pointers to its edges) so a traversal is a fast pointer-chase rather than a join, which is the whole reason they exist as a separate category.

### Normalization vs denormalization — the tradeoff underlying all of the above

**Normalization** means storing each piece of information exactly once and referencing it by ID from everywhere it's needed (e.g., a `city` stored once in a `cities` table, referenced by ID from every `user` row) — this avoids duplication, and duplication is dangerous because it creates the possibility of **inconsistency**: if "Bangalore" is renamed and it's duplicated in a thousand rows, you must update all thousand consistently or the data disagrees with itself. **Denormalization** means duplicating data directly into the places that read it, deliberately trading that consistency risk for read performance — no join needed at read time, because the data you need is already sitting right there. This single tradeoff is the real reason document/wide-column stores exist at all: they're frequently choosing to make denormalization cheap and joins expensive, on the bet that the dominant workload is "read one self-contained thing fast" rather than "flexibly query across normalized relationships." A useful interview shorthand: relational databases optimize for write-time consistency and flexible read-time querying; document/wide-column stores optimize for read-time speed on a known access pattern, pushing the consistency risk of duplication onto the application.

| Model | Best fit | Real products | Weak spot |
|---|---|---|---|
| Relational | Structured data, complex joins, strong consistency (banking, inventory, orders) | Postgres, MySQL, Oracle | Impedance mismatch, rigid schema migrations |
| Document | Self-contained, nested entities read/written as a whole (catalogs, CMS, profiles) | MongoDB, Couchbase | Weak many-to-many, cross-document joins |
| Wide-column | Very high write throughput, known query patterns, huge scale (time-series, event logs) | Cassandra, HBase, Bigtable | Poor ad hoc/flexible querying |
| Key-value | Simple lookups by ID, caching, sessions | Redis, DynamoDB, Memcached | No querying by value, no joins |
| Graph | Highly interconnected data, multi-hop traversal (social graphs, fraud rings) | Neo4j, Neptune, JanusGraph | Poor fit for tabular/aggregate analytics |

## 2.3 Query languages: SQL vs declarative vs imperative, graph query languages

### Declarative vs imperative — the core distinction

An **imperative** language tells the computer *how* to do something, step by step, in a specific order: loop over this collection, check this condition, accumulate this result. A **declarative** language tells the computer *what* result you want and leaves the *how* — the execution strategy, the order of operations, which index to use — up to the underlying engine. SQL is declarative: `SELECT name FROM animals WHERE family = 'Sharks'` says nothing about *how* to find shark rows — it just states the desired result, and the query planner decides whether to scan the table, use an index, what join order to use, etc.

DDIA's classic illustration is worth reproducing because it's the cleanest possible demonstration of the difference. Imagine a table of animals with columns like `name` and `family`, and you want the names of every shark. **Declaratively (SQL):**

```sql
SELECT name FROM animals WHERE family = 'Sharks';
```

**Imperatively**, in pseudocode resembling how you'd do it by hand in a general-purpose language:

```
sharks = []
for animal in animals:
    if animal.family == 'Sharks':
        sharks.append(animal.name)
return sharks
```

Both produce the same result. But the imperative version has *baked in* an execution strategy — a full linear scan, checked one record at a time, in whatever order the underlying collection happens to be stored — and that strategy is now the programmer's problem to optimize (add an index? which one? how do you keep it updated as data changes?). The declarative version hides all of that; the database is free to use an index on `family` if one exists, free to change its strategy entirely as the table grows or statistics change, and — critically for scalability — free to **parallelize execution across multiple CPU cores or even multiple machines automatically**, something an imperative loop written by a programmer generally isn't, because the query only specifies the *pattern* of the desired result, not a specific code path that assumes single-threaded, in-order execution. This is precisely why declarative languages fit well with automatic query optimization and with distributed execution: the engine has room to choose a plan.

### MapReduce as a middle ground

MapReduce (Phase 4.1 goes deeper on this as a batch-processing paradigm) sits between the two: it's neither fully declarative like SQL nor fully free-form imperative — it's a **constrained** form of imperative code, expressed as a `map` function (transforms/filters each input record independently) and a `reduce` function (aggregates values sharing a key, after the framework groups them). The constraint is the point: because `map` and `reduce` are pure functions with no side effects and no dependency on execution order, the framework can freely parallelize and distribute their execution across a cluster, and can retry a failed task without side effects — you get some of declarative SQL's automatic-parallelization benefit while still writing arbitrary code for the transform logic itself (useful for computations too complex to express in a `WHERE` clause). MongoDB historically supported a MapReduce query mode for exactly this — complex aggregations expressible as JavaScript map/reduce functions rather than a fixed query syntax — though MongoDB's newer **aggregation pipeline** framework has mostly superseded it with a more declarative, composable stage-based syntax (`$match`, `$group`, `$sort` stages chained together).

### Graph query languages

Graph data (2.2 above) needs its own query paradigm because "find everything reachable via a chain of relationships, of unknown length" doesn't map cleanly onto SQL's table/join model.

- **Cypher** (Neo4j's query language, now also an openCypher standard adopted more broadly) is declarative and pattern-based — you draw the shape of the graph pattern you want to match using an ASCII-art-like syntax, and the engine finds all matches. E.g., finding people who both live in the same city and are friends: `MATCH (a:Person)-[:FRIENDS_WITH]->(b:Person), (a)-[:LIVES_IN]->(c:City)<-[:LIVES_IN]-(b) RETURN a, b`. The `()-[]->()` syntax is literally meant to look like nodes and arrows — this readability is a deliberate design goal.
- **SPARQL** is the query language for the **RDF (Resource Description Framework)** triple-store data model — every fact is a `(subject, predicate, object)` triple (e.g., "Alice knows Bob," "Bob livesIn Boston") — used heavily in semantic-web and knowledge-graph contexts (Wikidata is a prominent public example). Also declarative and pattern-matching in spirit, though its syntax targets triples rather than Cypher's node-and-relationship visual style.
- **Gremlin/Apache TinkerPop** takes the opposite, imperative-traversal approach: you write a chain of traversal steps (`g.V().has('name','Alice').out('knows').values('name')` — "start at Alice, follow outgoing 'knows' edges, return names") — closer to the imperative animal-loop example above, just specialized for graph traversal, and this is what a lot of non-Neo4j graph systems (JanusGraph, Amazon Neptune supports both Gremlin and SPARQL) speak.

The interview-relevant reason to know this distinction: if a design calls for "find friends-of-friends who like the same restaurant," reaching for SQL means multiple self-joins that get uglier with every additional hop, whereas Cypher/Gremlin express that traversal natively and (usually) execute it more efficiently because the underlying storage keeps adjacency information colocated rather than requiring a join computed at query time.

## 2.4 Storage engines: hash indexes, SSTables, LSM-trees

Everything above this point has been about the *model* data is shaped into. From here down is about the actual mechanics of how a storage engine gets a value onto disk and back again — and this is where "why is Postgres slow at massive write throughput but Cassandra isn't" gets a real, mechanical answer instead of a vibe.

### The simplest possible storage engine — and why it's actually reasonable

DDIA's starting point (deliberately toy but instructive) is a database that's just an **append-only log file**: every write is `key,value\n` appended to the end of the file, nothing is ever overwritten. Appending is about the fastest disk operation that exists — sequential writes avoid the disk-seek costs that plague random writes (Phase 1.5's latency table: a disk seek is ~10ms, while sequential I/O avoids paying that repeatedly). The catastrophic problem: to *read* a key, you'd have to scan the entire file from the start, checking every record, which is O(n) in the number of writes ever made — completely unworkable at any real scale.

### Hash indexes (Bitcask-style)

The fix: keep an **in-memory hash map** from every key to the **byte offset** in the file where that key's most recent value lives. A write still just appends to the log (cheap), but now also updates the in-memory hash map entry for that key. A read becomes: hash map lookup for the offset (O(1), in memory), then one direct disk seek straight to that offset (one seek, not a scan) to fetch the value. This is essentially the model **Bitcask** (the default storage engine in Riak) uses, and it's a legitimately excellent design specifically when **the set of distinct keys is small enough to fit in memory** (values can be arbitrarily large and live on disk, but every key needs an in-memory hash entry) and writes are frequent and random — Bitcask can sustain very high write throughput because every write is one sequential append, nothing more.

The obvious problem: an append-only file grows forever, even for keys that get overwritten or deleted many times (old values become dead weight, since only the hash map's latest offset matters — everything earlier for that key is garbage). The fix is **compaction**: break the log into fixed-size **segments** (once a segment hits some size threshold, stop writing to it and start a new one), and run a background process that reads through an old segment, keeps only the most recent value for each key it finds, discards everything else, and writes the survivors into a new, smaller segment (this is also called **segment merging**, since multiple old segments can be merged into one compacted segment in the same pass). Reads briefly need to check several recent segments (newest to oldest) until the key is found; a **tombstone** record marks a key as deleted so compaction knows to drop it entirely rather than keep a stale value around forever.

Limitations of the pure hash-index approach: the in-memory hash map must fit in RAM (a billion distinct keys means a billion-entry hash map living in memory, which becomes the actual scaling bottleneck, not the disk), and it fundamentally has **no support for range queries** — "give me all keys between `user:1000` and `user:2000`" requires checking every single key individually against the hash map, since a hash map has no concept of key ordering. That specific limitation is exactly what SSTables fix.

### SSTables (Sorted String Tables)

The refinement: instead of writing key-value pairs to a segment in whatever arbitrary order they arrived, **require that each segment file's keys are sorted by key** before being written to disk. This one change unlocks several things simultaneously:

1. **Merging segments becomes cheap and efficient**, exactly like a mergesort merge step: to merge several sorted segments into one, you can read all input files sequentially, always taking whichever file's current key is smallest, and write it out — an efficient sequential merge that never has to hold more than the current front of each file in memory, even if the files themselves are far larger than available RAM. This is the mechanism compaction uses under the hood once segments are sorted, and it's dramatically more efficient than the hash-index approach's compaction for large segments.
2. **You no longer need every key in the in-memory index** — since keys within a segment are sorted, you can keep a **sparse index**: an in-memory index of just *some* keys (say, every few kilobytes' worth), pointing at their offset. To find a specific key, jump to the offset of the nearest indexed key *before* it, then scan forward sequentially from there — since the file is sorted, the target key (if present) must be nearby. This means the in-memory footprint can be far smaller than the hash-index approach requires, since you're not indexing every single key, just periodic checkpoints.
3. **Range queries become natural** — because keys are physically stored in sorted order on disk, "give me everything between X and Y" is just "seek to X, then read sequentially until you pass Y" — no per-key lookup needed at all.

### LSM-trees (Log-Structured Merge-trees)

SSTables explain the *on-disk* format, but writes still need to be sorted before hitting disk — you can't efficiently insert a new key into the middle of an already-written, sorted file on disk. The LSM-tree is the full write path that makes this practical:

1. **Memtable** — writes first land in an in-memory, sorted data structure (commonly a balanced tree, e.g. a red-black tree or skip list) — cheap to insert into, and trivially kept sorted in memory. For durability against a crash before the memtable is flushed, writes are also appended to an on-disk **write-ahead log (WAL)** first, in unsorted append-only order — purely so the memtable's contents can be replayed and rebuilt if the process crashes before a flush.
2. **Flushing** — once the memtable grows past a size threshold, it's written out to disk as a new, immutable SSTable segment (this write is fast and sequential precisely because the memtable is already sorted in memory — writing it out is just a linear walk). A fresh, empty memtable is started for new writes, and the WAL can be discarded/reset once its corresponding memtable is safely flushed.
3. **Reads** — check the memtable first (most recent data), then progressively older on-disk SSTable segments, most recent first, until the key is found (or confirmed absent). To avoid checking every single old segment for a key that was never written (a genuinely absent key), engines commonly keep a **Bloom filter** per segment — a compact probabilistic structure that can say "definitely not in this segment" with certainty, or "maybe in this segment, go check," cutting down wasted disk lookups for misses dramatically.
4. **Compaction (merging in the background)** — over time, many SSTable segments accumulate. A background process continuously merges segments together (the sorted-merge process described above), discarding overwritten/deleted (tombstoned) values and reducing the number of segments a read has to check. Two dominant strategies: **size-tiered compaction** (merge similarly-sized segments together as they accumulate — simpler, but can temporarily use more disk space and produce read amplification since more segment "tiers" may need checking) and **leveled compaction** (organize segments into levels of exponentially increasing size, e.g. L0, L1, L2..., where each level is kept fully sorted and non-overlapping in key range — more predictable read/space behavior at the cost of more total compaction work). RocksDB and Cassandra both let you choose between these strategies per table/workload.

**Real implementations:** Google's original **Bigtable** paper introduced this design; **LevelDB** (Google) and its more feature-complete fork **RocksDB** (Facebook/Meta) are the canonical embeddable LSM-tree engines that power storage inside many other systems (Cassandra can use its own LSM implementation; MyRocks is RocksDB as a MySQL storage engine; CockroachDB and TiDB both build on RocksDB/Pebble); **Cassandra** and **HBase** use LSM-trees as their core storage engine; even **Kafka's** append-only partition log is philosophically the same "sequential append + sorted/offset-indexed segments" idea applied to a commit log rather than a general key-value store — sequential writes and sequential/indexed reads for the win in both cases.

## 2.5 B-trees vs LSM-trees — the tradeoff every DB pick hinges on

LSM-trees are one entire family of storage engine design. The other dominant family — the one underlying most traditional relational databases — is the **B-tree**, and the choice between these two families is arguably the single most consequential storage decision a database vendor (and, by extension, an interview candidate picking a database) makes.

### B-tree internals

A B-tree organizes data into fixed-size **pages** (or blocks — traditionally 4KB, matching common disk/filesystem block sizes), arranged as a tree: each page holds a sorted set of keys and pointers to child pages covering the key ranges between them, all the way down to **leaf pages** that hold the actual values (or pointers to them). Looking up a key means starting at the root page, and at each level picking the child pointer whose range contains the target key, descending until a leaf is reached — a B-tree with branching factor (fanout) in the hundreds can index billions of keys in only 3-4 levels of depth, meaning a lookup is only 3-4 disk reads even against enormous datasets.

The defining mechanical difference from LSM-trees: a B-tree performs **updates in place**. Changing a value means finding the exact page containing that key on disk and **overwriting that page directly**. Inserting a new key that doesn't fit in its target page anymore triggers a **page split** — the page's contents are divided into two pages, and a pointer to the new page is added to the parent page (which may itself need to split, recursively, all the way up in rare cases — this is how the tree stays balanced and shallow).

In-place overwriting is inherently riskier than LSM's append-only approach: if the database crashes mid-write (partway through overwriting a page), that page can be left in a corrupted, half-old-half-new state. The universal defense is a **write-ahead log (WAL)**, conceptually similar to the LSM-tree's WAL but serving a different purpose here: every intended modification is first appended to the WAL *before* the actual in-place page write happens; if the database crashes, on restart it replays the WAL from the last checkpoint to redo any writes that didn't make it into the actual B-tree pages, restoring consistency. Postgres calls this the WAL; MySQL/InnoDB calls the equivalent the redo log.

### The real comparison: write, read, and space amplification

- **Write amplification** — the ratio of bytes actually written to disk versus bytes the application logically asked to write. B-trees suffer here because a single logical one-row update can trigger writing an entire 4KB page (or several, on a split) just to change a few bytes, and the WAL write happens on top of that. LSM-trees also suffer write amplification, but from a different source: the same piece of data gets rewritten repeatedly as it's merged from the memtable into L0, then compacted into L1, L2, and so on — each compaction pass rewrites data that's already on disk. In practice LSM-trees are generally regarded as having *lower* write amplification than B-trees for random writes specifically, because writes are batched and sequential rather than triggering scattered random page overwrites — this is the core reason LSM-trees are favored for write-heavy workloads.
- **Read amplification** — the number of actual disk reads needed to answer one logical read. B-trees are excellent here: a lookup is a small, bounded number of page reads (the tree's depth, typically 3-4), full stop. LSM-trees can require checking the memtable, then potentially multiple SSTable segments across multiple levels (mitigated but not eliminated by Bloom filters and leveled compaction) — so LSM reads are generally *more* expensive than B-tree reads for point lookups, especially for a key that was written long ago and has sunk into a deep compaction level.
- **Space amplification** — how much disk space is consumed beyond the logical size of the data. B-trees waste space via **internal fragmentation** — pages are rarely perfectly full after splits and deletions, leaving allocated-but-unused space inside each page (more on this in 2.8). LSM-trees waste space by keeping multiple versions of overwritten/deleted keys around simultaneously until compaction catches up and reclaims them — under heavy write load, an LSM-tree can temporarily bloat to well beyond its logical data size before compaction catches up.

| | B-trees | LSM-trees |
|---|---|---|
| Write pattern | In-place random overwrite | Append-only, sequential |
| Write amplification | Higher (whole-page rewrites, WAL) | Lower for the initial write, but ongoing compaction rewrites |
| Read amplification | Low, bounded (tree depth) | Higher (multiple segments/levels to check) |
| Space amplification | Internal fragmentation from partially-full pages | Temporary duplication until compaction runs |
| Best for | Read-heavy, latency-sensitive point lookups | Write-heavy, high ingest throughput |
| Real examples | Postgres, MySQL/InnoDB, SQLite, Oracle, SQL Server | Cassandra, HBase, RocksDB, LevelDB, ScyllaDB |

**The rule of thumb every DB pick hinges on:** if the workload is dominated by writes (ingest-heavy logging, event pipelines, time-series, high-write-throughput OLTP), lean LSM-tree (Cassandra, RocksDB-backed stores). If the workload is dominated by reads, especially latency-sensitive point lookups and range scans with a relatively modest write rate, lean B-tree (Postgres, MySQL). This single tradeoff explains why, for example, a metrics/logging pipeline commonly reaches for Cassandra while the same company's transactional order database is on Postgres — it's not fashion, it's this exact write/read amplification tradeoff matched to two genuinely different access patterns.

## 2.6 Column-oriented storage (for analytics/OLAP)

Everything in 2.4–2.5 assumed a **row-oriented** storage layout: all the columns belonging to one row are stored physically adjacent to each other on disk, so fetching "everything about order #4471" is one contiguous read. This is exactly right for **OLTP (Online Transaction Processing)** workloads — the bread-and-butter of an e-commerce or banking app — which are dominated by queries that touch a handful of rows but need most/all of their columns (fetch this one order and everything about it, update this one user's address).

**OLAP (Online Analytical Processing)** workloads are structurally the opposite: an analytics query like "what was our average order value by region, last quarter" touches **millions or billions of rows**, but only needs **two or three columns** out of possibly dozens (`region`, `order_value`, `order_date`) — it doesn't care about `shipping_address`, `customer_notes`, or the other twenty columns sitting in each row. In a row-oriented layout, answering this query still means reading every full row off disk (all columns, including the ones you don't need) just to pluck out three fields from each — a massive waste of I/O.

### Column-oriented storage layout

The fix: store each **column's values contiguously**, across all rows, in its own separate file/block — so a query needing only `region`, `order_value`, and `order_date` reads *only* those three column files sequentially, never touching the other columns' bytes at all. For an analytics query scanning billions of rows but a handful of columns, this alone can cut I/O by an order of magnitude or more.

Column-orientation additionally unlocks two big performance wins that a row-store fundamentally can't get as easily:

- **Compression** — a column contains many repeated or closely-related values of the *same type* (e.g., a `region` column might have only a few dozen distinct values repeated across billions of rows; a `status` column might be one of five enum values). This is exactly where techniques like **bitmap encoding** (represent each distinct value as a bitmap of which rows contain it — very compact when the number of distinct values is small, and bitmaps can be combined with fast bitwise AND/OR for filtering) and **run-length encoding** (if a sorted or naturally-clustered column has long runs of the same value, store "value X repeated N times" instead of X written out N times) shine — applied per-column, these routinely achieve compression ratios that a row-oriented format, which interleaves columns of completely different types and cardinalities, can't match nearly as well.
- **Vectorized processing** — because a column's data is packed contiguously and uniformly typed, the CPU can process it in tight, cache-friendly batches using SIMD (Single Instruction, Multiple Data) instructions — applying the same operation (a filter, a sum) to many values in one instruction — rather than the CPU-cache-unfriendly, branch-heavy row-by-row processing a row store requires. This is a major reason column stores achieve much higher throughput on aggregation-heavy queries.

### Real examples, and a genuine naming trap

- **Apache Parquet** — a column-oriented *file format* (not a database itself) widely used in data lakes (S3 + Spark/Athena/Presto-style architectures) — the de facto standard for storing analytical datasets at rest.
- **Amazon Redshift** and **Google BigQuery** — full column-oriented analytical database/warehouse systems, built ground-up around this layout, with query engines specifically optimized to exploit it (BigQuery in particular is famous for scanning terabytes of column data in seconds by parallelizing across a massive fleet and reading only the referenced columns).
- **The naming trap: "wide-column stores" (Cassandra, HBase) are NOT true column stores.** This confusion trips people up constantly. Cassandra's "column family" terminology refers to *sparse, flexible rows where each row can have a different set of named columns* (2.2's wide-column data model) — but *physically*, all the columns belonging to one row key are still stored together, colocated on disk, exactly like a row store. It's optimized for "fetch everything about this one row key fast," which is a row-store access pattern, not "scan one column across billions of rows," which is what true column-orientation (Parquet, Redshift, BigQuery) optimizes for. The word "column" in "wide-column store" describes the *data model's flexibility*, not the physical *storage layout* — these are two unrelated uses of the same word, and conflating them is a common and understandable mistake.

| | Row-oriented (OLTP) | Column-oriented (OLAP) |
|---|---|---|
| Physical layout | All columns of one row together | All rows of one column together |
| Best query shape | Few rows, many/all columns (`fetch order #4471`) | Many rows, few columns (`avg order value by region`) |
| Compression | Modest (mixed types per block) | Excellent (uniform type/cardinality per column) |
| Real examples | Postgres, MySQL, DynamoDB | Parquet, Redshift, BigQuery, Snowflake |
| Cassandra/HBase | — | Despite the name, physically row-oriented per row key |

## 2.7 Encoding formats: JSON/XML vs binary (Protobuf, Avro, Thrift) — schema evolution

Whenever data crosses a process boundary — written to disk, sent over a network to another service, passed between two versions of the same application during a rolling deploy — it has to be **encoded** (serialized) into bytes and later **decoded** (deserialized) back into an in-memory structure. The format chosen for this has real, measurable consequences for size, speed, and — the part that actually causes production incidents — how gracefully the format tolerates the schema changing while both old and new code are running simultaneously.

### Textual formats: JSON, XML, CSV

Human-readable, ubiquitous, trivially debuggable (you can just look at the bytes and understand them), and universally supported. But they carry real costs at scale: they're **verbose** — field names are repeated as literal text in every single record (`{"user_id": 4471, "user_id": ...}` a million times over, versus a binary format that would encode `user_id` as a one- or two-byte tag once the schema is known) — and they have **ambiguity problems**: JSON has no native distinction between integers and floating-point numbers (a large integer can silently lose precision when parsed as a JS-style float), no native binary/byte-string type (binary data must be Base64-encoded, inflating size further and adding encode/decode overhead), and no built-in schema, meaning validation and structure enforcement is bolted on externally (JSON Schema) rather than intrinsic to the format the way it is for the binary schema-based formats below. XML has a schema mechanism (XSD) but is even more verbose than JSON due to closing tags, and has largely fallen out of favor for new API/data-interchange work in favor of JSON, while remaining common in older enterprise/SOAP-style systems and certain document formats.

### Binary formats: Protocol Buffers, Thrift, Avro

The core mechanism that makes binary encodings compact **and** capable of graceful schema evolution is the **field tag**. Rather than writing out `"user_id":` as literal text before every value, the schema assigns each field a small integer tag once (e.g., `user_id = 1`, `email = 2`), and the encoded bytes just contain `<tag><type><value>` — the field *name* never appears in the actual encoded data at all, only in the schema definition both sides share. This is simultaneously why binary formats are compact (no repeated field-name text) and why they can evolve safely: a decoder reading data encoded with a newer or older schema can match incoming tags against the tags it knows, and simply skip any tag it doesn't recognize, because the encoded bytes are self-describing enough (tag + type + length) to skip past without understanding the field's meaning.

This yields the schema-evolution rules that actually matter in practice:
- **Adding a new field** is safe **only if it's optional** (or has a default) — old code reading new data simply doesn't see the new tag and ignores it (**forward compatibility** — old code can read data written by new code); new code reading old data that lacks the new field just uses the default (**backward compatibility** — new code can read data written by old code). If a new field were required, old data lacking it would fail to decode under the new schema, breaking backward compatibility.
- **Never reuse a tag number.** If a field is removed, its tag number must be retired, never reassigned to a new field — because old data still on disk (or old messages still in flight) with that tag would otherwise be misinterpreted as the new field's type/meaning once decoded under the new schema. This single rule is the most common real-world mistake with these formats.
- **Never remove a required field**, and generally avoid `required` fields altogether in evolvable schemas (Protobuf 3 dropped the `required` keyword entirely for exactly this reason) — a required field can never safely be added *or* removed later without breaking compatibility in one direction, so making everything effectively optional from the start is the safer default.

### Protobuf/Thrift vs Avro — where the tag actually lives

**Protocol Buffers (Google)** and **Apache Thrift (originally Facebook)** are conceptually siblings: both require a `.proto`/`.thrift` schema file with explicit numeric tags assigned to every field, both generate strongly-typed code (stubs/classes) for many languages from that schema, and both are the backbone of RPC frameworks (gRPC uses Protobuf natively; Thrift has its own RPC layer too — this is the same Thrift referenced in Phase 1.7's RPC section). Because the tag numbers live in the schema definition itself, both the writer and reader need access to (a compatible version of) the schema to encode/decode correctly — the tags aren't derivable from the data alone.

**Apache Avro** takes a structurally different approach: Avro schemas (defined in JSON, somewhat ironically) have **no tag numbers at all** — fields are just encoded in the exact order the schema defines, back to back, with no field identifiers in the byte stream whatsoever, making it even more compact than tag-based formats. The catch: a decoder **absolutely cannot read Avro data without the exact schema it was written with** (there's nothing to fall back on — no tags to match), so Avro's compatibility model instead works by having the **reader's schema and writer's schema both be available at decode time**, and Avro's library reconciles differences between the two (matching fields by name, applying defaults for fields present in one schema but not the other) — this is why Avro-encoded files/streams are typically accompanied by (or embed) the writer's schema, and systems like Kafka pair Avro with a **schema registry** service that stores and versions schemas centrally so any consumer can look up exactly which schema a given message was written with.

This distinction is exactly why DDIA highlights Avro as a particularly good fit for **dynamically generated schemas** — the canonical example being a database export/dump job. If you're periodically dumping an entire database's tables to files for a downstream analytics job, and the database schema might have gained or lost a column since the last dump, Avro can derive its schema straight from the database's current schema *automatically*, with no hand-maintained tag numbers to keep in sync — there's no equivalent of manually assigning and tracking Protobuf/Thrift tag numbers for every column of every table, which would be painful to maintain by hand across an evolving database schema over years.

| | JSON/XML | Protobuf / Thrift | Avro |
|---|---|---|---|
| Human-readable | Yes | No | No |
| Compactness | Low (verbose, repeated field names) | High (tag-based) | Highest (no tags at all, positional) |
| Schema required | Optional, bolted-on | Required (`.proto`/`.thrift`) | Required, but derivable/dynamic |
| Compatibility mechanism | None built-in | Tag matching, skip unknown tags | Reader/writer schema reconciliation |
| Great fit for | Public APIs, human debugging, ad hoc data | RPC (gRPC), strongly-typed service contracts | Dynamically-generated schemas, e.g. DB dumps, Kafka streams via schema registry |

## 2.8 Disk fragmentation: internal vs external — why storage engines compact/vacuum over time

Both the B-tree and LSM-tree stories above ended with the same shape of problem — pages that aren't fully packed, and old data lying around waiting to be reclaimed — and both trace back to one underlying physical-storage concept: **fragmentation**. Understanding it precisely explains *why* compaction and vacuuming aren't optional housekeeping but a structural necessity of both engine families.

**Internal fragmentation** is wasted space *inside* an allocated unit — the allocation is bigger than what's actually being used, and that slack space can't be used for anything else because it's already claimed. B-tree pages are the textbook example: a page is a fixed size (say 4KB), but after deletions, or right after a split that divides a page's contents roughly in half, a given page might genuinely only be, say, 60% full — the remaining 40% is allocated to that page, sitting on disk, but empty. Multiply that across millions of pages in a large table and a meaningful fraction of the table's on-disk footprint is pure internal fragmentation — space consumed but not holding live data.

**External fragmentation** is a different failure mode: it's not that any one allocation wastes space internally, it's that **free space is scattered across many small, non-contiguous chunks** throughout the storage, none of which is individually large enough to satisfy a new allocation that needs a contiguous block — even though the *total* free space, summed up, would be more than enough. This classically shows up after a long history of allocating and freeing variable-sized chunks: deletes and updates over time leave behind a patchwork of small gaps between still-live data, and a new write that needs one contiguous chunk of "quite a lot of space" can't find one even though plenty of free space exists in aggregate, just not contiguously.

**Why this directly explains LSM-tree compaction and Postgres VACUUM:**

- **LSM-tree compaction** exists specifically because of a fragmentation-adjacent problem: overwritten and deleted keys leave **dead, unreachable data** scattered across old SSTable segments — every old copy of a key that's since been overwritten, and every tombstoned deleted key, is pure waste sitting in an immutable segment file that can't be edited in place. Compaction's entire job is to walk through these segments, discard everything superseded or tombstoned, and rewrite only the live survivors into fresh, densely-packed segments — directly reclaiming exactly this kind of space waste, and simultaneously reducing the number of segments a read has to check (tying back to the read-amplification discussion in 2.5).
- **Postgres `VACUUM`** exists because of Postgres's MVCC (Multi-Version Concurrency Control, Phase 3.6 territory) design: an `UPDATE` in Postgres doesn't overwrite a row in place — it writes an entirely new row version and marks the old version as dead (a `DELETE` similarly just marks a row dead rather than immediately reclaiming its space), so that concurrent transactions that started before the change can still see the old, consistent version they expect. Over time this leaves dead row versions scattered throughout table pages — internal fragmentation within pages (dead space inside a page that's technically allocated to the table but not holding live data) that ordinary queries simply skip over but that keeps the table's on-disk size growing unless something reclaims it. `VACUUM` scans through and marks that dead-row space as reusable for future inserts/updates on the same table (or, in its `VACUUM FULL` variant, actually rewrites the whole table compactly and returns space to the OS) — mechanically, this is the exact same instinct as LSM-tree compaction: periodically walk through accumulated debris from an update-heavy, non-overwrite-in-place workload and reclaim it, because the storage engine's write strategy (append-new-version-rather-than-overwrite) is precisely what's generating the fragmentation in the first place. Skipping this maintenance is exactly why "table bloat" and "VACUUM falling behind" are real, well-known Postgres operational failure modes at high write throughput — the fragmentation doesn't go away on its own, and if dead-tuple accumulation outpaces vacuuming, both query performance and disk usage degrade until it's forced to catch up (or the database, in the worst case, risks transaction ID wraparound issues if vacuuming is neglected long enough).

The throughline across this entire file: whether it's a B-tree page, an LSM-tree segment, or a Postgres heap page, every storage engine design in this space is making the same underlying bet — that it's cheaper to write append-only/in-place now and periodically pay a background cleanup cost (compaction, vacuuming) than to keep every write perfectly compact in real time. Understanding *why* that bet is made, and what specifically it's cleaning up after, is what separates "Postgres needs VACUUM" as a memorized fact from an actual mechanical understanding of the tradeoff.

(a) No — and this is exactly the point of using Avro (or Protobuf/Thrift) instead of a raw, ad hoc binary format in the first place.
