# Phase 3 — Distributed Data

This is the phase. Almost every "design X at scale" interview eventually collapses into a question about this material: how do multiple copies of data stay (or fail to stay) in agreement, what happens when the network between them misbehaves, and what you're willing to give up to keep the system alive anyway. Interviewers who go deep on a design almost always go deep *here* — "what happens if the leader dies mid-write," "how do you handle two users editing the same row at once," "why not just wrap that in a distributed transaction" — and a hand-wavy answer is the single fastest way to lose credibility in the room. Grounded in Kleppmann's *Designing Data-Intensive Applications*, Part II (Chapters 5–9).

---

## 3.1 Replication: leader-follower, multi-leader, leaderless (Dynamo-style)

Replication means keeping a copy of the same data on multiple machines, for three overlapping reasons: **availability** (the system keeps working if one machine dies), **latency** (put a copy near the user instead of making every request cross a continent), and **read scalability** (spread read traffic across many copies). The hard part is never copying the data once — it's keeping every copy in sync as writes keep happening. There are exactly three architectures for this, and the difference between them is *who is allowed to accept writes*.

### Leader-follower (single-leader) replication

One node is designated the **leader** (a.k.a. primary/master). All writes go through it. It then propagates the write to zero or more **followers** (replicas/slaves) via a **replication log**. Followers apply writes in the same order the leader committed them, and reads can be served by the leader or, for read scaling, by any follower (accepting some staleness — see 3.2). This is the default replication model for almost every relational database (Postgres, MySQL) and plenty of non-relational ones (MongoDB in replica-set mode).

**How the leader actually ships changes to followers — three distinct mechanisms, and they are not interchangeable:**

1. **Statement-based replication:** the leader literally forwards the SQL statement it executed (`INSERT ...`, `UPDATE ...`) and each follower re-executes it locally. Sounds elegant — minimal bytes over the wire — but it's a correctness minefield: any statement with a non-deterministic function (`NOW()`, `RAND()`), an auto-incrementing column, or a side-effecting subquery can produce a *different* result on each follower than it did on the leader. Early MySQL used this by default and moved away from it for exactly this reason.

2. **Write-ahead log (WAL) shipping:** every storage engine that supports crash recovery already writes a low-level, append-only log of every byte change to disk *before* applying it (the WAL — this is also how the engine recovers after a crash, replaying the log from the last checkpoint). Replication can simply ship this exact log to followers, which replay it byte-for-byte. This is what Postgres streaming replication does. The catch: the WAL describes changes at the level of **which bytes changed on which disk blocks** — it is intimately tied to the specific storage engine's on-disk format. That coupling means you typically can't run a different storage engine version (sometimes not even a different minor version) on leader vs follower, and it makes zero-downtime storage-engine upgrades hard, because the log format itself might change between versions.

3. **Logical (row-based) log replication:** a separate log format, decoupled from the storage engine's internal byte representation, that describes changes at the level of rows — "insert this row with these column values into this table," "row with this primary key was updated to these new values," "row with this primary key was deleted." MySQL's row-based binlog format works this way. Because it doesn't leak storage-engine internals, it enables things WAL shipping can't: replicating to a different storage engine version, feeding the change stream to external consumers for **change data capture** (a preview of Phase 4 — CDC pipelines commonly tap a logical replication log rather than a WAL, precisely because it's stable and interpretable outside the database process), and building custom conflict-resolution logic on top since the log describes semantic changes rather than opaque byte diffs.

**Setting up a new follower:** you cannot just start streaming from "now," because there's no fixed offset that corresponds to "the leader's current state" without freezing writes (unacceptable on a live system). The real recipe: take a **consistent snapshot** of the leader's data at some point (most storage engines can do this without a global write lock, e.g. Postgres's `pg_basebackup`), note the exact log position that snapshot corresponds to, copy the snapshot to the new follower, then have the follower request all changes from the leader's log **since that exact position** onward. Once it's caught up to "now," it just keeps streaming forward.

**Handling follower failure:** a follower keeps a local log of the last transaction it processed; on restart, it just asks the leader to resume from that position. Easy.

**Handling leader failure — failover — is the genuinely hard part:** (1) detect the leader is actually dead, not just slow (usually a timeout — and there is no way to distinguish "leader is dead" from "network to leader is briefly bad" from the outside, which is exactly why timeout-based detection produces false positives); (2) promote a follower to new leader (ideally the one that was most caught-up, to minimize lost writes); (3) reconfigure clients and other followers to point at the new leader. Two failure modes make this genuinely dangerous in production:
- **Split brain:** the old leader wasn't actually dead (just network-partitioned from the coordinator doing the detecting) and comes back thinking it's still leader — now two nodes both accept writes, and they diverge. Systems need a way to force the old leader to step down (fencing — see 3.7) or this silently corrupts data.
- **Lost writes on failover:** if the old leader had accepted writes that hadn't yet replicated to the follower being promoted, those writes are simply gone once the new leader takes over.

**Real systems:** Postgres streaming replication (WAL-based), MySQL binlog replication (statement-based historically, row-based/logical now the safer default), MongoDB replica sets (oplog-based, logical).

### Multi-leader replication

Instead of one leader, **multiple nodes each accept writes**, and each propagates its writes to every other leader. This immediately reintroduces the exact problem single-leader replication was designed to avoid — concurrent writes to the same data on different leaders — but it's worth the pain in specific scenarios:

- **Multi-datacenter operation:** run one leader per datacenter. Writes made in a datacenter are handled by the local leader (low latency, no cross-region round trip on every write) and asynchronously replicated to the other datacenters' leaders. Compare to single-leader-per-region: every write anywhere in the world has to cross the network to the one true leader, which is a latency tax multi-leader avoids by construction. The cost is real, though — cross-datacenter network links are exactly where replication topology gets fragile, and now you have to handle write conflicts (3.12).
- **Clients with offline support:** think a calendar app that lets you edit events with no network connectivity — every device is effectively its own "leader" accepting local writes while offline, and reconciles with everyone else's writes once it reconnects. Tools like CouchDB were explicitly built around this model.
- **Collaborative real-time editing** (Google Docs-style): each user's edits are, conceptually, local writes to their own copy that need to merge with everyone else's concurrent edits — the same shape of problem as multi-leader replication, just at a much smaller and faster timescale (character/keystroke level, not row level), typically solved with **CRDTs (conflict-free replicated data types)** or **operational transformation** rather than generic database-level conflict resolution.

The unavoidable cost of multi-leader: **conflicting concurrent writes**, which single-leader systems structurally cannot have (there's only ever one node deciding write order). Resolution strategies are covered in depth in 3.12.

### Leaderless (Dynamo-style) replication

No leader at all. **Any replica can accept a write directly from a client**, and clients (or a coordinator node acting on their behalf) write to and read from **multiple replicas in parallel**, tolerating some being unavailable. This is the model Amazon's internal Dynamo system pioneered (2007 paper), and it directly inspired **Cassandra**, **Riak**, and **Voldemort**; Amazon's public-facing **DynamoDB** is a distinct, separately-built product that borrows the name and some ideas but is not literally the same system.

**Quorum reads/writes — the N/W/R parameters:**
- **N** = number of replicas the data is stored on.
- **W** = number of replicas that must acknowledge a write before it's considered successful.
- **R** = number of replicas a read must query (returning the most recent value among the responses, usually by version/timestamp) before it's considered successful.

If **W + R > N**, every read is guaranteed to overlap with at least one replica that has the latest write — this is the quorum guarantee, and it's the leaderless world's substitute for having a single leader serialize everything. A common configuration is N=3, W=2, R=2 (`2+2 > 3`): tolerates one replica being down for both reads and writes, at the cost of needing 2 out of 3 replicas to respond. Turning the dials trades off differently: lower W = faster, more available writes but weaker durability; lower R = faster reads but higher risk of reading stale data; W=1,R=N or W=N,R=1 pushes all the cost onto one side.

Note this quorum condition is necessary but **not sufficient** for strong consistency in every edge case — concurrent writes, network partitions mid-write, and clock issues can still produce anomalies (this is revisited properly under linearizability in 3.8).

**Read repair:** when a read queries multiple replicas and notices one returned a stale value, the coordinator writes the newer value back to the stale replica as a side effect of the read itself. This quietly fixes staleness for frequently-read keys without any separate background process.

**Hinted handoff:** if a replica that should receive a write is temporarily down, another node accepts the write on its behalf, stores it with a "hint" saying which node it was really meant for, and forwards it once that node comes back. This is what lets writes succeed even when the "correct" target replica is unreachable.

**Sloppy quorums:** the strict version of quorum reads/writes requires exactly the N designated home replicas to participate. A **sloppy quorum** relaxes this — if some of the designated N nodes are unreachable, the write is accepted by *any* W available nodes in the cluster (not necessarily the "right" ones), with hinted handoff used to get the data to its rightful home later. This trades strict quorum-overlap consistency for higher write availability during partial outages — Dynamo's original design explicitly favors availability here, which is a direct expression of the CAP tradeoff (3.9) baked into the architecture.

| | Leader-follower | Multi-leader | Leaderless (Dynamo-style) |
|---|---|---|---|
| Who accepts writes | One leader | Several designated leaders | Any replica, via quorum |
| Conflict handling | None needed (single order) | Required (async convergence) | Required (concurrent writes, quorum overlap) |
| Write availability during a partition | Blocked if leader unreachable | High (each region's leader keeps working) | High (sloppy quorums) |
| Real systems | Postgres, MySQL, MongoDB | Multi-DC MySQL/Postgres setups, CouchDB | Cassandra, Riak, DynamoDB |

## 3.2 Sync vs async replication, replication lag, read-your-writes consistency

### Synchronous vs asynchronous replication

When the leader accepts a write, does it wait for followers to confirm before telling the client "success"?

- **Synchronous:** the leader waits for (at least one) follower to confirm it has received and applied the write before acknowledging the client. Guarantee: that follower's copy is definitely up to date the instant the client hears "success" — durability is much stronger, because even if the leader dies the very next instant, a fully caught-up follower exists to take over with zero data loss. Cost: write latency is now bounded by the slowest step in that follower's round trip, and if that follower is unreachable, **writes block entirely** — you've traded latency and availability for durability.
- **Asynchronous:** the leader acknowledges the client immediately and replicates in the background. Cost: if the leader dies before the write reaches any follower, that write is **lost** — permanently, silently, no error was ever shown to the client because none occurred at write time. Benefit: writes stay fast and available even if every follower is down or slow.
- **Semi-synchronous (the common real-world compromise):** one follower is synchronous (guaranteeing at least one fully up-to-date copy exists at all times) and the rest are asynchronous. If the synchronous follower becomes unresponsive, the leader typically promotes a different follower to be the new synchronous one, so the system never actually blocks forever on a single dead follower.

This is a direct, concrete durability-vs-latency/availability tradeoff — no cleverness escapes it, only where you place the dial.

### Replication lag and its three concrete anomalies

Fully asynchronous followers can lag behind the leader — under normal load, by milliseconds; under load spikes, network issues, or if a follower is just slow, by seconds or literally minutes. This lag is invisible in the happy path and becomes very visible the moment a user's own actions seem to disappear or reorder. Three specific, well-known symptoms and their fixes:

**1. Read-your-writes consistency.** A user submits a comment, then the page reloads and routes the read to a lagging follower that hasn't received it yet — the user's own just-written comment appears to vanish. This is jarring specifically because it's *the user's own action*, not some abstract staleness. Fixes: (a) for data a user might have just modified, always route that specific read to the leader (e.g., always read your own profile from the leader, but other users' profiles from a follower); (b) track a logical timestamp (or replication log position) of the user's last write, and when reading, only query a follower that has caught up to at least that position — otherwise fall back to the leader or wait.

**2. Monotonic reads.** A user issues two reads in a row, and by bad luck they land on two different followers with different amounts of lag — the second read (against the less-caught-up follower) shows an *older* state than the first read did. To the user, time appeared to run backward. Fix: ensure each user's reads are always routed to the **same replica** (e.g., a hash of the user ID picks the replica deterministically) — that replica may still be behind the leader, but at least it's only ever moving forward from that one user's perspective.

**3. Consistent prefix reads.** If writes happen in a causal order (a question is asked, then an answer is given), a lagging replica might apply those writes out of order relative to what an observer sees, because in a sharded/partitioned system different partitions can replicate at independent, uncoordinated speeds. Kleppmann's canonical example: someone asks "How far away is the moon?" and someone else replies "About 384,400 km" — if an observer's read hits a replica that has received the answer's partition update but not yet the question's, they see the answer appear *before* the question was ever asked, which is nonsensical. Fix: ensure that writes which are causally related are written to the same partition (so ordering is trivially preserved), or use an explicit mechanism to track and preserve causal dependencies across partitions when replicating.

All three problems have the same root cause — asynchronous replication means "the current state of replica X" is not a single well-defined thing across the whole cluster at any given instant — and all three fixes are really the same idea in different clothes: track *some* notion of "how far has this replica progressed" and use it to route or gate reads.

## 3.3 Partitioning/Sharding: by key range, by hash — and the hot-spot problem

Replication handles "the same data on multiple machines." **Partitioning** (a.k.a. sharding) handles the orthogonal problem: the dataset is too large or too hot for *any single machine* to hold or serve, so it's split into disjoint pieces, each piece owned by a different node (and each piece is typically *also* replicated, per 3.1 — the two techniques compose). The entire game in partitioning is choosing which records land on which partition such that (a) you can find them again efficiently and (b) load spreads evenly across nodes.

### Partitioning by key range

Each partition is assigned a contiguous range of keys — e.g., partition 1 holds keys A–G, partition 2 holds H–M, and so on — and the boundaries are typically adjusted dynamically as data grows (see 3.4). This is how Bigtable and HBase partition row keys, and it's what early sharded MongoDB deployments used.

**Advantage:** range scans are efficient and cheap — "give me all events between timestamp X and Y" or "all users with last names starting with Sm" hits one, or a small contiguous number, of partitions, because sort order on disk matches the partition key order.

**The hot-spot risk:** if the partition key is something monotonically increasing — most classically, a timestamp — then **all writes for "right now" land on the same partition**, no matter how many partitions exist in total, because "now" is always at the tail end of the range. Every other partition sits idle while one node absorbs 100% of write traffic. This is a real, common design mistake: a naive time-series schema partitioned purely by timestamp will always bottleneck on whichever partition owns the current time window.

### Partitioning by hash

Apply a hash function to the key, and use the hash's value (not the raw key) to decide the partition — e.g., partition = `hash(key) mod num_partitions` (or, in practice, a range of the hash's output space, often arranged via consistent hashing so that adding/removing nodes doesn't require reshuffling everything — see Phase 5, 5.11). A good hash function spreads similar keys uniformly across the hash space, so sequential or clustered keys no longer cluster on one partition. Cassandra and DynamoDB default to this.

**Advantage:** load spreads much more evenly, and the timestamp hot-spot problem above simply disappears, because `hash(timestamp)` for two adjacent timestamps lands in wildly different, effectively random partitions.

**The cost:** you lose efficient range scans. "All events between X and Y" can no longer be answered by touching one contiguous partition — it now requires querying *every* partition and merging results (**scatter-gather**), because rows that were adjacent by key are now scattered randomly across the whole cluster by design.

### The hot-spot problem and its concrete mitigation

Even hash partitioning doesn't save you if a single *specific* key gets disproportionately hot — a celebrity's account in a social app, a viral product ID in an e-commerce app — because `hash(that one key)` is still just one fixed value, landing all traffic for that one key on one partition regardless of how well-distributed the rest of the keyspace is.

**Mitigation: add a random prefix or suffix to the hot key**, splitting its writes across multiple partitions instead of one — e.g., instead of key `celebrity123`, write to `celebrity123-0` through `celebrity123-9` (a random one of ten chosen per write), spreading that one logical entity's write load across ten partitions instead of concentrating it on one. The cost is symmetric with the benefit: **reads now have to scatter-gather** across all ten suffixed keys and merge the results client-side (or in an aggregation layer) to reconstruct the full picture for that entity, since there's no longer one canonical location holding all of `celebrity123`'s data. This technique is only worth applying to the specific keys that are actually hot — applying it universally just re-imposes scatter-gather cost on every read for no benefit.

| | Range partitioning | Hash partitioning |
|---|---|---|
| Range scans | Efficient (contiguous on disk) | Requires scatter-gather across all partitions |
| Load distribution | Risk of hot spots (esp. sequential keys) | Generally even |
| Hot single-key mitigation | N/A (different problem) | Random prefix/suffix + scatter-gather read |
| Example systems | Bigtable, HBase | Cassandra, DynamoDB (default) |

## 3.4 Rebalancing partitions, request routing to the right shard

### Rebalancing: what happens as data grows or nodes are added/removed

A partitioning scheme fixed at day one inevitably needs to change — the dataset grows past what the original partition count can hold well, or nodes are added for more capacity, or a node dies and its data needs to land somewhere else. **Rebalancing** is the process of moving partitions (or splitting them) across nodes to keep load even, and the naive approach — `hash(key) mod N` where N is the node count — is actively bad, because changing N reshuffles *almost every key's* assigned partition simultaneously, triggering a massive, unnecessary data migration for what might be a one-node capacity bump. Three real strategies avoid this:

1. **Fixed number of partitions, sized larger than the current node count.** Create far more partitions up front than you have nodes today (e.g., 1,000 partitions across 10 nodes, ~100 partitions per node) — when a new node joins, it simply takes ownership of some partitions from existing nodes (whole partitions move, but no partition is ever re-split, and no key ever gets reassigned to a *different* partition — only the partition-to-node mapping changes). Simple and predictable, but you must guess the eventual partition count in advance: too few and you can't scale finely; too many and per-partition overhead (file handles, metadata, compaction bookkeeping) adds up. This is Elasticsearch's and Riak's approach by default.

2. **Dynamic partition splitting.** Partitions split automatically once they exceed a configured size threshold, with each half handed off to (potentially) a different node — and small partitions can merge back together if data is deleted. This adapts naturally to actual data volume rather than a pre-guessed number, but is more operationally complex to implement correctly and can cause uneven initial load if you start with one partition holding the entire dataset (an empty database has nothing to split yet). HBase and MongoDB use this model.

3. **Partitioning proportional to the number of nodes.** Fix the number of partitions *per node* (not the total) — when a new node joins, it randomly picks existing partitions to split and takes ownership of half of each, keeping partition count-per-node roughly constant as the cluster grows. Cassandra uses this approach.

Regardless of strategy, rebalancing should ideally be **mostly automatic** for operational sanity, but fully automatic rebalancing is risky if load detection is noisy — an automated system can misjudge "this node is slow" as "this node is overloaded" and trigger a cascading, unnecessary rebalance that makes things worse; many production systems keep a human in the loop to approve the trigger even if the mechanics are automated.

### Request routing: how does a client find the right node?

Once data is split across partitions that move around over time, something has to answer "which node do I send this request to *right now*." Three architectural answers:

1. **A routing tier that queries a separate coordination service.** Clients (or a load-balancer-like proxy layer in front of the cluster) ask a dedicated, strongly-consistent coordination service which node currently owns a given partition, then route the request there directly. **ZooKeeper** (used by Kafka and HBase for exactly this) and **etcd** (used by Kubernetes and CockroachDB) are the canonical tools for this role — they're small, highly-consistent key-value stores built specifically to hold this kind of critical cluster metadata reliably, using a consensus protocol underneath (ZooKeeper uses ZAB, etcd uses Raft — see 3.10) so that the routing information itself never becomes inconsistent or lost.

2. **Gossip protocol between nodes.** No separate coordination service — every node in the cluster knows the full partition-to-node mapping itself, and nodes periodically exchange (“gossip”) their view of cluster state with each other so that any node can correctly redirect a misrouted request even after a rebalance. Cassandra and Riak use this — it removes a dependency on an external coordination system, at the cost of more complex node-to-node protocol logic and briefer windows of inconsistency while gossip propagates.

3. **Client-side partition awareness.** The client library itself embeds the partitioning logic (e.g., it knows the hash function and the current partition map) and computes which node to talk to directly, skipping an intermediate routing hop entirely. This is faster (no extra network hop) but couples client code to cluster topology, and the client needs some way to learn about topology changes (often by subscribing to the same coordination service from option 1, just from the client side instead of a proxy tier).

These aren't mutually exclusive in practice — e.g., Kafka clients use client-side partition awareness for the data-plane requests but still consult ZooKeeper/the controller (metadata plane) to learn the current partition map in the first place.

## 3.5 Transactions: ACID properly explained, weak isolation pitfalls

A **transaction** groups multiple reads/writes into one logical unit that the application can treat as a single operation — either it all happens, or none of it does, insulating application code from having to worry about partial failures and concurrent access itself. **ACID** is the classical (if inconsistently-used-in-marketing) definition of what a "real" transaction guarantees. Each letter is a genuinely separate guarantee, and it's worth knowing precisely what concretely breaks if that one letter is dropped.

- **Atomicity:** a transaction's writes either *all* happen or *none* happen — there is no such thing as a transaction that's half-committed. Without atomicity: if a transaction crashes partway (server dies mid-write), you're left with some writes applied and others not, e.g. a bank transfer where money left account A but never arrived in account B — the database is now in a state that never should have been reachable by any correct execution. Atomicity is what makes "if anything fails, everything rolls back" a fact you can rely on instead of something the application has to hand-implement with manual undo logic. Mechanically implemented via the WAL — the transaction's intended writes are journaled *before* being applied, so on crash-recovery, any transaction that didn't reach a "commit" marker in the log gets rolled back.

- **Consistency (the application-level kind, distinct from the "C" in CAP — genuinely different concept sharing an unfortunate letter):** the database moves from one *application-valid* state to another — invariants like "account balances always sum to zero across a transfer" or foreign-key constraints hold before and after every transaction. Without it: nothing enforces that a transaction leaves data in a state the application logic actually expects — e.g., a transfer could commit having only debited one account, or a row could reference a foreign key that doesn't exist. Note this is actually **the application's responsibility, not purely the database's** — the database provides atomicity/isolation/durability as the *tools* the application uses to preserve its own consistency invariants (via constraints, foreign keys, application logic run inside the transaction) — the DB alone can't know what "consistent" means for your specific business rules.

- **Isolation:** concurrently-running transactions don't see each other's partial, uncommitted effects — as if each transaction ran alone, one at a time, even though in reality many run concurrently for throughput. Without it: transaction A can observe transaction B's half-finished work — reading rows B is in the middle of updating, or worse, rows B updates and then aborts, which A never should have seen at all. Full isolation (serializability) is expensive to implement fully, which is precisely *why* real databases offer a menu of weaker isolation levels that sacrifice some of this guarantee for performance — the entire subject of 3.6, and the subject of the anomalies below.

- **Durability:** once a transaction commits, its data survives — even a full crash immediately after, even the exact machine it ran on failing to ever boot again. Without it: a transaction can be told "success" and then simply lose that data on a crash a moment later, which is worse than an honest failure, because the client already believes the operation succeeded. Mechanically, durability on a single node means the write is fsync'd to non-volatile storage (not sitting only in an OS page cache) before acknowledging commit; in a distributed/replicated setting, true durability additionally requires the data to have reached more than one physical machine (a single-node fsync doesn't protect against that one disk/machine dying), which is exactly why synchronous replication (3.2) exists as a durability mechanism, not merely a "freshness" one.

### Weak isolation anomalies — concrete failure scenarios, not abstractions

Real databases very rarely run at full serializable isolation by default (Postgres and MySQL both default to **read committed**, not serializable) because full isolation is expensive. That tradeoff is invisible until a specific interleaving of concurrent transactions produces a bug that's incredibly hard to reproduce or debug, because it depends on exact timing. These are the named anomalies to know cold:

- **Dirty reads:** transaction A reads data that transaction B has written but **not yet committed**. If B then aborts, A has now acted on data that officially never existed. Example: an order-processing job reads a row mid-update by another transaction that's about to roll back — the job now bases a decision on a value the database will shortly claim never happened.

- **Dirty writes:** transaction A overwrites data that transaction B has written but not yet committed, before B's transaction resolves. This can interleave two transactions' writes in an inconsistent hybrid way — e.g., two concurrent "assign this order to a driver" transactions, each updating both an `orders` row and a `drivers` row; without protection against dirty writes, the `orders` row could end up assigned to driver X while the `drivers` row shows driver Y as busy — a state neither transaction, run alone, would have produced.

- **Read skew (non-repeatable reads):** within a single transaction, two reads of the same or related data return inconsistent results because another transaction committed a change in between them. Classic example: a user checks their checking account balance ($500) and savings account balance ($500) in two separate reads inside one "view my accounts" transaction — but between the two reads, a *different*, fully committed transaction transfers $100 from checking to savings — the user now sees $400 in checking (post-transfer) and $500 in savings (pre-transfer read, before it arrived) — $900 total, $100 has apparently vanished, even though every individual transaction was itself correct.

- **Lost updates:** two transactions concurrently perform a read-modify-write on the same value, and one's write silently clobbers the other's, losing an update that should have counted. Classic example: two processes concurrently increment a page's view counter — both read the current value (say, 42), both independently compute 43, both write 43 — the counter is now 43 instead of the correct 44, and one increment simply vanished with no error raised anywhere.

- **Write skew:** two transactions each read some **overlapping** set of data, then each makes a decision based on what they read and writes to **disjoint** rows — and the combination of both writes violates an invariant that held before either transaction, even though neither transaction's write, alone, conflicts with the other on the same row (so naive same-row locking doesn't catch it). Kleppmann's canonical example: a hospital requires **at least one doctor on call** at all times. Two doctors, Alice and Bob, are both on call. Both simultaneously decide to go off call (each independently checks "is at least one other doctor still on call?", both see the other still listed as on call, both proceed to set their own `on_call = false`). Both transactions individually appear valid at the moment they check — but the end state has **zero** doctors on call, violating the invariant neither transaction's own logic would have permitted if it had known about the other's concurrent decision. This is the hardest anomaly to reason about and the hardest for a database to prevent automatically (see SSI in 3.6, which specifically targets this).

- **Phantoms:** a transaction's write affects the result of another transaction's *earlier* query predicate — even though no specific *row* the second transaction read was modified — because a new row now matches a `WHERE` condition that was evaluated before that row existed. This is exactly what breaks the doctors-on-call example at the SQL level: a query like `SELECT COUNT(*) FROM doctors WHERE on_call = true` doesn't lock any specific existing row, it locks nothing that would catch a row's on-call flag being flipped elsewhere concurrently — the "conflict" is on a search condition, not a row, which is why simple row-level locking is structurally unable to prevent it (this is exactly why databases add **predicate locks** / **index-range locks** specifically to close the phantom hole — see 3.6).

## 3.6 Isolation levels: read committed, snapshot isolation, serializable

Databases offer a menu of isolation levels, each closing off some subset of the anomalies above at increasing implementation cost. Knowing which level closes which hole — and which it deliberately leaves open — is the actual interview-relevant skill here, not just naming them.

### Read committed

The most common default (Postgres, Oracle, SQL Server all default here, or close to it). Two guarantees, both enforced at the row level: (1) you only ever read data that has been **committed** (no dirty reads), and (2) you only ever overwrite data that has been committed (no dirty writes — implemented with a plain row-level lock held until the writing transaction commits or aborts, blocking any other transaction from writing the same row in the meantime).

**What it does *not* prevent: read skew.** Nothing stops two separate reads inside one transaction from seeing two different, individually-committed snapshots of the world if a concurrent transaction commits in between them — the checking/savings account example above happens *specifically* under read committed. This is a well-understood, accepted gap in practice — read committed is popular precisely because it's cheap (short-lived row locks, no long-held read locks blocking writers) and the read-skew scenario, while real, is rare enough in typical workloads that most teams accept the risk rather than pay for stronger isolation everywhere.

### Snapshot isolation via MVCC

**Snapshot isolation:** each transaction reads from a **consistent snapshot** of the entire database as of the moment the transaction started — regardless of what other transactions commit while it's running, it keeps seeing the world exactly as it looked at transaction start. This closes read skew entirely — the checking/savings example is now impossible, because both reads see the pre-transfer snapshot consistently.

**How it's actually implemented — MVCC (multi-version concurrency control):** rather than storing one current value per row, the database keeps **multiple historical versions** of each row, each version tagged with the transaction ID (or a monotonic sequence number) that created it. A read doesn't fetch "the current row" — it fetches the version that was current as of its own snapshot's starting point, filtering out any version created by a transaction that committed after the reader's snapshot began. Old versions eventually get garbage-collected (Postgres calls this **vacuum** — a direct link to Phase 2's disk-fragmentation topic: this is literally why databases need periodic compaction, MVCC's old-version buildup is one of the main sources of it) once no active transaction could possibly still need to read them.

**The killer property this buys: readers never block writers, and writers never block readers.** A long-running read transaction just keeps reading its own frozen snapshot's old row versions while writers create newer versions elsewhere — there's no lock contention between reads and writes at all, unlike read committed's dirty-write-prevention locks or full 2PL. This is why snapshot isolation is popular for read-heavy analytical queries running alongside live writes — Postgres calls its snapshot-isolation-adjacent level `REPEATABLE READ`, and it's the mechanism behind MySQL/InnoDB's `REPEATABLE READ` default too.

**What it still doesn't prevent: write skew (and therefore phantoms).** Snapshot isolation guarantees consistent *reads*, but two transactions can still each read the same consistent snapshot, each make a decision based on it, and each write to different rows in a way that violates an invariant across both writes combined — the doctors-on-call scenario happens under snapshot isolation exactly as it does under read committed, because neither transaction's write physically conflicts with the other's at the row level.

### Serializable isolation

The strongest level: the *result* of running transactions concurrently is guaranteed to be identical to *some* possible serial (one-at-a-time) ordering of those same transactions — even though they may have actually executed concurrently for performance. Three real, structurally different mechanisms achieve this:

**1. Actual serial execution.** Just... run transactions one at a time, on a single thread, no concurrency at all. Sounds primitive, but it became practical once RAM got large enough to hold entire working datasets (eliminating disk I/O wait, historically the reason concurrency was needed to keep a CPU busy at all) — if a transaction never blocks on disk, a single thread can push through an enormous number of short transactions per second with zero locking overhead and zero possibility of any concurrency anomaly, by construction. **VoltDB** and **Redis** (for its scripting/multi-command execution) are built around this model. The catch: it only works if transactions are short and don't do slow external things mid-transaction (a network call to another service inside a transaction would stall the *entire* database, since there's only one thread) — so this model pushes hard toward small, fast, stored-procedure-style transactions rather than arbitrary interactive multi-step client transactions.

**2. Two-phase locking (2PL) — pessimistic, lock-based.** Every reader takes a **shared lock** and every writer takes an **exclusive lock** on the rows/ranges it touches; shared locks can coexist with other shared locks but not with an exclusive lock, and exclusive locks block everything else. "Two-phase" refers to the lock lifecycle: a growing phase where locks are acquired, and a shrinking phase where locks are released — critically, **all locks are held until the transaction commits or aborts**, not released early as soon as a particular row is done being used (that's what distinguishes it from weaker locking schemes and is exactly what makes it serializable rather than just "read committed with extra steps"). To close the phantom hole specifically, 2PL implementations add **predicate locks** or, more practically, **index-range locks** (approximate predicate locks attached to index ranges) so that a `WHERE on_call = true` query locks the *range/condition*, not just rows that existed at query time — meaning a concurrent insert or update matching that condition is blocked too. **Why it kills performance:** long-held locks mean high contention under concurrent load — transactions queue up waiting for locks other transactions are sitting on, throughput craters under contention, and it's also prone to **deadlock** (transaction A waits on a lock B holds while B waits on a lock A holds), requiring a deadlock detector that periodically picks a victim transaction to abort and retry.

**3. Serializable snapshot isolation (SSI) — optimistic.** Start from ordinary snapshot isolation (cheap, non-blocking reads via MVCC as described above), but additionally **track dependencies between concurrent transactions** and, at commit time, detect whether any pattern of reads/writes occurred that *could* have caused a serializability violation (specifically: did a transaction read data that was later modified by a transaction that committed concurrently, in a pattern indicating a genuine conflict). If such a pattern is detected, **abort one of the transactions** and let the application retry it. This is optimistic in the literal sense — assume conflicts are rare, let transactions run without blocking, and only pay a cost (an abort + retry) on the rare occasions a real conflict actually occurred — versus 2PL's pessimistic stance of blocking upfront on every potential conflict whether or not one would have actually materialized. This is exactly the mechanism behind **Postgres's `SERIALIZABLE`** isolation level (added in 9.1), and it's why Postgres's serializable mode is dramatically less painful in practice than a naive lock-based serializable implementation would be — you get full serializability with close-to-snapshot-isolation performance under low-to-moderate contention, at the cost of applications needing to handle occasional transaction retries.

| Isolation level | Dirty read/write | Read skew | Lost update | Write skew / phantoms | Mechanism |
|---|---|---|---|---|---|
| Read committed | Prevented | **Possible** | Possible | Possible | Row-level locks on writes, always read latest committed |
| Snapshot isolation | Prevented | Prevented | Prevented (with care) | **Possible** | MVCC, consistent per-transaction snapshot |
| Serializable | Prevented | Prevented | Prevented | Prevented | Actual serial execution / 2PL / SSI |

## 3.7 The trouble with distributed systems: clock drift, network faults, partial failures

Everything so far assumed replicas eventually agree, leaders eventually get detected as dead, and clocks roughly make sense. This section is about *why none of those assumptions are safe defaults* — the physical and logical reasons distributed systems are fundamentally harder than single-machine ones, independent of how well the code is written.

### The network must be assumed asynchronous

A single-machine program has predictable timing: a function call returns, or the process crashes and that's observable. A network call has **no such bound**. A request can be delayed by an arbitrarily long, unpredictable amount — queued behind other traffic, retried by an intermediate router, stuck behind a congested link — and there is **no upper limit** you can safely assume in a general internet/datacenter network (this is the formal "asynchronous network model," as opposed to a "synchronous network model" with guaranteed bounded delay, which real networks do not provide even though they usually behave well most of the time). This single fact is why timeouts are always a guess, never a proof: a timeout firing tells you "I didn't hear back within X," and nothing more.

### A crash and a network partition are indistinguishable to the observer

This is the single most important sentence in this section: **if node A sends a request to node B and gets no response, A cannot tell whether B crashed, B is just slow, the request never arrived, or the response was sent but never arrived.** All four look identical from A's side — silence. Every piece of failure-detection logic in every distributed system (leader election, health checks, timeouts) is fundamentally just **guessing based on silence**, and any protocol that assumes it can perfectly distinguish "dead" from "slow" is quietly relying on an assumption the network doesn't actually provide. This is exactly why leader failover (3.1) is dangerous — promoting a new leader because the old one "seems dead" can be wrong, and if the old leader wasn't actually dead, you now have two.

### Clock drift — why wall-clock time can't be trusted for ordering

Every machine has a **quartz clock** that drifts (typically tens of milliseconds of drift per day if left uncorrected — a large amount in database-timing terms), corrected periodically by **NTP (Network Time Protocol)** syncing against reference time servers. But NTP sync itself is imperfect: it's just another network request with variable latency, sync happens periodically (not continuously) so drift reaccumulates between syncs, and if NTP sync is misconfigured or a firewall blocks it, a machine's clock can silently drift by seconds or more without anyone noticing. **Leap seconds** are a sharper, well-documented failure case: an extra second occasionally inserted into UTC to keep it aligned with Earth's actual rotation — several major outages (a well-known 2012 incident affected multiple large sites simultaneously) trace directly to leap-second handling bugs, because "23:59:60" isn't a value most time-handling code was ever written to expect.

**The concrete consequence:** you cannot safely use wall-clock timestamps (`System.currentTimeMillis()`-style) to determine "which of these two writes, from two different machines, happened first" — clock skew between the two machines can easily exceed the actual real-world gap between the two events, silently reordering them. This directly undermines naive **last-write-wins** conflict resolution (3.12), which relies on exactly this comparison — two concurrent writes on two machines with even a few hundred milliseconds of clock skew between them can have their "winner" decided by clock error rather than by which write genuinely happened later.

**The alternative: logical clocks, which capture order without capturing real time at all.**
- **Lamport timestamps:** each node keeps a simple counter, incremented on every local event, and every message carries the sender's counter value; a receiver sets its own counter to `max(local counter, received counter) + 1`. This guarantees that if event A **causally** influenced event B (A happened, then a message about it was sent and received, then B happened), A's Lamport timestamp is guaranteed to be less than B's — giving a total order consistent with causality, without ever touching a physical clock. The limitation: Lamport timestamps give you *a* valid total order, but they **cannot tell you whether two events are causally related or merely concurrent** — you can compare any two timestamps and get an answer, but that answer doesn't distinguish "A definitely happened before B" from "A and B were actually unrelated and just got arbitrarily ordered."
- **Vector clocks:** fix exactly that gap. Each node maintains a **vector** of counters, one slot per node in the system, incremented in its own slot on each local event and merged (element-wise max) with a received vector on message receipt. Comparing two vector clocks now tells you one of three things, unambiguously: A happened-before B, B happened-before A, or **A and B are concurrent** (neither vector dominates the other) — this third case is exactly the information Lamport timestamps threw away, and it's precisely what's needed to correctly detect genuinely concurrent, conflicting writes in a leaderless system (Dynamo/Riak use vector clocks internally for exactly this reason — to know when two writes actually conflict versus when one simply descended from the other).

### Process pauses breaking "if I hold a lock, I'm still allowed to act on it"

A common (and dangerously intuitive) design pattern: a node acquires a lock or lease (e.g., "I am the leader, valid until time T, as granted by a coordination service"), and assumes that as long as it internally believes it still holds that lock, it's safe to act as the exclusive owner of whatever the lock protects. The hidden assumption this breaks: **the node might not actually be running continuously the whole time it thinks it is.** A **garbage collection pause** (a stop-the-world GC pause in a JVM can genuinely run into multiple seconds under memory pressure), an OS thread being descheduled, or a **VM being suspended/migrated by its hypervisor** (common in virtualized/cloud environments — the VM can be paused for a noticeable duration by infrastructure the application has zero visibility into) can all freeze a process for long enough that its lock lease **expires while the process is paused**, without the process itself observing any elapsed time at all from its own perspective — it resumes, execution continues from exactly where it left off, and it has no way to know significant wall-clock time passed. It then proceeds to act as leader, still fully believing its lease is valid, when the coordination service has already reassigned that lock to someone else.

**The fix: fencing tokens.** Every time a lock/lease is granted, the coordination service hands out a **monotonically increasing token** along with it (e.g., 33, then 34, then 35, one higher each time the lock changes hands). The client includes this token with every subsequent write to the protected resource, and **the resource itself (not the lock holder) is responsible for rejecting any write carrying a token lower than the highest one it has already seen.** Now, even if a paused node wakes up and, still believing it's the leader, sends a write with stale token 33 — after the lock has since been reassigned and a newer client has already written with token 34 — the resource simply rejects the stale write, because it has already seen a higher token. This moves the safety check to the one place that can actually enforce it correctly: not "trust the client's belief about whether it still holds the lock," but "have the resource itself verify the token on every single write, unconditionally."

## 3.8 Consistency models: linearizability, causal consistency, eventual consistency

Given all of the above — asynchronous networks, unreliable failure detection, clocks you can't trust — what can a distributed system actually *promise* about how fresh or ordered the data a client sees will be? These promises are called **consistency models**, and they form a spectrum from strongest/most expensive to weakest/cheapest.

### Linearizability

**The precise definition:** the system behaves as if there were only **a single copy of the data**, and every operation appears to take effect **atomically at some single, real-time point between when it was invoked and when it returned** — and critically, that single global ordering must be consistent with real, observed time: if operation B started after operation A had already completed (in real wall-clock terms, as observed by any client), then B must see the effects of A. This is a much stronger and more precise guarantee than "eventually consistent" or even "usually looks right" — it means there's no window, however brief, where a client can observe stale data once *any* client has observed the new value.

**Why it's expensive:** achieving linearizability essentially requires **consensus** (3.10) — every write needs to be agreed upon, in a single global order, by a mechanism that a majority of nodes participate in, before it can be considered "done" from any observer's perspective. This inherently costs a network round trip (at minimum) for coordination on every operation, and — per the CAP theorem (3.9) — a linearizable system **cannot remain available during a network partition**, because honoring a read during a partition risks returning stale data relative to a write that landed on the other side of the split, which linearizability strictly forbids. Systems that offer it (ZooKeeper, etcd, and any system built directly on Raft/Paxos consensus) pay real latency for it and are explicitly built for correctness-critical *coordination metadata* (locks, leader election, config), not for high-throughput bulk data — this is exactly why ZooKeeper/etcd show up as *coordination services* (3.4) rather than as general-purpose application databases.

### Causal consistency

A meaningfully weaker, much cheaper guarantee: operations that are **causally related** (one happened-before the other — e.g., a reply to a comment, or a write that was based on reading an earlier value) must be seen by every observer in that same relative order, but operations that are **not** causally related (truly concurrent, independent writes) can be observed in *any* order by different clients without violating the guarantee. This directly maps back to the consistent-prefix-reads problem in 3.2 — causal consistency is precisely the formal guarantee that prevents "the answer appears before the question." Crucially, causal consistency **does not require global consensus** to implement — you only need to track and respect the specific "happens-before" relationships that actually exist (using something like vector clocks from 3.7, or simplified version-tracking), not agree on one single global total order for every unrelated operation in the system — which is exactly why it's achievable without paying consensus's full cost, and is considered the strongest consistency model that remains achievable while still staying available during a network partition.

### Eventual consistency

The weakest useful guarantee, and the default for leaderless/Dynamo-style systems (3.1) run without extra coordination: **no ordering guarantee whatsoever** between concurrent operations — the only promise is that **if writes stop, all replicas will eventually converge to the same value.** "Eventually" is deliberately unbounded — could be milliseconds under normal conditions, could be much longer under network trouble — and in the meantime, different clients reading different replicas can see arbitrarily different, arbitrarily stale answers, including answers that arrive out of causal order. This is the tradeoff Dynamo-style systems make deliberately in exchange for always remaining available for both reads and writes, even during a partition — it's a legitimate, common engineering choice (shopping carts, social media like-counts, DNS itself), not a "lesser" system, provided the application is built with the awareness that staleness and out-of-order effects are possible and are handled (or are genuinely tolerable) at the application level.

| Model | Ordering guarantee | Needs consensus? | Available during partition? |
|---|---|---|---|
| Linearizability | Single global real-time order | Yes | No |
| Causal consistency | Preserves happens-before order only | No | Yes |
| Eventual consistency | None (just eventual convergence) | No | Yes |

## 3.9 CAP theorem — properly, not the oversimplified version

The pop-science version — "a distributed system can only have two of Consistency, Availability, and Partition tolerance, pick two" — is close enough to be dangerous, because it implies partition tolerance is an optional design choice on the same footing as the other two. It isn't, and the actual theorem is narrower and more useful than the slogan suggests.

**What CAP actually claims:** in any distributed system, **during an actual network partition** (some nodes genuinely cannot communicate with other nodes), you must choose between:
- **Consistency** (in CAP's specific sense — closer to linearizability than to ACID's "C"): every read reflects the latest write, which means a node cut off from the rest of the cluster by the partition must **refuse to serve reads or writes** it can't guarantee are up to date, or
- **Availability:** every request gets a non-error response, which means a partitioned node **keeps serving requests using only the data it locally has**, even though it cannot guarantee that data is current relative to what the other side of the partition might have written.

**Outside of an active partition — i.e., the network is behaving normally — you can have both consistency and availability simultaneously**; there is no tradeoff to make in the common case. CAP is exclusively a statement about **what a system is forced to sacrifice during the (hopefully rare, hopefully brief) windows when the network is actually broken.**

**Why "partition tolerance isn't really optional" is the key correction to the pop-science version:** in any real distributed system spanning more than one machine, network partitions **will** happen eventually — a switch fails, a cable gets cut, a datacenter loses connectivity — this isn't a choice you opt into or out of, it's a physical reality of operating multiple machines connected by an imperfect network. So framing it as "pick 2 of C/A/P" as if P were a toggle you could simply leave off is misleading — you don't get to choose whether partitions occur, only how your system behaves **when** one does. The real, unavoidable choice CAP describes is just **CP vs AP**: when a partition happens, does this system favor consistency (some nodes go unavailable/return errors) or availability (all nodes keep answering, accepting possible staleness)? Single-leader systems that refuse writes when the leader is unreachable are choosing CP in that moment; Dynamo-style leaderless systems with sloppy quorums, by design, choose AP.

### PACELC — the more useful, complete extension

CAP only describes behavior **during a partition (P)**, and says nothing about the overwhelmingly common case where the network is fine — but there's *still* a real tradeoff even then, and PACELC (Abadi, 2012) names it explicitly: **if Partitioned, choose between Availability and Consistency; Else (normal operation, no partition), choose between Latency and Consistency.** Even with a perfectly healthy network, a system that wants strong consistency (e.g., wait for a synchronous quorum/majority acknowledgment on every write, or route every read through a single leader to guarantee freshness) inherently pays higher latency than a system willing to read from the nearest replica and risk some staleness. This is exactly the sync-vs-async replication tradeoff from 3.2, restated as a formal consistency model — PACELC is the more complete, more practically useful framework precisely because it acknowledges that the interesting tradeoff for most systems, most of the time, isn't the rare partition scenario CAP describes — it's this everyday latency-vs-consistency dial that's live on every single request, partition or not. In interviews, naming PACELC after CAP is a strong signal you understand the tradeoff isn't just a partition-day emergency question.

## 3.10 Consensus algorithms: Paxos, Raft — what problem they actually solve

**The problem consensus solves, precisely:** get multiple nodes to **agree on a single value**, once, durably, such that the agreed value cannot later be changed or disagreed upon — **despite** some nodes crashing, messages being delayed or lost, and no reliable way to distinguish a crashed node from a slow one (per 3.7). This sounds narrow, but it's the underlying primitive beneath a surprising amount of what's covered elsewhere in this file: **leader election** (getting a cluster to agree on "who is the one true leader" is itself an instance of consensus — agreeing on a single value, where the value happens to be a node identity), **atomic commit** across a distributed transaction (agreeing on "commit" vs "abort" as the one true outcome — see 3.11), and **linearizable operations** in general (every linearizable write needs the cluster to agree on where in the total order it lands). Any system that offers strong, coordinated guarantees is, underneath, running a consensus protocol somewhere.

### Raft — the more commonly implemented one today, explained at a mechanical level

Raft (Ongaro & Ousterhout, explicitly designed with **understandability** as a first-class design goal, in contrast to Paxos below) organizes cluster time into a sequence of **terms**, each term having at most one leader. Two coupled mechanisms:

**Leader election.** Every node is in one of three states: follower, candidate, or leader. Followers expect periodic **heartbeats** from the current leader; if a follower doesn't hear one within a **randomized election timeout**, it assumes the leader is gone, increments the term number, transitions to candidate, and requests votes from every other node. Each node votes for at most one candidate per term (first valid request it sees), and a candidate that receives votes from a **majority** of nodes becomes the new leader for that term and starts sending heartbeats itself. **Why the timeout is randomized, specifically:** if every follower used the identical fixed timeout, they'd all become candidates simultaneously the instant a leader disappeared, split the vote evenly among themselves, fail to reach a majority, and have to retry — repeatedly, potentially indefinitely under bad luck. Randomizing each node's timeout independently means one node's timer fires meaningfully earlier than the others almost every time, so it becomes a candidate and gathers votes before others even wake up to contest it — this small randomization is the entire mechanism that makes elections converge quickly and reliably in practice.

**Log replication.** Once elected, the leader is the only node that accepts client writes. Each write is appended to the leader's local log as an entry (tagged with the current term and a log index), and the leader sends that entry to all followers in parallel via the same heartbeat/AppendEntries mechanism. **An entry is only considered "committed" once a majority of nodes (leader included) have durably appended it to their own local log** — only then does the leader apply it to the actual state machine and respond to the client as successful, and only then does it inform followers they may also apply it. This majority requirement is exactly what survives crashes safely: if the leader dies right after committing (majority-replicated) but before every follower got the memo, the new leader — guaranteed by the election rule to be a node that itself has every committed entry, since it needed votes from a majority and committed entries exist on a majority — still has the full committed history and simply continues from there. Entries the old leader hadn't yet gotten to a majority are safely discarded/overwritten, since no client could ever have been told they succeeded.

**Real systems built directly on Raft:** **etcd** (Kubernetes's cluster state store runs on it), **Consul** (HashiCorp's service-discovery/coordination tool), **CockroachDB** and **TiDB** (per-range/shard consensus in distributed SQL databases).

### Paxos — why it's notoriously harder

Paxos (Lamport, originally published in a famously obscure, allegory-heavy 1998 paper) solves the *identical* fundamental problem — get a majority of nodes to agree on one value despite failures — and is provably equivalent in what it guarantees, but has a long-standing reputation (acknowledged by Lamport himself in a later, more plainly written paper) for being exceptionally difficult to fully understand and, more importantly, difficult to correctly **implement** from the core algorithm alone. The core "single-decree Paxos" protocol only specifies how to agree on **one single value** — real systems need a continuous *sequence* of agreed values (a replicated log, exactly like Raft's), which requires layering **Multi-Paxos** on top, and the original papers leave significant engineering gaps in how to do that efficiently and correctly (leader election/leasing, log compaction, reconfiguration) — famously described in Google's own "Paxos Made Live" paper as requiring substantial, non-obvious engineering beyond the algorithm itself to get a real system working correctly. Raft's explicit, stated design goal was to be **just as provably correct as Paxos while being dramatically easier to teach, reason about, and implement correctly** — it does this by, among other things, restricting leader election to a stronger constraint (only a node with an up-to-date log can become leader at all, simplifying a lot of edge-case reasoning Paxos leaves more open-ended) and by presenting log replication as one unified, concrete mechanism rather than a generic value-agreement primitive that has to be extended into a log separately. This understandability gap is *the* reason Raft, not Paxos, is what you'll find underneath most consensus-dependent systems built in the last decade (etcd, Consul, CockroachDB) even though Paxos (and variants like Google's Chubby lock service, which predates Raft) proved the ideas first and remains used in some older or Google-internal systems (Chubby, Spanner's underlying replication).

## 3.11 Distributed transactions: 2PC, and why it's avoided at scale

Everything in 3.5/3.6 covered transactions **within one database node**. What about a transaction that must atomically span **multiple** independent nodes — e.g., debit an account in database A and credit one in database B, where both must succeed or both must fail, with no in-between state ever visible? **Two-phase commit (2PC)** is the classical protocol for this.

### 2PC mechanics

A **coordinator** node orchestrates the transaction across all **participant** nodes, in two strict phases:

**Phase 1 — Prepare:** the coordinator sends a "prepare" request to every participant, asking, in effect, "can you guarantee you're able to commit this?" Each participant does everything short of actually committing — it acquires whatever locks are needed, writes its intended changes durably (so it could survive a crash and still honor the eventual decision), and replies **"yes, I'm prepared"** or **"no, abort."** Critically, once a participant votes "yes," it has made an **irrevocable promise** — it must hold those locks and must be able to commit if told to, no matter what happens next, even if it doesn't hear back from the coordinator for a long time.

**Phase 2 — Commit (or abort):** if **every** participant voted yes, the coordinator durably records the decision "commit" and sends a "commit" message to every participant, who then actually apply their changes and release their locks. If **any** participant voted no (or didn't respond within a timeout), the coordinator instead sends "abort" to everyone, and all participants roll back and release locks. The transaction is only considered truly complete once every participant has acknowledged this second-phase message.

### Why it's a blocking protocol — the specific failure that makes it dangerous

Consider the exact moment after every participant has voted "yes" (all locks held, all durably prepared) but **before** the coordinator's phase-2 decision message reaches them — and the coordinator crashes right there. **Every participant is now stuck**: it can't unilaterally commit (it doesn't know if some *other* participant voted no, in which case committing would be wrong), and it can't unilaterally abort (it doesn't know if the coordinator had already decided to commit and other participants might already be committing, in which case aborting would be wrong too). Each participant is contractually bound by its own "yes" vote to just **wait**, holding every lock it acquired, until the coordinator recovers and tells it what actually happened — and if the coordinator's crash is prolonged (or its own durable decision log is lost), that wait has **no upper bound**. Every row those locks touch is now unavailable to any other transaction, for however long the coordinator stays down. This is a fundamentally different failure mode than a single-node transaction ever has, precisely *because* it depends on one coordinator's durability and liveness that the rest of the system has no way to substitute for.

### Why this pushes large-scale systems away from distributed transactions entirely

This blocking failure mode is the concrete, mechanical reason — not a vague "distributed transactions are hard" hand-wave — that most large-scale systems structurally avoid 2PC-style distributed transactions, in favor of one of two alternatives:

- **Eventual consistency + compensating actions (the saga pattern):** break the multi-step operation into a sequence of local transactions, each committing independently and immediately (no cross-node locks held open at all), and if a later step fails, execute explicit **compensating transactions** that semantically undo the effects of the earlier, already-committed steps (e.g., "issue a refund" rather than "roll back the original charge," because the original charge already fully committed and released its locks long ago). This trades away atomicity's clean guarantee for availability and the complete elimination of cross-node blocking — at the real cost of needing to design and correctly implement a compensating action for every step, and accepting that intermediate, partially-applied states are genuinely, briefly visible to the rest of the system (unlike true ACID atomicity, where they never are).
- **Avoiding cross-partition transactions altogether**, by designing the data model so that anything requiring transactional atomicity lives within a single partition/shard in the first place (e.g., co-locating a user's orders and that user's account balance on the same shard, keyed by user ID) — sidestepping the entire problem at the schema/sharding-design level rather than solving it at the protocol level. This is frequently the pragmatic real-world answer: design around needing distributed transactions rather than paying their cost.

(Some modern distributed databases — Google Spanner chief among them — do offer genuine distributed transactions at scale, but only by pairing 2PC-like commit coordination with extremely tightly synchronized clocks — Spanner's TrueTime API, backed by atomic clocks and GPS receivers in every datacenter, bounding clock uncertainty tightly enough to make global ordering decisions safe. This is a notable, expensive exception that proves the rule rather than a counterexample to it — it's precisely the kind of purpose-built infrastructure investment most companies don't have and design around instead.)

## 3.12 Multi-leader conflict resolution: last-write-wins, timestamp-based, custom merge logic

Multi-leader (3.1) and leaderless (3.1) replication both accept the possibility of **concurrent, conflicting writes** to the same piece of data — two updates, made independently on different nodes, neither aware of the other at the time it was made. Something has to decide what the data looks like once both writes have propagated everywhere. Three real strategies, in increasing order of correctness and implementation effort:

### Last-write-wins (LWW)

The simplest possible resolution: attach a timestamp to every write, and when two conflicting versions of the same key are found, **keep whichever has the later timestamp and silently discard the other.** This requires no coordination, no merge logic, and always produces a deterministic single answer, which is exactly why it's the easiest thing to reach for and remains a common default (Cassandra offers it as a built-in option, for instance).

**The real danger, stated concretely:** LWW causes **silent data loss** — and the word "silent" is the important part. Both writes were, individually, entirely valid and neither client was ever told anything failed; one just vanishes without any error, retry signal, or conflict notification anywhere. Worse, per 3.7, if the timestamps being compared come from unsynchronized or drifting wall clocks on different machines, "later timestamp" doesn't even reliably mean "actually happened later in real time" — a write that objectively happened second, in real causal terms, can still lose to a write that happened first, purely because its originating machine's clock was running fast. This makes LWW a genuinely risky default for anything where losing a write silently is unacceptable (financial data, inventory counts) and a reasonable choice mainly for genuinely low-stakes, high-volume data (ephemeral cache entries, presence/last-seen timestamps) where losing an occasional update truly doesn't matter.

### Timestamp/version-based detection of concurrency (not just resolution)

A meaningfully better approach separates two questions LWW conflates: **"were these writes actually concurrent?"** versus **"which one should win?"** Using version vectors (the multi-key generalization of the vector clocks from 3.7 — one counter per replica, tracked per key) lets the system determine, precisely and correctly, whether one write causally descended from the other (in which case there's no real conflict — just apply the newer one, no data loss, no ambiguity) or whether the two writes were **genuinely concurrent** (neither aware of the other), in which case there is a real, unavoidable conflict that needs an actual decision — not a coin-flip based on unreliable clocks. Riak (a direct Dynamo-lineage system) does exactly this: it uses version vectors to detect true concurrency, and when it finds a real conflict, it can be configured to **return both conflicting versions to the client** — often called a "sibling" in Riak's own terminology — rather than silently picking one, pushing the actual resolution decision to a layer that has the application-specific context to make it correctly.

### Application-level custom merge logic

The most correct, most work-intensive approach: write explicit, domain-specific logic that merges two conflicting versions into a single, semantically sensible result, rather than picking a winner and discarding the other. The canonical example, straight from Amazon's original Dynamo paper: a **shopping cart**. If a customer adds item A to their cart from their phone while offline, and separately adds item B from their laptop, both writes are individually valid, and picking one via LWW would mean the customer's cart silently loses whichever item lost the timestamp comparison — obviously wrong from a business standpoint. The correct merge is a **union of both item sets** — the reconciled cart contains both A and B, because that's what a reasonable person would expect their cart to actually contain, and the merge logic encodes that specific business meaning rather than treating the conflict as a generic "pick a version" problem the storage layer can solve blindly. This is strictly more work than either prior approach — it requires the application (not the database) to understand what "correctly combining two versions" means for that specific piece of data, and that logic is different for every data type (a cart merges as a union; a document merges very differently; a boolean flag might not have a sensible merge at all and may genuinely need to surface as a conflict for a human to resolve) — but it's the only approach of the three that can guarantee **zero silent data loss** while still allowing writes to succeed everywhere, all the time, which is the entire reason multi-leader/leaderless replication was chosen in the first place.

| Strategy | Silent data loss? | Coordination needed | Cost |
|---|---|---|---|
| Last-write-wins | Yes, real risk | None | Lowest |
| Version-vector detection + surface conflicts | No (conflicts surfaced, not hidden) | Track per-key version vectors | Medium |
| Custom application merge logic | No | Domain-specific merge function per data type | Highest |

## Comprehension checks

**1.** You're designing a ride-sharing backend. The "driver's current location" data is updated every few seconds per driver and read constantly by the matching service; occasionally showing a location that's a couple seconds stale is harmless. Separately, the "ride fare charged to a rider's card" data must never silently lose a write or show two different, non-converging values to two different services. Which replication/consistency approach fits each, and why would using the same approach for both be a mistake?

<details>
<summary>Expand</summary>

- **Driver location:** a good fit for leaderless/Dynamo-style replication with a low `W` and low `R` (or even eventual consistency with no strict quorum) — writes need to be fast and always-available (a driver's phone has flaky connectivity), and a few seconds of staleness on a location is genuinely tolerable given locations are already stale-by-nature (drivers keep moving). Optimizing for write availability and low latency over strict freshness is exactly the right tradeoff here — this is PACELC's "Else" branch: no partition needed to justify favoring latency over consistency, it's just the right default for this data.
- **Fare charged:** needs strong consistency — this is exactly the kind of data where a lost or ambiguous write is unacceptable. This calls for single-leader replication (so there's one unambiguous order of truth) with synchronous or semi-synchronous replication for durability (3.2), and ideally the fare-charge operation lives entirely within one partition/shard (keyed by ride ID or rider account) specifically so it never needs a distributed transaction (3.11) — sidestepping 2PC's blocking-failure risk by design rather than by accident.
- **Why using the same approach for both is a mistake:** applying leaderless/eventual consistency to the fare data risks exactly the silent-data-loss and conflicting-write problems described in 3.12 — unacceptable for money. Applying strict single-leader synchronous replication to the location data would tank write throughput and availability (every driver's phone would need a leader round trip every few seconds, and a leader hiccup would stall all location updates) for a freshness guarantee the use case doesn't actually need. The lesson: consistency requirements are a per-data-type decision, not a single global architectural choice for the whole system.

</details>

**2.** A teammate proposes: "Let's just wrap the whole checkout flow — reserve inventory, charge the card, create the order record — in a single two-phase-commit transaction across our inventory service's database, our payments service's database, and our orders service's database. That way it's all atomic and we never have an inconsistent state." What's the concrete operational risk with this design, and what would you propose instead?

<details>
<summary>Expand</summary>

- **The concrete risk:** 2PC requires every participant to hold locks from the moment it votes "prepared" until the coordinator's final commit/abort decision arrives (3.11). If the coordinator (or the network to it) fails in that window — which will happen eventually at scale, per 3.7's "partitions and crashes are not optional, they're a certainty over enough time" — every participant is stuck blocking indefinitely, holding locks on live inventory rows, payment records, and order rows, potentially taking down checkout capacity for any other request touching that same locked data, for however long it takes to notice and manually recover the coordinator. This isn't a rare edge case to shrug off; it's the specific, well-documented failure mode that makes 2PC operationally risky at any real scale/traffic level.
- **What to propose instead:** a saga — break checkout into independent local transactions per service (reserve inventory and commit immediately; charge the card and commit immediately; create the order and commit immediately), each of which never holds a cross-service lock. If a later step fails (e.g., the card charge fails after inventory was already reserved), run an explicit compensating action (release the inventory reservation) rather than relying on a still-open distributed transaction to roll everything back atomically. This accepts that a brief, real intermediate state (inventory reserved, payment not yet charged) is visible to the rest of the system, in exchange for never having any node blocked indefinitely waiting on a possibly-dead coordinator.

</details>
