# Phase 5 — Core Building Blocks

This is the phase DDIA doesn't cover but every "design X" interview leans on constantly. Load balancers, caches, CDNs, rate limiters, object storage, consistent hashing — these are the Lego bricks every high-level design snaps together from. If Phase 1–4 is "how does data move and get stored correctly," Phase 5 is "what pieces do I actually draw on the whiteboard." Depth here matters just as much as the foundational phases — a candidate who says "we'll add a cache" without knowing which write policy or why it can silently lose data is not passing a Microsoft-level loop.

## 5.1 Load balancers

A load balancer sits between clients and a fleet of backend servers, distributing incoming traffic so no single server is overwhelmed, and so the fleet can grow/shrink without clients caring which specific machine answers them. The two big questions for any LB are (1) *which layer does it operate at* and (2) *which algorithm does it use to pick a backend*.

**L4 (transport layer) load balancing:** operates on IP address and TCP/UDP port only. It doesn't parse HTTP, doesn't know about URLs, headers, or cookies — it just sees packets and forwards them to a backend based on connection-level information (source IP, source port, destination IP, destination port). Because it does essentially no inspection, it's very fast and can handle enormous throughput with minimal CPU — some L4 balancers operate near line-rate, just rewriting packet headers (NAT) or even routing packets without touching the payload at all (direct server return). The tradeoff is that it's "dumb" about content: it cannot route `/api/users` differently from `/api/orders`, and it cannot make decisions based on what's inside the request. AWS Network Load Balancer (NLB) is the canonical modern example.

**L7 (application layer) load balancing:** terminates the connection, actually parses the HTTP request (or gRPC, WebSocket, etc.), and can route based on anything in it — URL path, HTTP method, headers, cookies, even body content. This is what enables **path-based routing** (`/api/v1/users` → the users microservice, `/api/v1/orders` → the orders microservice, all behind one hostname), **A/B testing / canary releases** (route 5% of traffic with a specific cookie or header to a new version), and **content-based routing** in general. The cost is CPU: terminating TLS, parsing HTTP, and inspecting content is meaningfully more expensive per request than L4's header-only forwarding. AWS Application Load Balancer (ALB), NGINX, Envoy, and HAProxy (in L7 mode) are the standard examples.

**Interview rule of thumb:** if you just need "spread TCP connections across N backends as fast as possible with no smarts," L4. If you need "route this request to a specific service based on what it's asking for," L7. Real production stacks frequently use *both* — an L4 balancer (or anycast + L4) at the very edge absorbing raw connection volume and DDoS pressure, handing off to L7 balancers that do the smart routing to microservices.

### Load balancing algorithms

| Algorithm | Mechanics | When you'd pick it |
|---|---|---|
| **Round robin** | Requests distributed to backends in strict rotating order (1, 2, 3, 1, 2, 3, …) | Backends are roughly identical in capacity and requests are roughly uniform in cost — simplest possible fair distribution |
| **Weighted round robin** | Same rotation, but backends with more weight get proportionally more requests (e.g., a beefier server gets weight 3 vs a smaller one's weight 1) | Fleet has heterogeneous hardware (mid-migration to bigger instance types, or intentionally mixed capacity) |
| **Least connections** | Route to whichever backend currently has the fewest active/open connections | Request cost varies a lot (some requests are long-lived or expensive) — round robin would blindly send more work to an already-loaded server just because it's "its turn" |
| **Least response time** | Route to the backend with the best combination of active connections and observed recent response latency | You want to actively route away from a backend that's technically accepting connections but is slow (e.g., mid-GC pause, thermal throttling) — a more responsive variant of least-connections |
| **IP hash** | Hash the client's source IP (sometimes combined with destination) to deterministically pick a backend | You need same-client-to-same-backend affinity without cookies (e.g., stateful protocols, or a cheap way to get sticky sessions) |
| **Weighted (general)** | Any of the above algorithms, but biased by a per-backend weight | Same rationale as weighted round robin, applied to a smarter base algorithm |
| **Geographic / geo-based** | Route based on the client's geographic location (often combined with GeoDNS/anycast) to the nearest datacenter/region | Global user base where latency matters — you want a user in Singapore hitting a Singapore or Southeast-Asia region, not us-east-1 |
| **Consistent hashing** | Both backends and requests (via some key — user ID, cache key) are hashed onto a ring; a request routes to the backend owning its position on the ring (see 5.11) | You need requests for the *same logical key* to consistently land on the same backend — critical for LBs in front of stateful caches/shards, where you want cache locality and minimal remapping when the backend fleet resizes |

**Health checks — why the LB needs to know if a backend is actually alive:**

- **Active health checks:** the load balancer itself periodically pings each backend on a dedicated health endpoint (e.g., `GET /healthz` every 5 seconds) independent of real traffic. If a backend fails N consecutive checks, it's pulled out of rotation; if it later passes M consecutive checks, it's added back. This catches a dead/hung backend even if it happens to be receiving zero real traffic at the moment.
- **Passive health checks:** the load balancer watches real traffic outcomes — a spike in 5xx responses or connection timeouts from a specific backend — and reacts by reducing or stopping traffic to it, without a separate dedicated probe. Cheaper (no extra traffic generated) but slower to detect a backend that's dead-but-not-yet-tried.

Production systems typically run both: active checks catch failures fast and proactively, passive checks catch failure modes that only manifest under real request patterns (e.g., a backend that's fine for health checks but chokes on a specific heavy query). Removing dead backends from rotation matters enormously — without it, some fraction of user requests keep getting routed into a black hole (timeouts) until a human intervenes, which is exactly the kind of cascading-failure trigger Phase 6 covers (a dead backend eating requests can also starve retries and pile up latency across the whole system).

**Sticky sessions — the tradeoff:** some applications keep session state in the memory of whichever server first handled a user (rather than externalizing it to Redis or similar — see 1.4's discussion of the sticky-session problem). To make that work, the LB must pin a given client to the same backend for the life of their session, typically via a cookie the LB sets (`Set-Cookie: SERVERID=backend3`) or via IP hash. The upside is it's the path of least resistance if you don't want to re-architect session storage. The downside is real: it undermines even load distribution (a backend that happens to get several "big" sessions stays hot while others idle), and it turns that backend into a soft single point of failure for every user pinned to it — if it goes down, all those users lose their session state simultaneously. The modern default recommendation is to avoid needing stickiness at all by keeping servers stateless and pushing session state to a shared store, precisely so the load balancer is free to use whatever algorithm best balances load without correctness depending on it.

## 5.2 Caching

Caching is the single highest-leverage lever in system design, and it's a direct, concrete application of the latency table from 1.5 — a cache hit trades a slow lookup (disk, database, cross-region network call) for a fast one (RAM, or at worst a same-datacenter hop to a dedicated cache server). Everything about caching design is really about answering two questions: **when does data get written into the cache relative to the source of truth**, and **what gets evicted when the cache is full**.

### Write policies — mechanics and, critically, failure modes

**Cache-aside (a.k.a. lazy loading):** the application, not the cache, owns the logic. On read: check the cache; on a hit, return it; on a miss, read from the database, then populate the cache with that value before returning it. On write: the application writes to the database — and either invalidates the corresponding cache entry (safer) or does nothing and lets it expire via TTL. **Failure mode:** if something else updates the database directly (another service, a batch job, a direct DB migration) without going through your application's write path, the cache now holds **stale data** with no mechanism to know it's stale until the TTL naturally expires. This is the most common caching pattern in practice (it's what "add Redis in front of your DB" usually means by default) precisely because it's simple and only caches what's actually requested — but that staleness window is the tradeoff you're always implicitly accepting.

**Write-through:** every write goes to the cache and the database **synchronously**, as a single logical operation, before the write is considered complete. This keeps cache and database always consistent (no stale-read window) at the cost of added write latency, since every write now waits on two systems instead of one. It also means cold data that's never read still gets written into the cache, which can waste cache capacity on values nobody asks for.

**Write-back (write-behind):** the write goes to the cache first and is acknowledged to the client immediately; the cache asynchronously flushes it to the database sometime later (batched, on a timer, or on eviction). This gives very fast write latency and can absorb write bursts (many writes to the same hot key get coalesced into one eventual DB write). **Failure mode — the big one to say out loud in an interview:** if the cache node crashes before the async flush happens, that write is **gone** — it was never durably persisted anywhere else. This is a real data-loss risk, not a theoretical one, and it's exactly why write-back is used selectively (e.g., where the cache itself is replicated/durable, or where losing the very latest write is an acceptable risk) rather than as a default.

**Write-around:** writes go **straight to the database**, completely bypassing the cache. A subsequent read that misses the cache pulls from the DB and populates the cache then (essentially write-around is cache-aside's write path specifically designed to avoid writing to cache). This avoids **cache pollution** — the situation where write-heavy data that's rarely read again (e.g., an audit log write) would otherwise flood the cache with entries that get evicted before ever being read, pushing out genuinely hot data in the process.

| Policy | Write path | Consistency | Write latency | Failure risk |
|---|---|---|---|---|
| Cache-aside | App reads DB on miss, populates cache | Can go stale if DB written elsewhere | Not affected (only read path touches cache) | Stale cache reads |
| Write-through | Cache + DB, synchronously | Strong (always in sync) | Higher (waits on both) | None distinct to this pattern |
| Write-back | Cache first, DB async later | Cache ahead of DB temporarily | Lowest | **Data loss** if cache dies before flush |
| Write-around | DB only, cache untouched on write | Cache never has stale write (only reads populate it) | Not affected on writes | Cache misses immediately after a write (cold read) |

### Eviction policies

When the cache is full and a new entry needs to go in, something has to be evicted. The two workhorses:

**LRU (Least Recently Used):** evict whichever entry hasn't been accessed in the longest time. The intuition is temporal locality — data accessed recently is likely to be accessed again soon. **Real O(1) implementation:** a hashmap (key → node pointer) combined with a doubly linked list ordered by recency (most-recently-used at the head, least-recently-used at the tail). `get(key)`: look up the node via the hashmap, then unlink it from its current position and re-insert it at the head — O(1) because the doubly linked list allows removal from an arbitrary position in constant time given a pointer to the node. `put(key, value)`: if the key exists, update value and move to head as in `get`; if not, insert a new node at the head, and if capacity is exceeded, remove the node at the tail (the hashmap entry for that key is removed too). This exact data structure combo (`HashMap<K, Node>` + intrusive doubly linked list) is a very common system design / coding interview question in its own right.

**LFU (Least Frequently Used):** evict whichever entry has been accessed the fewest total times, on the theory that access frequency is a better long-term predictor of future access than recency alone. It handles a case LRU handles poorly: an item accessed 1000 times historically but not in the last minute shouldn't necessarily be evicted just because a brand-new item was touched once a second ago. The tradeoff is more bookkeeping (a frequency counter per key, and ties need a secondary policy) and it can get "stuck" favoring historically popular items even after they've genuinely gone cold (mitigated in practice with aging/decay of counts over time).

### Thundering herd / cache stampede

**The problem:** a popular cache key expires (or the cache node restarts cold), and a large burst of concurrent requests all miss simultaneously, all fall through to the database at once, and can overwhelm it — potentially causing a cascading failure where the DB slows down, more requests time out and retry, making it worse.

**Solutions:**
- **Locking / single-flight (a.k.a. request coalescing):** when a miss occurs, the first request to miss acquires a lock (or registers as "the one fetching this key"), goes to the database, and populates the cache; every other concurrent request for the *same key* waits on that in-flight fetch and reuses its result instead of independently hitting the database. Libraries like Go's `singleflight` package implement exactly this pattern.
- **Probabilistic early expiration:** instead of a hard TTL cliff, each read has a small, increasing probability of proactively refreshing the cache entry *before* it actually expires, spreading refreshes out over time instead of having everyone hit the wall simultaneously at the exact expiry instant.
- **Staggered/jittered TTLs:** if you're populating many related keys at once (e.g., a cache warm after a deploy), add random jitter to each key's TTL so they don't all expire in the same instant later.

### Where caching happens

Caching isn't one layer — it's stacked at multiple points, each catching what the layer above it missed:
- **Browser cache:** driven by `Cache-Control`/`ETag` headers (1.2) — avoids even making a network request for unchanged static assets.
- **CDN / edge cache:** catches requests before they reach your origin at all (5.3).
- **Application-level cache:** Redis/Memcached sitting between your app servers and the database — the classic cache-aside layer.
- **Database-level cache:** the DB's own buffer pool/page cache (e.g., PostgreSQL's shared buffers, MySQL's InnoDB buffer pool) caching hot pages in memory so even a "cache miss" at the app layer might not require a real disk read.

### Redis vs Memcached

| | Redis | Memcached |
|---|---|---|
| Data model | Rich: strings, lists, sets, sorted sets, hashes, streams, bitmaps | Simple key → byte-string only |
| Persistence | Yes — RDB (point-in-time snapshot) and/or AOF (append-only log of write operations, replayed on restart) | None — pure in-memory, data is gone on restart |
| Concurrency model | Historically single-threaded event loop for command execution (simplifies atomicity of operations); newer versions add threaded I/O | Multithreaded natively, often better raw throughput for pure key-value `get`/`set` workloads under high concurrency |
| Extra features | Pub/sub, Lua scripting, transactions (`MULTI`/`EXEC`), built-in replication and clustering, TTL per key | Minimal — deliberately simple |
| Typical use case | Anywhere you need more than a plain KV cache — session store, leaderboard (sorted sets), rate limiter counters, pub/sub messaging, a durable-ish cache | Pure, simple, maximally fast KV caching layer with no need for persistence or advanced structures |

**Cache hit ratio:** the fraction of reads served from cache vs. falling through to the source of truth (`hits / (hits + misses)`). This is the single most important operational metric for any cache — a cache with a 40% hit ratio might not be worth its operational complexity and cost versus just hitting the database, while a 95%+ hit ratio on a hot dataset is what makes an expensive backend viable at scale at all. Interviewers often want you to reason about *why* the hit ratio would be high or low for a given access pattern (e.g., a power-law/Zipfian access distribution like "20% of products account for 80% of views" caches extremely well; a workload with uniformly random access across a huge key space caches poorly no matter how big the cache is).

## 5.3 CDN (Content Delivery Network)

A CDN is a globally distributed network of edge servers (**PoPs** — points of presence) that cache and serve content physically close to end users, so requests don't have to round-trip all the way to your origin server/datacenter for every single asset. This is a direct, large-scale application of the cross-region latency numbers from 1.5 — shaving 100+ ms off every asset load by serving from a nearby edge node instead of a distant origin.

### Pull-based (origin pull)

The CDN fetches content from your origin **on demand**, the first time a given edge PoP sees a request for it. That first request is a cache miss at the edge — the edge server fetches it from your origin, caches a copy, and serves it. Every subsequent request to that same PoP for that same URL is served directly from the edge cache until the entry's TTL expires (governed by `Cache-Control`/`Expires` headers your origin sends), at which point the next request triggers a fresh pull. This is the default, simplest-to-operate model — you don't manage the CDN's contents directly, you just configure cache headers and the CDN figures out what to cache and for how long on its own. Cloudflare, Amazon CloudFront, and most CDN configurations default to pull.

### Push-based

You **proactively upload** content directly to the CDN ahead of time, rather than waiting for the CDN to discover it via a client request. This is the right model when content changes rarely but must be available everywhere immediately, with zero "first requester pays the cache-miss latency" cost — the canonical example is shipping a large software release or game update: you don't want the very first users in each region to eat a slow origin pull, you want the bits already sitting at every edge location the moment the release goes live. Akamai has historically supported push workflows heavily for exactly this large-file, must-be-everywhere-instantly use case; CloudFront/Cloudflare can approximate push by pre-warming caches, though their primary operating model is pull.

| | Pull | Push |
|---|---|---|
| Content gets to edge | On first client request (cache miss) | Proactively uploaded by you, ahead of demand |
| Operational effort | Low — configure headers, CDN handles the rest | Higher — you manage what's uploaded and when |
| First-request latency | Slower (cache miss round-trips to origin) | None — already there |
| Best for | General web assets, dynamic-ish content, long tail of URLs | Large infrequently-changing files that must be instantly available everywhere (software releases, video assets pre-launch) |

### Cache invalidation — the classic "two hard things in computer science" problem

- **TTL expiry:** the simplest approach — content is considered valid for a fixed duration and re-fetched from origin after that. Works well when you can tolerate some staleness and can predict how long content should live.
- **Explicit purge/invalidation API:** call the CDN's API to force-evict a specific URL (or a whole path prefix) across all edge locations immediately. This works but has real downsides: it's not instantaneous globally (propagation to every PoP takes some time), it costs money/has rate limits on most providers, and it's easy to forget to call it, leaving stale content served indefinitely.
- **Versioned URLs (cache-busting via filename hashing):** instead of invalidating `app.js`, you build `app.a3f9c1.js` where the hash is derived from the file's content, and reference that hashed filename in your HTML. When the content changes, the hash changes, producing a brand-new URL — old cached copies of the old URL simply become irrelevant (nobody references them anymore) and can be left to expire naturally, while the new URL is a guaranteed cache miss that pulls the new content fresh. **Why this is usually the more reliable choice than purge APIs:** it sidesteps the propagation-delay and reliability problem entirely — there's no race condition where some edge nodes have purged and others haven't, because you're never relying on mutating what a URL means, only ever pointing to new immutable URLs. It also lets you set extremely long (even "forever") cache TTLs on versioned assets since the URL itself encodes freshness, maximizing cache hit ratio for anything that hasn't changed.

**Static vs dynamic content through a CDN:** purely static assets (JS/CSS/images/video) are the classic CDN use case — cache aggressively, often with versioned URLs. Dynamic, personalized content (a logged-in user's dashboard) is traditionally *not* cached by the CDN at all and passes through to origin — though modern CDNs increasingly support edge compute (Cloudflare Workers, CloudFront Functions/Lambda@Edge) to run logic at the edge and cache/personalize dynamic responses closer to the user too.

## 5.4 API design: REST vs GraphQL vs gRPC

### RESTful resource modeling

REST models everything as **resources** (nouns), manipulated via standard HTTP methods (the verbs, covered in 1.2). Getting resource modeling right is most of what makes an API feel well-designed vs. awkward:

- **Plural nouns for collections:** `/users`, not `/user` — `/users` is the collection, `/users/42` is a specific member of it. This convention alone eliminates a huge class of bikeshedding about endpoint naming.
- **Nesting for relationships:** `/users/42/orders` reads naturally as "the orders belonging to user 42." Nesting should generally stop at one or two levels deep (`/users/42/orders/7/items` is already pushing it) — beyond that, prefer flattening with query parameters or separate top-level lookups, since deep nesting makes URLs brittle and awkward to construct client-side.
- **Status codes carry real meaning** (see 1.2's table) — a well-modeled REST API uses `201 Created` with a `Location` header pointing to the new resource on a successful `POST`, `404` for a resource that doesn't exist, `409 Conflict` for something like a duplicate unique-key creation, rather than always returning `200` with an error buried in the JSON body.
- **Pagination — offset/limit vs cursor-based, and why cursor wins under concurrent writes:** `GET /users?offset=100&limit=20` is simple but has a real correctness problem — if a row is inserted or deleted before offset 100 between the client's page-1 and page-2 requests, the "window" shifts, and the client either sees a duplicate row (an item shifted back into the range it already saw) or skips one entirely (an item shifted out of the range before the client got to it). **Cursor-based pagination** (`GET /users?after=user_00042&limit=20`) instead returns an opaque cursor (often an encoded ID or a compound sort key) pointing to "the last item you saw," and the next page is defined as "everything after that specific item" — which is stable regardless of concurrent inserts/deletes anywhere else in the collection, because the cursor anchors to a specific row's identity rather than a numeric position that shifts as the underlying data changes. This is why virtually every large-scale API (Twitter/X, Slack, Stripe, GitHub) uses cursor-based pagination for anything beyond small, rarely-changing datasets.

### GraphQL

**The actual value proposition:** a client sends a single query specifying *exactly which fields it needs*, across potentially multiple related resources, and gets back exactly that shape — no more, no less. This directly solves two classic REST pain points: **over-fetching** (a REST `/users/42` endpoint returns a fixed shape including fields this particular screen doesn't need — wasted bandwidth, especially painful on mobile) and **under-fetching** (a screen needs a user plus their last 5 orders plus each order's line items, which in REST means multiple round trips: `/users/42`, then `/users/42/orders`, then per-order line-item calls — GraphQL does it as one query, one round trip). It's a single endpoint (typically `POST /graphql`) with the request body describing the query — the routing logic that in REST lives in the URL structure instead lives in the **schema** (types, fields, and the relationships between them) and **resolvers** (the functions that actually fetch each field's data).

A GraphQL **query** reads data (roughly REST's `GET`); a **mutation** writes data (roughly REST's `POST`/`PUT`/`DELETE`, expressed as named operations like `createUser(input: ...)`); a **subscription** is a long-lived connection (usually over WebSockets) that pushes updates as they happen.

**The real cost — the N+1 query problem:** imagine a query for a list of 50 blog posts, each including its author's name. A naive resolver implementation runs one query to fetch the 50 posts, then — because each post's `author` field is resolved independently — runs 50 *additional* queries, one per post, to fetch each author individually. That's 51 queries (N+1) where a hand-written REST/SQL endpoint would've done it in 1 or 2 with a JOIN. This is not a hypothetical edge case — it's the default behavior of naive GraphQL resolvers and the single most common GraphQL performance bug in production.

**The fix — DataLoader:** the standard pattern (popularized by Facebook's `dataloader` library) batches and caches resolver calls **within a single request**. Instead of each post's author-resolver immediately firing its own DB query, DataLoader collects all the individual `load(authorId)` calls that happen within one tick of the event loop, then issues a single batched query (`WHERE id IN (1, 2, 3, ..., 50)`) and distributes the results back to each waiting resolver — turning 50 queries into 1. It also de-duplicates and caches within that request's lifetime, so if the same author ID is requested twice, only one database round trip happens.

### gRPC

Already covered in depth at the protocol level in 1.7 — the design-choice framing that matters here: gRPC's strengths (HTTP/2 multiplexing, compact binary Protobuf serialization, strong typing with generated stubs, native support for streaming in all four directions) make it the clear winner for **internal service-to-service communication**, especially where you control both ends, care about raw performance, and want a strict, versioned contract enforced by code generation rather than convention. It's a poor fit for public-facing APIs precisely because of what makes it fast: binary payloads aren't human-debuggable in a browser dev tools network tab the way JSON is, and it's not natively cacheable by standard HTTP caches/CDNs the way idempotent REST `GET`s are.

### Picking between the three

| | Best fit | Why |
|---|---|---|
| **REST** | Public APIs, anything needing broad client compatibility and HTTP-native caching | Cacheable (`GET` + `Cache-Control`/CDN), universally understood, human-debuggable, simple tooling |
| **GraphQL** | Client-driven data needs, especially mobile apps under variable network conditions, or products with many different client UIs each needing different data shapes from the same backend | Client controls exactly what's fetched — one round trip instead of many, minimal over-the-wire waste, which matters most on slow/metered connections |
| **gRPC** | Internal service-to-service calls, especially where streaming or strict typing matters | Fastest serialization, strongly typed contracts via `.proto`, native bidirectional streaming, but weak browser/public-API ergonomics and caching |

## 5.5 Message queues & pub/sub

Message queues decouple **producers** (things generating work/events) from **consumers** (things processing them) — the producer doesn't need the consumer to be available, fast, or even running at the moment it sends a message; it just hands the message to the broker and moves on. This buys resilience (a consumer outage doesn't lose work, it just backs up in the queue) and lets producer and consumer scale independently.

| | Kafka | RabbitMQ | SQS |
|---|---|---|---|
| Delivery model | **Log-based**: messages appended to a durable, partitioned, ordered log; consumers track their own offset and can replay from any point | **Queue-based**: broker tracks per-message delivery state, message is removed once acknowledged | **Managed queue** (AWS): similar queue-based delete-on-ack model, but fully hosted, no cluster to operate |
| Ordering | Guaranteed *within a partition*, not across the whole topic | Guaranteed within a single queue (typically) | Standard queues: no ordering guarantee. FIFO queues: strict ordering, at the cost of lower throughput |
| Multiple independent consumers of the same data | Yes, natively — many consumer groups can each read the whole stream at their own pace/offset | Not really the model — once acked, it's gone; fanout to multiple consumers needs multiple queues bound to an exchange | Not natively — SNS (pub/sub) is typically layered in front of SQS to fan out to multiple queues |
| Throughput | Very high — designed for high-volume event streaming | High, but generally lower ceiling than Kafka for pure throughput; better at complex routing | High, scales automatically, but you're bound by AWS's service limits/latency characteristics |
| Replay | Yes — this is a first-class feature, replay from any offset (subject to retention) | No — once consumed and acked, gone | No — once consumed and deleted, gone (though a DLQ can hold failures) |
| Operational complexity | High if self-hosted (ZooKeeper/KRaft, partition rebalancing, broker tuning) — lower via managed offerings (Confluent Cloud, MSK) | Moderate — simpler than Kafka to run, but still a stateful cluster to operate | Minimal — fully managed, no servers to think about, pay-per-use |
| Best fit | Event streaming, event sourcing, systems needing replay or multiple independent readers of the same stream | Task queues, complex routing (see AMQP exchange types in 1.7), moderate throughput with rich routing needs | Simple decoupling in an AWS-native stack where you don't want to operate any broker infrastructure at all |

**Dead-letter queues (DLQ):** when a consumer repeatedly fails to process a specific message (a bug in the handler, malformed data, a downstream dependency that's permanently rejecting it), naive retry logic would keep redelivering that same message forever, potentially blocking every message behind it in the queue (head-of-line blocking at the application level) or endlessly burning consumer resources. A DLQ is a separate queue that a message gets routed to after exceeding a configured number of delivery/processing attempts — it's pulled out of the main flow so the rest of the queue keeps moving, and engineers can inspect the DLQ later to diagnose and manually reprocess or discard the poison message. Every production queueing system (SQS, RabbitMQ, Kafka via consumer-side dead-lettering topics) supports this pattern, and any interview design involving a queue should mention it as the answer to "what happens if a message can never succeed."

**At-least-once vs exactly-once, concretely:**
- **At-least-once:** the default, easiest guarantee to provide — the broker redelivers a message if it doesn't receive an ack in time, which means the same message *can* be processed more than once (e.g., the consumer processed it and crashed right before sending the ack — the broker, having heard nothing, redelivers). This is why consumers must be **idempotent** (see 5.12) — processing the same message twice must be safe.
- **Exactly-once:** genuinely hard to achieve end-to-end and often more accurately described as "effectively-once" — it requires either the messaging system to provide transactional guarantees tightly coupled to the consumer's own state changes (Kafka's transactional producer/consumer APIs, when both producer and consumer participate in the same Kafka transaction) or, more commonly and more robustly in practice, building idempotency into the consumer's own processing logic (dedupe by a message ID stored in the same transaction as the side effect) on top of an at-least-once delivery guarantee. The practical interview answer is usually: assume at-least-once delivery from the broker, and get exactly-once *processing semantics* via idempotency keys at the application layer.

## 5.6 Rate limiting algorithms

Rate limiting protects a service from being overwhelmed — by a buggy client retrying too aggressively, an abusive user, or a genuine traffic spike — by capping how many requests a given client (by API key, IP, user ID, etc.) can make in a given time period.

**Token bucket:** a bucket holds up to `B` tokens and refills at a fixed rate `r` tokens/second (up to the max capacity). Each incoming request consumes one token; if a token is available, the request proceeds and the token is removed; if the bucket is empty, the request is rejected (or queued, depending on implementation). Because tokens accumulate up to the bucket's capacity during idle periods, this algorithm **allows bursts** — a client that's been idle can suddenly fire off up to `B` requests instantly before being throttled back to the steady refill rate. This burst tolerance is usually a feature, not a bug — it models real traffic patterns better than a hard uniform cap.

**Leaky bucket:** conceptually inverted from token bucket — incoming requests are added to a queue (the "bucket"), and they're processed/"leak out" at a strictly fixed rate regardless of how bursty the arrivals were. If the queue is full when a new request arrives, it's dropped. This **smooths** traffic into a perfectly steady outflow rate, which is valuable when the downstream system genuinely cannot handle bursts at all — but it adds latency, since a request can sit queued behind others even if the service has spare capacity, and bursty-but-legitimate traffic gets artificially delayed rather than let through.

**Fixed window counter:** the simplest possible implementation — count requests in a fixed-size time window (e.g., "100 requests per minute," where the minute is wall-clock-aligned: 12:00:00–12:00:59, then resets). Simple to implement (increment a counter, reset it when the window rolls over) but has a concrete, well-known edge case: a client can send 100 requests in the last second of one window (12:00:59) and another 100 in the first second of the next window (12:01:00) — that's **200 requests in a 2-second span**, double the intended rate, purely because the two bursts straddle the window boundary. This "2x burst at the boundary" problem is exactly the kind of detail an interviewer expects you to catch and explain, not just name the algorithm.

**Sliding window log:** store the **exact timestamp of every request** for a given client (e.g., in a sorted set). To check a new request, discard timestamps older than the window (`now - window_size`) and count what's left; if under the limit, allow and record the new timestamp. This is precise — no boundary artifact at all — but memory-heavy, since it stores one entry per request per client rather than a single counter, which can get expensive at high request volume or with many distinct clients.

**Sliding window counter:** the practical middle ground used by most real production rate limiters (this is roughly what Cloudflare and many API gateways implement). It keeps two fixed-window counters — the current window and the previous one — and computes a weighted estimate: `current_window_count + previous_window_count * (fraction of previous window still "inside" the sliding view)`. For example, if you're 30% into the current minute, the estimate is `current_count + previous_count * 0.7`. This gets very close to sliding-window-log's accuracy (no hard boundary exploit) while only needing two integers per client instead of a full timestamp log — O(1) space per client instead of O(requests).

| Algorithm | Allows bursts? | Boundary artifact? | Memory per client | Notes |
|---|---|---|---|---|
| Token bucket | Yes, up to bucket size | No | O(1) | Good default; models real traffic well |
| Leaky bucket | No — smooths to constant rate | No | O(queue size) | Adds latency; good when downstream truly can't handle bursts |
| Fixed window counter | Somewhat, unintentionally | **Yes — up to 2x at boundary** | O(1) | Simplest, but has a real correctness gap |
| Sliding window log | No | No | O(requests in window) | Most precise, most expensive |
| Sliding window counter | Slightly (small approximation error) | No (approximately) | O(1) | Best practical tradeoff — most production systems land here |

## 5.7 SQL vs NoSQL decision framework

This revisits 2.2's data-model taxonomy but reframes it as an actual decision tool, grounded in real product scenarios rather than abstract feature lists.

**The core questions to ask, in order:**

1. **Do I need multi-row/multi-table ACID transactions?** If an operation must atomically touch multiple rows or tables and absolutely cannot leave the system in a half-updated state (money moving from account A to account B — A must decrease and B must increase together, or neither happens) → **relational (SQL)**. This is the single strongest signal pointing at SQL, because true multi-document/multi-row ACID transactions are either unavailable or bolted-on-and-expensive in most NoSQL systems (some, like MongoDB, do now support multi-document transactions, but it's not the natural mode the system was designed around, and it costs performance).
2. **Is the access pattern known in advance, simple, and key-based, and do I need to scale horizontally past what one machine can hold?** If reads/writes are overwhelmingly "give me the record for this ID" (or a small set of well-known query patterns) rather than ad-hoc joins/aggregations across relationships → **NoSQL key-value or document store**. These systems are built to shard cleanly across many machines specifically because they don't need to support arbitrary cross-partition joins — DynamoDB, Cassandra, MongoDB are all designed around the assumption that you model your data around your access patterns up front, not query flexibly after the fact.
3. **Is my data fundamentally about relationships/connections between entities, where the interesting queries are traversals ("friends of friends," "shortest path," "people who bought X also bought Y")?** → **graph database** (Neo4j, Amazon Neptune). Relational databases can technically model graphs (a join table for edges), but multi-hop traversal queries degrade badly with JOIN depth; graph databases store adjacency directly so traversal cost stays roughly proportional to the number of hops, not the size of the whole dataset.

**Walked scenarios:**

- **A bank ledger:** every transaction must debit one account and credit another atomically, must never lose a cent, must support ad-hoc auditing queries and reporting joins across accounts/transactions/customers, and volume, while large, is nowhere near "needs to shard across 500 machines" territory for most institutions. → **SQL** (e.g., PostgreSQL, or a distributed SQL system like Spanner/CockroachDB if you truly need horizontal scale *and* transactions). ACID and strong consistency aren't optional here — "eventually your balance is correct" is not an acceptable answer to a regulator or a customer.
- **A social media feed (e.g., "show the latest posts from people I follow"):** access pattern is overwhelmingly "give me the N most recent posts for this user's feed" or "give me this user's own timeline" — simple, known-in-advance, key-based lookups at massive scale (millions of writes and reads per second), where perfect cross-user transactional consistency isn't the priority (a post appearing a few seconds late in someone's feed is a non-event). → **NoSQL document or wide-column store** (Cassandra is the textbook choice here — it's literally what backs Twitter-scale timeline/feed infrastructure conceptually — or DynamoDB), sharded by user ID, optimized for very high write throughput and simple partition-key reads.
- **A friend-recommendation engine ("people you may know," suggesting connections 2-3 hops away in the social graph):** the entire value of the feature *is* the traversal — "friends of my friends who I'm not already friends with" is a multi-hop graph query that would require multiple expensive self-joins in SQL and doesn't map cleanly to a key-value access pattern at all. → **Graph database** (Neo4j, Neptune), where that exact query is a cheap, natural traversal from a starting node outward.

**The honest interview framing:** SQL vs. NoSQL is not "which is better," it's "which failure mode can I tolerate less" — SQL trades horizontal scaling ease for strong consistency and flexible querying; NoSQL trades flexible querying and (in some cases) strong consistency for horizontal scale and raw throughput on known access patterns. A senior answer names the specific access pattern and specific consistency requirement of the scenario at hand, rather than reciting "NoSQL is for big data."

## 5.8 Blob/object storage (S3-style)

**The object storage model:** unlike a traditional filesystem, object storage is a **flat namespace** — a **bucket** contains **objects**, each addressed by a unique **key** (a string), mapped directly to a blob of bytes plus metadata. There is no real directory hierarchy underneath: a key like `photos/2026/vacation/img001.jpg` *looks* like a nested file path, and most tooling (including the S3 console) renders it as if it were folders, but the `/` characters are purely cosmetic — the object store has no actual concept of a `photos` "directory" as a distinct entity, it's just a flat key string that happens to contain slashes. This matters practically: operations like "list everything under this prefix" are a string-prefix scan over keys, not a directory traversal, and there's no such thing as an empty "folder" existing on its own (some tools fake this by creating a zero-byte object with a trailing-slash key).

**Multipart upload:** for large objects (the classic threshold discussed is anything above roughly 100MB, though it's configurable), instead of uploading the whole file as one request, the client splits it into multiple parts, uploads each part **in parallel** (each part gets its own request and can be retried independently without re-uploading the whole file if one part fails), and then issues a final "complete multipart upload" call listing all the part identifiers, which the storage service assembles server-side into the final single object. This gives better throughput (parallelism), resilience (a failed part doesn't restart the whole upload), and is the standard mechanism for anything from large video files to database backups.

**Signed URLs — the precise mechanics of temporary, scoped access without exposing credentials:**

The problem signed URLs solve: your backend holds real credentials (an access key + secret key) for your storage bucket, but you often need to let a *client* (a browser, a mobile app) directly upload or download an object without ever handing that client your actual credentials — because if you did, that client (or anyone who intercepts its traffic/decompiles the app) could do *anything* your credentials allow, forever.

The mechanism: your server, which does hold the real secret key, constructs a URL that embeds a **cryptographic signature** — specifically, an **HMAC (keyed-hash message authentication code)** computed over a canonical string that includes the resource path (bucket + key), an **expiry timestamp**, and the permitted operation(s) (e.g., `GET` only, or `PUT` for upload), using the secret key as the HMAC key. That signature gets appended to the URL as a query parameter alongside the expiry and other signed fields. When the client later makes a request to that URL, the storage service **independently recomputes the same HMAC** using its own copy of the secret key over the same canonical request data, and checks that it matches the signature in the URL, and that the current time is before the embedded expiry. If both check out, the request is allowed — **without any callback to your application server** at request time. This is the key insight: your server did the (cheap, offline) work of producing a signature once, and the storage service can verify it independently and instantly on every subsequent request, purely through shared-secret cryptography, with no need for your server to be involved in — or even aware of — each individual access. This is exactly how "upload directly to S3 from the browser" or "give a user a temporary download link that expires in 15 minutes" work in practice, and it's the standard answer to "how would you let users upload large files without routing all those bytes through your own application servers first."

## 5.9 Search infrastructure basics

**The inverted index — the core data structure that makes full-text search fast:** a normal ("forward") index maps document → the terms it contains, which is useless for the actual question search needs to answer ("which documents contain the word 'raft'?") because it would require scanning every document. An **inverted index** flips this: it maps **term → list of document IDs** (a "postings list") that contain that term. Searching for a word becomes a direct lookup (hashmap or B-tree lookup on the term) returning the postings list immediately, instead of a linear scan over every document in the corpus. A multi-word query ("distributed" AND "consensus") becomes an intersection of the two terms' postings lists — a well-understood, efficient set operation, especially when postings lists are stored sorted so intersection can be done in a single merge pass.

**Relevance scoring:**
- **TF-IDF (Term Frequency–Inverse Document Frequency):** a document is scored higher for a query term the more often that term appears in it (**term frequency** — a document mentioning "raft" 10 times is probably more about Raft than one mentioning it once), but that raw frequency is discounted by how common the term is **across the whole corpus** (**inverse document frequency** — the word "the" appears constantly everywhere and carries almost no distinguishing signal, so its weight is pushed way down, while a rare term like "paxos" that appears in few documents carries a lot of signal when it does appear).
- **BM25** is the modern, more refined successor used by default in most real search engines (including Elasticsearch) — it builds on the same TF-IDF intuition but adds saturation (term frequency's contribution to the score has diminishing returns — the 20th occurrence of a word barely adds more relevance signal than the 10th did) and document-length normalization (a term appearing 3 times in a 50-word document is a much stronger signal than the same 3 occurrences in a 5,000-word document, and BM25 accounts for that).

**Elasticsearch architecture basics:**
- Built on top of **Apache Lucene**, which is the actual inverted-index/search-engine library doing the low-level indexing and querying work — Elasticsearch is the distributed system layered around Lucene, handling clustering, sharding, replication, and a REST API on top.
- An Elasticsearch **index** (roughly analogous to a database/table) is split into multiple **shards**, and those shards are distributed across the nodes in the cluster. Each shard is itself a **complete, independent Lucene index** (its own self-contained inverted index) — a query against the whole Elasticsearch index is executed by fanning it out to every shard and merging the results.
- Each shard has a **primary** copy and can have one or more **replica** shards — replicas serve two purposes: redundancy (if a node holding a primary dies, a replica can be promoted, no data loss) and read scalability (search queries can be served by either the primary or any replica, spreading read load). This mirrors the leader-follower replication concepts from Phase 3, applied specifically to shards of a search index.
- Sharding count is typically fixed at index-creation time (resharding later is more disruptive than in some other systems), which is why capacity planning for expected index size matters up front in a real Elasticsearch deployment — a classic interview-relevant operational gotcha.

## 5.10 Notification/push systems: fan-out on write vs fan-out on read

This is the central design tension behind any feed, timeline, or notification system (Twitter/X, Instagram, Facebook) — **when** does the system do the work of figuring out "what does this user see," at write time or at read time?

**Fan-out on write (a.k.a. push model):** when a user posts, the system immediately writes/pushes that post into the feed (or inbox) of **every one of their followers**, right at write time — so each follower already has a pre-computed feed sitting ready, and reading a feed later is just "fetch my already-materialized feed," which is fast and cheap. The cost is entirely shifted to write time, and it's proportional to follower count: a normal user with a few hundred followers means a few hundred writes, trivial. A user with **millions of followers** posting once means millions of fan-out writes triggered by a single action — this is famously called the **"celebrity problem"** (sometimes "hot key" or "hot write" problem): the write amplification for one post from a hugely-followed account can be enormous, slow, and resource-intensive, potentially delaying delivery to everyone by minutes, and creating a massive, bursty write spike on the system.

**Fan-out on read (a.k.a. pull model):** nothing is pre-computed at write time — a post is just written once, to the author's own timeline. When a follower opens their feed, the system computes it **on the fly** by querying and merging the recent posts from everyone that user follows. Writes are trivially cheap (one write, always, regardless of follower count) — but reads become expensive, especially for a user who follows many accounts (their feed read now has to query and merge from potentially thousands of sources every single time they open the app), and this cost is paid on every single read rather than once at write time.

**The hybrid solution real systems actually use:** fan-out on write for the overwhelming majority of regular users (whose follower counts make the write cost trivial and whose followers benefit from instant, pre-computed reads), combined with fan-out on read — or a special-cased merge — specifically for celebrity/high-follower-count accounts. In practice this often looks like: a normal user's feed is mostly pre-materialized via fan-out-on-write, and at read time the system *additionally* checks "am I following any celebrity accounts?" and merges their latest posts in live, on read, rather than ever having tried to push those posts out to millions of feeds at write time. This is the standard answer Twitter-scale system design discussions converge on, and it's a direct, concrete example of choosing different strategies for the median case vs. the long-tail outlier case rather than one-size-fits-all.

## 5.11 Consistent hashing

Consistent hashing is the single technique that shows up across sharding (Phase 3), load balancing (5.1), and caching (5.2) — it's worth understanding once, deeply, because it explains *why* all three of those systems can add or remove a node without catastrophically reshuffling everything.

**The problem with naive modulo hashing:** if you shard data across `N` servers by computing `hash(key) % N`, then changing `N` — adding or removing even a single server — changes the modulo result for **almost every key**, because the divisor itself changed. Going from 4 servers to 5 means nearly all keys now map to a different server than before, which for a cache means an almost-total cache wipe (every key effectively becomes a miss against its "new" server), and for a sharded database means a massive, expensive data-reshuffling operation just to add one more machine.

**The mechanism:** both the **nodes** (servers/shards) and the **keys** (data items) are hashed using the same hash function onto points on a **fixed circular ring** — conceptually, the hash output space (e.g., `0` to `2^32 - 1`) is treated as wrapping around back to `0`, forming a circle. A node is placed on the ring at the position given by hashing its identifier (e.g., its IP address or server name). A key belongs to whichever node is **the first one encountered going clockwise** from that key's position on the ring.

**Why this bounds the remapping when the fleet changes:** when a node is added, it's inserted at one specific point on the ring — it only "steals" the keys that fall between it and its counter-clockwise neighbor (the range that previously all belonged to the next node clockwise from the new node). Every other key, everywhere else on the ring, is completely unaffected — it still maps to the same node it did before, because nothing about its position or its nearest-clockwise-node relationship changed. On average, adding a node to a cluster of `N` nodes only remaps roughly `1/N` of the total keys (specifically, the keys owned by whichever single node happens to be its clockwise neighbor), rather than nearly all of them as naive modulo hashing would. Removing a node has the mirror-image effect — its keys are absorbed by its clockwise neighbor, and no other node's keys are touched.

**Virtual nodes — why they're necessary in practice:** with only a handful of physical nodes, hashing each one to a single point on the ring produces very uneven arcs by chance — one physical node might end up "owning" a much larger stretch of the ring than another purely due to hash randomness, leading to lopsided load even though the algorithm is theoretically fair. The fix is to give each **physical** node multiple positions on the ring (e.g., 100–200 **virtual nodes** each, via hashing `nodeID + "-0"`, `nodeID + "-1"`, ... `nodeID + "-N"`), so each physical node's total "ownership" is the sum of many small, scattered arcs rather than one single contiguous arc. With enough virtual nodes per physical node, the law of large numbers smooths out the unevenness, and load distributes far more evenly across physical nodes — this is exactly how systems like Amazon Dynamo, Cassandra, and most consistent-hashing-based load balancers actually implement it in production; naive single-point-per-node consistent hashing is a teaching simplification, not what's actually deployed.

## 5.12 Idempotency & deduplication in distributed calls

**Why retries are unavoidable:** in a distributed system, a network timeout tells you the client didn't *receive a response* — it tells you nothing about whether the server actually received, processed, and completed the request before that response was lost, delayed, or never sent. This is the exact same ambiguity called out for RPC in 1.7 and for message delivery in 5.5: the client genuinely cannot distinguish "the request never arrived," "it arrived and is still processing," and "it arrived, completed, and only the response got lost" — from the client's point of view they all look identical (a timeout). Given that ambiguity, the only safe default behavior for a client that cares about not silently losing an operation is to **retry**. But retrying a non-idempotent operation (like "charge this card") risks executing it twice.

**The concrete mechanism — idempotency keys:** the client generates a **unique key per logical operation** (typically a UUID) *before* making the first attempt — not a new one per retry, the *same* key is reused across every retry of that same logical operation. That key is sent alongside the request (commonly as a header, e.g., `Idempotency-Key: 7c3f...`). On receiving a request, the server first checks whether it has already seen and processed that exact key — typically by looking it up in a store (a database table or a cache like Redis) that maps `idempotency_key → result`, kept for some reasonable TTL (long enough to cover realistic retry windows, e.g., 24 hours). 
- If the key has **not** been seen before: the server executes the operation normally, and — critically, as part of the *same* transaction/atomic unit of work as the operation itself — stores the key along with the result.
- If the key **has** been seen before: the server does **not** re-execute the operation at all. It simply returns the previously stored result, as if the operation had just now succeeded, even though nothing actually ran this time.

**The concrete payment example that makes this matter:** a client calls "charge $50 to this card," the server successfully charges the card and sends back a `200 OK` — but that response is lost in transit (a network blip, the client's connection drops before it reads the response). The client, having seen only a timeout, retries the exact same "charge $50" request. Without idempotency handling, the server has no way of knowing this is a retry of an already-completed charge rather than a brand-new charge request, and processes it again — the customer is now charged **$100** for something that should have cost $50, a real, damaging bug that idempotency keys directly prevent: the retried request arrives with the *same* idempotency key, the server recognizes it's already processed that exact key, and returns the original "charged $50, success" result without touching the payment processor a second time.

**Why the storage of the key must be atomic with the operation itself:** if the "mark this key as processed" step happens separately from (and especially *after*) the actual side effect, there's a race window where a retry could sneak in between the side effect completing and the key being recorded, and double-execute anyway — this is why production implementations typically record the idempotency key and its result within the same database transaction as the operation's own state change, not as an afterthought bolted on outside it.

## 5.13 Observability: logging, metrics, tracing, health checks

Observability is how you know something's wrong (or right) in a running production system, without having to guess or wait for a customer complaint. It rests on three complementary pillars plus a fourth practical layer (health checks) purpose-built for automated failure detection.

**Structured logging:** instead of free-text log lines (`"User 42 logged in at 10:03"` — readable by a human, painful to query at scale), structured logs are emitted as consistently-shaped records, typically JSON, with a fixed set of fields (`timestamp`, `level`, `service`, `user_id`, `request_id`, `message`, plus arbitrary contextual key-values). This matters because at scale, logs aren't read line-by-line by a human tailing a file — they're ingested into a system (e.g., the ELK/Elastic stack, Splunk, Datadog) and **queried and aggregated**: "show me every 5xx response for `service=checkout` in the last hour, grouped by `error_code`" is a trivial structured query against JSON fields, and effectively impossible to do reliably against inconsistent free-text strings. Including a **request ID** or **trace ID** field consistently across every log line touched by one request is what lets you later reconstruct "everything that happened for this one specific request" across many services — the connective tissue between logging and tracing.

**Metrics — the three fundamental types:**
- **Counter:** a value that only ever increases (until a process restart resets it) — total requests served, total errors, total bytes sent. Useful for computing rates over time (e.g., "requests per second" is the derivative/rate of a monotonically increasing counter).
- **Gauge:** a value that can go up or down, representing a current snapshot state — current memory usage, current number of open connections, queue depth right now.
- **Histogram:** captures the **distribution** of observed values, not just a single number — most critically used for latency, bucketed so you can extract percentiles: **p50** (median — half of requests are faster than this), **p95**, **p99** (the tail — the slowest 5%/1% of requests). Percentiles matter far more than averages in production because an average can look perfectly healthy while a meaningful fraction of real users are having a terrible, slow experience — "average latency is 50ms" can coexist with "p99 latency is 4 seconds," and it's the p99 users who complain, file tickets, and churn. This is why SLOs (service level objectives) are almost always expressed in percentile terms ("p99 latency under 300ms"), never plain averages.

**Distributed tracing:** a **trace** represents one complete end-to-end request as it flows through a distributed system, composed of multiple **spans**, where each span represents the work done by one specific service/component the request touched (e.g., "API gateway received request" → "auth service validated token" → "order service queried database" → "payment service called external processor" — each is its own span, with its own start/end time, nested or sequential under the overall trace). The mechanism that ties these together across process/service/network boundaries is a **trace ID**, generated once at the very start of the request and **propagated forward** through every downstream call — typically as an HTTP header (or gRPC metadata) that each service reads, includes in its own emitted spans, and forwards to whatever it calls next. Without this propagation, you'd have a pile of disconnected logs/spans from different services with no way to reconstruct that they were all part of the same originating request. **OpenTelemetry** is the modern, vendor-neutral standard for generating and exporting this data (traces, metrics, and logs, unified) — it decouples "how my code emits observability data" from "which backend (Jaeger, Datadog, Honeycomb, Grafana Tempo, etc.) actually stores and visualizes it," so instrumentation isn't locked to one vendor.

**Health check patterns — liveness vs readiness:** these answer two genuinely different questions, and conflating them is a common real-world bug:
- **Liveness:** "is this process alive and not deadlocked/hung?" A failed liveness check typically triggers the orchestrator (e.g., Kubernetes) to **kill and restart** the process, on the theory that a hung process won't self-recover.
- **Readiness:** "is this process currently able to accept and correctly serve traffic right now?" A process can be perfectly alive (liveness passes) but **not ready** — e.g., it just started and hasn't finished establishing its database connection pool yet, or it's warming an in-memory cache, or it's deliberately draining connections during a graceful shutdown. A failed readiness check tells the load balancer/orchestrator to **stop routing new traffic to it**, without killing it — exactly the "active health check" mechanism described in 5.1, applied at the container-orchestration layer as well as the load-balancer layer. Using a liveness check where a readiness check belongs is a classic real-world mistake: a process still warming up gets killed and restarted in a loop, because "not ready yet" was misinterpreted as "dead," and it never gets the chance to finish starting up.

## 5.14 API lifecycle and design approaches

### Lifecycle stages and their real concerns

- **Design:** deciding the actual contract — what resources/operations exist, what the request/response shapes look like, what errors are possible — *before* writing implementation code (or, in contract-first, formalized as an actual spec document). The core question at this stage is "what will consumers of this API need, and what shape minimizes future breaking changes."
- **Develop:** building the implementation behind the agreed contract. The main risk at this stage is implementation details leaking into the contract (e.g., exposing an internal database column name directly as a field, which then becomes very hard to change later without breaking consumers).
- **Deploy:** getting a new version out while existing consumers keep working. The central decision is **versioning strategy**: **URL versioning** (`/v1/users`, `/v2/users` — simple, highly visible, easy to route differently at the infrastructure layer, but can lead to duplicated endpoint logic across versions) vs **header versioning** (`Accept: application/vnd.myapi.v2+json`, or a custom `API-Version` header — keeps URLs stable/clean, but is less discoverable and easy for consumers to forget to set, silently defaulting to an unintended version).
- **Monitor:** once live, track real usage — which consumers call which endpoints/versions, error rates per endpoint, latency percentiles (tying directly back to 5.13's metrics), and specifically usage of any **deprecated** endpoints/fields, which is what tells you whether it's actually safe to remove something yet or whether a major consumer is still depending on it.
- **Retire:** a **sunset policy** — a clearly communicated timeline (e.g., "v1 will stop working on 2027-01-01") given well in advance, ideally with active warnings surfaced to consumers still using the old version (a `Deprecation` or `Sunset` HTTP header is the standards-track way to signal this programmatically, not just in documentation), plus a **migration window** giving consumers real time to move to the new version before the old one is actually shut off. Retiring an API abruptly, without warning, is one of the more damaging things a platform team can do to its downstream consumers/partners.

### Design approaches

- **Top-down:** design the contract/interface first — what the API looks like from the consumer's point of view — and only afterward build the implementation to satisfy it. This front-loads the hard interface-design thinking, which is exactly the right tradeoff for **consumer-facing / public APIs**, where the interface, once published, is expensive to change and many external parties will build against whatever you ship — you want to get the shape right before it's load-bearing for people outside your control.
- **Bottom-up:** build the underlying components/services first, and let the API's shape emerge more organically from what was actually built. This is faster to get moving for **internal tooling** where the "consumer" is your own team and iteration is cheap — but it carries a real risk: the resulting API can end up **leaky** (exposing internal implementation quirks directly) or **awkward** (shaped by what was convenient to build rather than what's convenient to consume), because no one deliberately designed the consumer-facing contract as a first-class artifact.
- **Contract-first:** write the formal specification (an **OpenAPI** spec for REST, or a `.proto` file for gRPC) *before* any implementation code exists on either side, and then **generate client and server stubs from that spec**. This is powerful specifically because it enables genuinely **parallel work**: frontend and backend teams can both start building against the agreed, generated stubs simultaneously, without either side blocking on the other's implementation being finished — the contract itself is the synchronization point, and both sides trust it because the stubs are mechanically generated from it rather than hand-written and potentially drifting out of sync with docs.

## 5.15 Application architecture patterns

### MVC → MVCS → MVCRS: where business logic and data access actually live

**MVC (Model-View-Controller):** the classic split — the **Controller** handles incoming input/requests, the **Model** holds the data and (in the classic definition) the business logic, and the **View** renders output. **The common real-world problem:** in practice, especially in web frameworks where "the model" ends up being treated as a thin representation of a database row/table, business logic has nowhere disciplined to live and creeps directly into controllers — a controller method that's supposed to just "handle the HTTP request" ends up doing validation, business rule enforcement, orchestration across multiple models, and data access all in one place. This is the well-known **"fat controller"** problem — controllers become bloated, hard to test (you can't easily unit-test business logic without spinning up the whole HTTP request path), and hard to reuse (the same business logic needed by a background job or a CLI tool can't be reused because it's trapped inside an HTTP-request-shaped method).

**MVCS (adding a Service layer):** introduces a **Service** layer sitting between the Controller and the Model, whose whole job is to hold the actual business logic — the controller's job shrinks down to "parse the request, call the appropriate service method, format the response," and stays thin. The service layer is what a background job, a CLI command, or a different API version could all call into equally, since it's decoupled from any particular delivery mechanism (HTTP, message queue trigger, cron job).

**MVCRS (adding a Repository layer):** goes one step further, introducing a **Repository** layer between the Service layer and the actual data store, whose job is purely data access — abstracted behind an interface like "get user by ID," "save order," with the concrete implementation (is this hitting PostgreSQL? MongoDB? a cache? some combination?) hidden entirely behind that interface. This buys two concrete things: (1) you can **swap or change the underlying storage** (migrate from one database to another, add a caching layer in front of reads) by changing only the repository implementation, without touching a single line of business logic in the service layer, because the service layer only ever talks to the repository's interface, never to a specific database driver directly; (2) **testability** — unit tests for the service layer's business logic can inject a fake/mock repository (an in-memory stand-in) instead of needing a real database running, making tests fast and independent of infrastructure.

| Layer | Responsibility | What it should NOT do |
|---|---|---|
| Controller | Parse request, call service, format response | Business logic, direct data access |
| Service | Business logic, orchestration, validation rules | HTTP-specific concerns, raw SQL/queries |
| Repository | Data access abstraction (CRUD against whatever the actual store is) | Business rules, request/response formatting |
| Model | The data shape itself (entity/domain object) | — |

### Server-driven vs client-driven UI

**Client-driven UI:** the client (mobile app, web frontend) owns the rendering logic and layout decisions — the server's job is purely to return data (typically as JSON via REST/GraphQL), and the client decides how to lay it out, which components to show, in what order. This is the default, familiar model for most web and mobile development.

**Server-driven UI:** the server instead returns a **description of what UI to render** — a layout/config (e.g., "show a card component with this title, this image, this button, in this order") — and the client acts as a comparatively **"dumb renderer"**, interpreting that server-provided structure into actual UI at runtime, rather than having that layout hard-coded into the client's own shipped code. **The concrete real-world reason this matters:** mobile app updates go through app store review (Apple App Store, Google Play), which can take anywhere from hours to days, and users have to actually download and install the update before they see anything different — meaning a client-driven app's UI/promo/layout changes are gated behind that entire release-and-adoption cycle. Server-driven UI lets a company change what users see — a new promotional banner, a reordered home screen, an entirely new flow for a feature flag/experiment — **instantly, for all users, with zero app-store review and zero client update required**, because the client is just faithfully rendering whatever structure the server sends this time. The cost is real too: the client becomes more generic and less able to build deeply custom, highly-polished, platform-specific interactions (since it has to stay general enough to render server-described structures rather than hand-tuned native screens), and debugging/reasoning about "what does the UI actually look like right now" becomes harder since it's a function of server state rather than fixed in the shipped app binary. Large consumer apps (many e-commerce and social apps) use server-driven UI heavily for exactly the promo/home-screen/feature-flag use case, while keeping core, interaction-heavy screens (a camera viewfinder, a chat composer) client-driven and natively built.

**1.** You're designing an e-commerce checkout API. A client submits a "place order and charge card" request, but the response times out due to a flaky mobile network. The client's retry logic automatically resends the exact same request. Separately, the product team wants the order-listing page to support jumping to "page 3" reliably even while new orders are being placed by other users concurrently. What two distinct techniques from this phase address these two problems, and how do they actually work?

<details>
<summary>Expand</summary>

- **Duplicate charge on retry:** an **idempotency key** (5.12). The client generates one UUID per logical "place this order" attempt and sends it on every retry of that same attempt. The server checks a store of already-processed keys before executing — if it's seen this key before, it returns the previously stored result instead of charging the card again. This must be recorded atomically with the charge itself to avoid a race where a retry sneaks in between the charge completing and the key being recorded.
- **Reliable pagination under concurrent writes:** **cursor-based pagination** (5.4), not offset/limit. Offset/limit ("page 3" = `offset=40&limit=20`) shifts underneath you as orders are inserted/deleted elsewhere in the table, causing skipped or duplicated rows across page loads. A cursor anchors to a specific order's identity ("give me the 20 orders after this specific order ID"), which stays stable regardless of what else changes in the table.

**2.** A celebrity influencer account with 50 million followers is about to post, and separately your team is deciding whether to run a naive GraphQL resolver for a "list of posts with author names" screen. Explain what goes wrong in each case if you use the "obvious" default approach, and name the specific fix for each.

<details>
<summary>Expand</summary>

- **Celebrity post:** naive **fan-out on write** (5.10) would try to push that one post into 50 million individual follower feeds/inboxes at write time — an enormous, slow write-amplification spike (the "celebrity problem"). The fix used in practice is a **hybrid model**: regular users get fan-out on write (cheap, since follower counts are small), but celebrity accounts are special-cased to fan-out on read — followers' feeds pull/merge the celebrity's recent posts live at read time instead of the post ever being pushed to millions of feeds.
- **GraphQL resolver:** a naive per-post resolver for `author` triggers the **N+1 query problem** (5.4) — one query for N posts, then N additional individual queries, one per post, to fetch each author. The standard fix is the **DataLoader pattern**: batch all the individual author-lookup calls that occur within one request into a single `WHERE id IN (...)` query, cutting N+1 queries down to 2.

</details>
