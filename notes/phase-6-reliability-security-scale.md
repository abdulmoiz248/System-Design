# Phase 6 — Reliability, Security & Scale at the Edges

Everything so far has been about making a system *work* and *work fast*. This phase is about making it keep working when a datacenter burns down, a downstream dependency hangs forever, an attacker probes it, or traffic spikes 10x overnight — the concerns that separate a demo from something Microsoft would actually run in production. As with every other phase, the goal is mechanics and "why," not vocabulary.

---

## 6.1 Failover, redundancy, multi-region architectures; SPOF identification & mitigation

**The core idea:** any system that runs on real hardware will experience hardware failure, network partitions, and entire datacenter outages — not hypothetically, but on a schedule. At Microsoft/AWS/Google scale, "a rack loses power" or "a whole availability zone goes dark" is a **Tuesday**, not a black-swan event. Reliability design isn't about preventing failure (impossible) — it's about making failure *survivable* and, ideally, invisible to the end user.

**Single Point of Failure (SPOF) — what it is and how to find one systematically:** a SPOF is any single component whose failure takes down the whole system, or a meaningful part of it, with no path around it. The way to actually find SPOFs in an interview (or in a real architecture review) is mechanical, not clever: **walk every single component in the diagram — every server, database, load balancer, cache, message queue, DNS record, even the network link and the power supply — and for each one ask "if this dies right now, does the system stop working, degrade badly, or keep going?"** Anything where the honest answer is "stops working" is a SPOF, full stop, no matter how unlikely you think the failure is. Common SPOFs that get missed even by people who've internalized "add a load balancer": a *single* load balancer instance sitting in front of many redundant app servers (the app tier is redundant, but the LB itself isn't — so LBs themselves are deployed in redundant pairs, often with a floating/virtual IP that moves to the standby on failure); a database with no replica; a single DNS provider; a shared config service or secrets store with one instance; a single NTP source that everything's clock sync depends on; a single message queue broker instead of a cluster.

**Mitigating SPOFs — the concrete mechanisms:**
- **Redundant instances behind a load balancer.** The most common fix at the app tier — run N ≥ 2 identical instances, put a load balancer in front, and losing any single instance just means the LB routes around it. This only works if the LB itself is redundant and if the app tier is stateless (Phase 1.4) — a stateful instance can't just be silently replaced by another one that doesn't have the same in-memory state.
- **Health checks removing unhealthy nodes automatically.** A load balancer (or orchestrator) periodically pings each backend (an HTTP `GET /health` endpoint, a TCP connect, or an application-level check that verifies the instance can actually reach *its* dependencies, not just that the process is alive) and stops routing traffic to any instance that fails N consecutive checks. This is what turns "a server crashed" from an outage into a transparent capacity dip — the system detects and reacts without a human paging in at 3am.
- **Self-healing via orchestration.** Kubernetes is the canonical example: a Deployment declares "I want 5 replicas of this pod running," and the **controller loop** continuously reconciles actual state against that desired state — if a pod crashes, gets OOM-killed, or its node dies entirely, Kubernetes schedules a replacement automatically, no human intervention required. This is a generalization of the health-check idea: instead of just *routing around* a dead instance, the system actively *replaces* it to restore full capacity.

**Multi-region architecture — the two real strategies:**

**Active-passive (a.k.a. active-standby) failover:** one region (the primary) serves all live traffic; a second region (the standby) sits provisioned and ready, replicating data from the primary, but doesn't serve production traffic under normal conditions. If the primary fails, traffic is redirected to the standby, which is promoted to primary.
- *Pros:* conceptually simple — no need to solve concurrent multi-region writes, since only one region is ever the source of truth at a time. Easier to reason about data consistency.
- *Cons:* the standby's capacity sits **idle** most of the time — you're paying for compute/infrastructure that does nothing under normal operation, which is expensive relative to the value delivered. **Failover itself takes real time** — detecting the primary is actually down (not just experiencing a transient blip — you don't want to fail over on a 2-second network hiccup), promoting the standby, and repointing traffic all take seconds to minutes, during which the system is degraded or fully down. And depending on replication mode (Phase 3.2), failover **can lose in-flight data** — if replication to the standby was asynchronous, any writes accepted by the primary but not yet replicated at the moment of failure are gone.

**Active-active:** multiple regions all serve live production traffic simultaneously, typically routed by proximity (GeoDNS, anycast) or load.
- *Pros:* far better resource utilization (no idle standby capacity — every region is doing useful work), and dramatically lower failover time, because there's no "promote a cold standby" step — if one region dies, traffic simply stops being routed there and the remaining regions absorb it (assuming they were provisioned with enough headroom to do so — see 6.8).
- *Cons:* this is architecturally much harder, because now you must solve **cross-region data consistency** — if a user's write can land in region A and another user reads it moments later from region B, how does that write get there, how fast, and what happens if two regions accept conflicting writes to the same record at nearly the same time? This is exactly the multi-leader replication and conflict resolution problem from Phase 3 (3.1, 3.12) — active-active multi-region is, at its core, multi-leader replication applied at the geography level, with all the same tradeoffs (eventual consistency windows, last-write-wins or custom merge logic for conflicts).

| | Active-Passive | Active-Active |
|---|---|---|
| Resource utilization | Poor — standby idle | Good — all regions doing useful work |
| Failover time | Slower (detect → promote → repoint) | Fast/near-instant (traffic just stops routing there) |
| Data consistency complexity | Low (single writer) | High (multi-leader conflict resolution) |
| Risk of data loss on failover | Yes, if replication was async | Lower — no single "primary" to lose |
| Typical use case | Simpler systems, DR-focused | High-scale global systems (Phase 3-literate teams) |

**DNS-based failover and its core weakness:** a common (and cheap) way to implement failover is at the DNS layer — health-check the primary region's endpoint, and if it fails, update the DNS record to point at the standby/secondary region's IP instead (this is the same GeoDNS/health-check-aware DNS mechanism from Phase 1.3). The problem is **DNS caching**: every DNS record has a TTL, and resolvers, OSes, and browsers all cache the old answer for up to that TTL. Even after you flip the record at the authoritative server, clients holding a cached (now-dead) IP will keep trying to reach the failed region until their local cache expires — meaning DNS-based failover is never instant, and a certain fraction of users experience an outage for the duration of the TTL (which is exactly why, as noted in Phase 1.3, teams proactively lower TTLs before a planned failover-capable deployment — a low TTL here isn't paranoia, it's what makes DNS failover actually fast). This is also why DNS-based failover is often layered with something faster underneath it at large scale (anycast, where the same IP is announced from multiple locations and BGP routing — not DNS/client caching — decides which one a packet reaches, so a failed location can simply stop being announced and traffic reroutes at the network layer within seconds).

## 6.2 Circuit breakers, retries with backoff, bulkheads

These three patterns exist for the same underlying reason: in a distributed system, calls to other services **fail, or worse, hang** — and a naive caller that just keeps calling a broken dependency doesn't just fail its own request, it can make the *entire system* worse by piling load onto an already-struggling service, or by tying up its own threads/connections waiting on something that'll never respond. All three patterns are about **failure containment** — stopping one component's bad day from becoming everyone's bad day.

**Circuit breaker — the three states, precisely:**
- **Closed** — the normal state. Requests flow through to the downstream dependency as usual, and the breaker silently counts failures (and successes) in a rolling window.
- **Open** — once failures exceed a configured threshold (e.g., >50% of calls failed in the last 10 seconds, or 5 consecutive failures), the breaker **trips open**. In the open state, calls to the downstream service **fail immediately, without even attempting the network call** — the caller gets an instant error (or falls back to a default/cached response) instead of waiting out a timeout. This does two things at once: it **protects the failing downstream service** from being hammered with more requests while it's already struggling (which often makes recovery slower or impossible — a service in a bad state getting *more* load rarely helps), and it **protects the caller** from wasting threads, connections, and time waiting on calls that are statistically very likely to fail anyway.
- **Half-open** — after a cooldown period, the breaker lets a small number of *test* requests through to see if the downstream service has recovered. If those test calls succeed, the breaker closes again and normal traffic resumes; if they still fail, it trips back to open and waits another cooldown period before trying again. This is what makes the breaker self-healing rather than requiring a human to manually reset it once the downstream is fixed.

**Real libraries worth naming:** **Hystrix** (Netflix) was the library that popularized this pattern in the JVM/microservices world in the early 2010s — it's now legacy/in maintenance mode (Netflix themselves moved away from it), but it's historically important because it's the reason "circuit breaker" became a mainstream term in backend engineering, and interviewers may still reference it by name. **resilience4j** is the modern standard replacement in the Java ecosystem — lighter weight, built for Java 8+ functional style, and modular (circuit breaker, rate limiter, retry, and bulkhead are separate composable modules rather than one monolithic library). Equivalent patterns exist in most languages/frameworks (e.g., Polly in .NET — worth knowing given the Microsoft/Azure lean of this prep).

**Retries with exponential backoff and jitter:** a naive retry ("if it fails, immediately try again") is often worse than not retrying at all — if the downstream service is struggling because it's overloaded, an immediate retry adds load at the exact moment it can least handle it. **Exponential backoff** fixes the timing: after each failed attempt, double the wait time before the next attempt (e.g., 1s, 2s, 4s, 8s, 16s...), giving the downstream service progressively more room to recover, and capping the retry attempts (or total elapsed time) so a caller doesn't retry forever. But exponential backoff alone has a subtler failure mode: if a downstream service has a brief outage and **many clients all failed at the same moment**, plain exponential backoff means they'll all retry again at *exactly* the same future moment too — 1 second later, all of them try again together; if that fails, 2 seconds later, all of them try together again. This synchronized pile-on is called a **retry storm** (or "thundering herd" applied to retries), and it can turn a brief blip into a self-sustaining outage, because the recovering service gets hit by a synchronized wave of traffic right as it's trying to come back up. **Jitter** — adding randomness to the backoff interval (e.g., instead of waiting exactly 4 seconds, wait a random value between 0 and 4 seconds, or 4 seconds ± some random offset) — spreads those retries out over time instead of letting them land in lockstep, which is the entire point: it's not about making any individual client's retry smarter, it's about desynchronizing the herd.

**Bulkhead pattern:** named directly after ship compartmentalization — a ship's hull is divided into watertight compartments (bulkheads) so that if one compartment floods, the water is contained there and doesn't sink the whole ship. Applied to software: **isolate the resources used to call different downstream dependencies**, typically via separate thread pools or separate connection pools per dependency, so that if one dependency becomes slow or unresponsive, it can only exhaust *its own* pool of resources — it can't starve the threads/connections that calls to other, healthy dependencies need. Without this isolation, a single slow dependency (say, a third-party payment provider that starts timing out) can consume every thread in a shared pool waiting on it, which means calls to completely unrelated, perfectly healthy dependencies (say, an internal inventory service) also start failing — not because inventory is broken, but because there are simply no threads left to make that call. Bulkheads turn "one dependency's failure" back into "one dependency's failure," instead of letting it cascade into "the whole service is down."

These three patterns compose naturally: a bulkhead limits how much damage a slow dependency call can do to shared resources; a circuit breaker stops making calls to a dependency once it's clearly failing, so retries aren't even attempted against something obviously broken; and retries-with-backoff-and-jitter handle the transient, recoverable failures that do get attempted while the circuit is closed.

## 6.3 Authentication methods: Basic, Digest, API keys, session-based vs JWT

Authentication answers "who is making this request." The methods below trade off simplicity, statefulness, and revocability against each other — there's no universally "best" one, only the right one for a given use case.

**Basic Auth:** the client sends `username:password`, **base64-encoded** (not encrypted — base64 is a reversible encoding, trivially decoded by anyone who intercepts it), in the `Authorization` header on **every single request**. This is only safe at all when the connection runs over TLS (Phase 1.2) — over plain HTTP, credentials are exposed in the clear. Even over TLS, the design has a real weakness: the raw credentials are resent on every request, meaning they exist in plaintext in memory/logs on both ends far more often than necessary, and there's no way to limit what a compromised credential can do or revoke access without changing the actual password. Its appeal is pure simplicity — no server-side session state, no token infrastructure — which is why it still shows up for quick internal tooling or simple API integrations, but it's a poor fit for anything user-facing at scale.

**Digest Auth:** an improvement on Basic's core flaw (credentials crossing the network at all). The flow is challenge-response: the server sends a **nonce** (a one-time random value) in a `401` challenge; the client computes a hash of the credentials combined with that nonce (and other request details) and sends only the hash back — the raw password itself never crosses the network, even encoded. This is a genuine security improvement over Basic in principle, but it's relatively weak and legacy by modern standards (limited hash algorithm support historically defaulted to MD5, which is cryptographically broken for other purposes; it doesn't protect the request body or provide the same guarantees TLS does) — in practice, "just use TLS + Basic, or better, use tokens" has displaced Digest almost everywhere. Worth knowing it exists and why it was an improvement, less worth reaching for today.

**API keys:** a single opaque string, generated once and included in requests (as a header or query param), identifying the calling application (not necessarily a specific human user). Simple to implement and simple for the caller to use — no login flow, no token refresh logic. The real weakness: an API key is typically a **long-lived, coarse-grained credential** — a leaked key (committed to a public GitHub repo, logged accidentally, exposed in client-side JS) grants **full access until someone notices and manually revokes it**, and API keys usually don't carry fine-grained scope (which specific actions this key can perform) the way a well-designed token can. This is why API keys are generally reserved for server-to-server integrations where the key can be kept in a secrets manager, not for end-user authentication.

**Session-based authentication (stateful):** the classic web app pattern. On login, the server verifies credentials, generates a random **session ID**, and stores session state (who this user is, what they're allowed to do, when it expires) **server-side** — in memory, in a file, or, for anything beyond a single server, in a shared store like **Redis**. The session ID itself is handed to the client via a **cookie**, and the browser automatically sends that cookie back on every subsequent request. On each request, the server takes the session ID from the cookie and **looks up** the corresponding session state to know who's making the request. The critical architectural consequence: **the server must be stateful, or the session store must be centralized**, for this to work across multiple server instances — if server A creates the session in its own local memory and the load balancer routes the user's next request to server B, server B has no idea who this session ID belongs to unless it can look it up in a store both servers share. This is exactly the sticky-session problem from Phase 1.4, and the practical fix is the same one — push session state into Redis (or similar) so any instance can serve any request, rather than pinning a user to one server.

**JWT (JSON Web Token) — stateless:** structured as three base64-encoded segments joined by dots: `header.payload.signature`.
- **Header** — declares metadata about the token itself, most importantly the signing algorithm used (e.g., `HS256` — HMAC with SHA-256, a symmetric algorithm where the same secret both signs and verifies; or `RS256` — RSA signature with SHA-256, an asymmetric algorithm where a private key signs and a public key verifies, useful when the verifier shouldn't hold the signing secret at all).
- **Payload** — the **claims**: arbitrary data about the token, typically user ID, role, and expiry (`exp`). Critically, this is base64-**encoded**, not encrypted — anyone who has the token can decode and read the payload trivially (paste any JWT into jwt.io and you'll see the claims in plaintext). This means **secrets must never go in a JWT payload** — no passwords, no sensitive PII, nothing you wouldn't be fine printing on a postcard.
- **Signature** — computed by hashing the header and payload together with a secret (HMAC) or signing them with a private key (RSA), letting **any server holding the corresponding secret/public key verify the token hasn't been tampered with** — without needing to call back to a central database or session store at all. Change one character of the payload and the signature no longer matches, so tampering is immediately detectable.

**JWT's real pros and cons, stated honestly:**
- **Pro — scales better.** Because verification is just a cryptographic check against the token itself, any server instance can verify any token independently, with **no database lookup, no shared session store, no network round trip**. This is a genuine advantage for horizontally scaled, multi-service architectures — it's exactly the kind of statelessness Phase 1.4 pushed toward for the app tier generally.
- **Con — hard to revoke before expiry.** This is the tradeoff that catches people off guard: because there's no central store being checked, **a JWT is valid until it expires, no matter what** — if a user's account is compromised, or an admin needs to force a logout, or a user's permissions just changed, there is no built-in mechanism to invalidate an already-issued token early. The workaround (a **blocklist** of revoked token IDs that every verifying server checks) technically works, but it **reintroduces the exact centralized, stateful lookup JWTs were adopted to avoid** — at that point you've rebuilt session-based auth with extra steps. The practical mitigation most real systems use is keeping JWTs **short-lived** (see access/refresh tokens in 6.4) precisely so the "can't revoke early" window is small by design rather than solved architecturally.

| | Session-based | JWT |
|---|---|---|
| State location | Server-side (memory/Redis) | Client-side (in the token itself) |
| Verify a request | DB/store lookup by session ID | Cryptographic signature check, no lookup |
| Scales across instances | Needs shared session store | Naturally stateless |
| Revoke immediately | Trivial (delete the session) | Hard (must maintain a blocklist, reintroducing state) |
| Typical lifetime | Until logout/expiry, renewable | Short-lived by design, paired with a refresh token |

## 6.4 Token strategy: access tokens vs refresh tokens; OAuth2.0 flows; SSO

**Access tokens vs refresh tokens — why two tokens instead of one:** a single long-lived token is a liability (if it leaks, it's valid for a long time), and a single short-lived token with no renewal mechanism forces the user to log in again constantly (bad UX). The standard fix is to split responsibilities:
- **Access token** — short-lived (typically minutes), sent on **every API call** (usually as a `Bearer` token in the `Authorization` header), and is what a resource server actually checks to authorize a request. Because it expires quickly, **the damage window if it leaks is small** — an attacker who steals it can only use it until it naturally expires, often before they'd even get around to abusing it.
- **Refresh token** — long-lived (days to weeks), stored more securely on the client (e.g., an **httpOnly cookie**, which JavaScript running on the page can't read — a deliberate mitigation against theft via XSS, see 6.6), and used for exactly one purpose: **exchanging itself for a new access token** without forcing the user through the login flow again.

**The concrete refresh flow:** client makes API calls with the access token until it expires (or the server returns `401`); the client then sends the refresh token to a token endpoint; the server validates the refresh token, and if valid, issues a fresh access token (and often a fresh refresh token too — "refresh token rotation," which additionally lets the server detect reuse of an old, already-rotated-out refresh token as a signal of theft); the client resumes calling the API with the new access token, transparently to the user. This is exactly why you can close a mobile app for a week and reopen it still logged in — the refresh token, not the access token, is what's actually keeping the session alive behind the scenes.

**OAuth 2.0 — an authorization framework, not an authentication protocol.** This distinction matters and gets tested: OAuth2 is about a user granting a third-party application **limited access to their resources on another service**, without handing over their password to that third party (e.g., "let this photo-printing app access your Google Photos" — the printing app never sees your Google password, only a scoped token). It answers "what is this app allowed to do," not "who is this user" (that's what OIDC, layered on top, adds — see below).

**The main OAuth2 flows:**
- **Authorization Code flow** — the standard for traditional server-side web apps. The user is redirected to the authorization provider (e.g., Google's login page), approves the requested access, and the provider redirects back to the app with a short-lived **authorization code** (not a token yet) in the URL. The app's **backend server** then exchanges that code, together with its own **client secret**, for the actual access/refresh tokens — this exchange happens server-to-server, so the tokens **never touch the browser directly** at any point, which is the whole security property this flow is built around (the browser only ever sees the short-lived, single-use code).
- **Client Credentials flow** — machine-to-machine, no user in the loop at all. A service authenticates directly with its own client ID and client secret and receives an access token representing *itself*, not any particular user — used for backend-to-backend API access (e.g., a batch job calling an internal API on its own behalf).
- **PKCE (Proof Key for Code Exchange)** — the modern addition designed for **public clients** that can't safely hold a client secret at all (a mobile app or a single-page JavaScript app — both ship code to the end user's device, so any embedded secret could be extracted). Instead of a static client secret, the client generates a random **code verifier**, derives a **code challenge** from it (a hash), sends the challenge at the start of the authorization request, and later proves possession of the original verifier when exchanging the code for tokens — the provider checks the verifier matches the earlier challenge. This proves the app completing the exchange is the same one that started the flow, without ever needing a long-lived embedded secret. PKCE has become the recommended default even for confidential clients in many cases, not just public ones, because it closes an authorization-code-interception attack that plain Authorization Code flow is otherwise exposed to.

**SSO (Single Sign-On):** the broader user experience of logging in once and gaining access to multiple, independent applications without re-authenticating for each one (e.g., logging into one Microsoft/Google/Okta account and getting into email, calendar, internal tools, and third-party apps all at once). Two real protocols implement this underneath:
- **SAML (Security Assertion Markup Language)** — older, XML-based, still very common in enterprise environments (large corporate identity providers, legacy B2B integrations). An identity provider issues a signed XML "assertion" asserting who the user is, which a service provider trusts and consumes.
- **OIDC (OpenID Connect)** — built directly on top of OAuth2 as an identity layer, JSON-based, and the modern default for consumer-facing and most new enterprise integrations alike — this is the mechanism behind "Sign in with Google/Microsoft/Apple" buttons. OIDC adds a standardized **ID token** (itself a JWT) on top of OAuth2's access token, specifically carrying identity claims (who the user is), which is the piece OAuth2 alone deliberately didn't define.

## 6.5 Authorization models: RBAC, ABAC, ACL

Where authentication answers "who is this," authorization answers "what is this identity allowed to do." Three common models, each with a different unit of granularity and a different failure mode as systems grow.

**RBAC (Role-Based Access Control):** permissions are attached to **roles** (e.g., `admin`, `editor`, `viewer`), and users are assigned to one or more roles rather than having permissions granted individually. Checking access becomes "does this user's role include this permission" — simple to reason about, simple to audit ("show me everyone with the `admin` role"), and simple to implement. The known failure mode as an organization's requirements get more granular is **role explosion**: if you need "editor, but only for documents in the Marketing folder, and only during business hours, and only if they haven't been flagged for review," a pure role model forces you to either create an ever-growing combinatorial explosion of narrowly-scoped roles (`marketing-editor-business-hours-unflagged`) or bolt on exceptions outside the role system entirely — at which point the simplicity that made RBAC attractive is gone.

**ABAC (Attribute-Based Access Control):** access decisions are computed **at request time** by evaluating **policy rules against attributes** of the user, the resource, and the environment — e.g., "allow if `user.department == resource.department` AND `current_time` is within business hours" or "allow if `user.clearance_level >= resource.classification_level`." This is far more flexible and fine-grained than RBAC — it can express conditions RBAC simply has no vocabulary for (time of day, resource ownership, relationship between user and resource attributes, request context like IP range or device trust level) without needing to predefine a role for every combination. The cost is that ABAC is **harder to audit and reason about globally** — there's no fixed, enumerable list of "who can do what" the way there is with a role table; the actual set of permissions any given user effectively has emerges dynamically from evaluating rules against live attribute values, which makes "can user X access resource Y" a computation rather than a lookup, and makes security review meaningfully harder (you have to reason about the policy engine's behavior across all possible attribute combinations, not just read a table).

**ACL (Access Control List):** a list attached **directly to each individual resource**, specifying exactly which users or groups have which permissions on *that specific resource* — the canonical real-world example is a single file's sharing settings in Google Drive or Dropbox ("this document is shared with alice@ (editor), bob@ (viewer), and the Marketing group (commenter)"). The key structural difference from RBAC: **the permission lives on the resource, not in a global role definition.** RBAC asks "what can this role do across the system," ACL asks "who can do what to this one specific object." ACLs are the natural fit when access needs to be granted per-object by the object's owner (sharing a specific file, a specific calendar event, a specific folder) rather than governed by a centrally-administered role hierarchy — but they don't scale well to reasoning about system-wide policy the way RBAC does, since permissions are scattered across every individual resource instead of centralized.

| | Unit of control | Granularity | Auditability | Example |
|---|---|---|---|---|
| RBAC | Role → permissions | Coarse (per role) | Easy — enumerable role table | "Admins can delete users" |
| ABAC | Policy rule over attributes | Fine, contextual | Hard — behavior emerges from rule evaluation | "Allow if same department AND business hours" |
| ACL | Resource → user/group list | Fine, per-object | Easy per-object, hard system-wide | "This file shared with Alice (edit), Bob (view)" |

These aren't mutually exclusive in real systems — it's common to see RBAC for broad system-level permissions (who can access the admin panel at all) layered with ACLs for object-level sharing (which specific documents a given user can open) and ABAC-style conditions sprinkled in for context-sensitive rules (geofencing, time-based restrictions) on top of both.

## 6.6 Web/app security: CORS, XSS, CSRF, SQL/NoSQL injection, rate limiting, firewalls, VPNs, encryption in transit/at rest

**CORS (Cross-Origin Resource Sharing) — mechanically:** browsers enforce the **same-origin policy** by default — JavaScript running on `https://siteA.com` cannot read the response of a request it makes to `https://siteB.com` unless `siteB.com` explicitly allows it. This isn't about blocking the request from being *sent* (it often still is), it's about blocking the browser's JavaScript from *reading the response*. CORS is the mechanism by which a server opts back into allowing this, via response headers — most importantly `Access-Control-Allow-Origin`, which names which origins are permitted to read responses from this server (or `*` for "any origin," which is fine for a public API but dangerous for anything involving credentials). For **"non-simple" requests** — anything beyond plain `GET`/`POST` with standard content types, e.g. a `PUT`/`DELETE` request, or one carrying custom headers like a JWT in `Authorization` — the browser first sends a **preflight `OPTIONS` request** asking "am I allowed to make this actual request," before sending the real one; the server responds with which methods/headers/origins it permits, and only if that preflight succeeds does the browser proceed with the real request. This preflight round-trip is invisible in normal application code but shows up clearly in network traces and is a common source of "why is there an extra OPTIONS request in front of my API call" confusion.

**XSS (Cross-Site Scripting) — three variants:**
- **Stored XSS** — malicious script gets **saved into the backend** (e.g., typed into a comment field, a username, a profile bio) and is later served, unescaped, to *other* users viewing that content — the most dangerous variant because it compromises every viewer, not just the attacker's own session.
- **Reflected XSS** — the malicious script is embedded in the request itself (typically a crafted URL with script in a query parameter) and the server **immediately reflects it back** in the response without sanitizing it (e.g., a search page that echoes `?q=<search term>` straight into the results page HTML) — requires tricking a victim into clicking a specific malicious link, but doesn't require anything to be persisted.
- **DOM-based XSS** — the vulnerability never touches the server at all; it's entirely **client-side JavaScript** unsafely writing untrusted data (from the URL, from `document.referrer`, from a postMessage, etc.) directly into the page's DOM (e.g., via `innerHTML`) in a way that lets it execute as script.

**XSS mitigation:** **output encoding/escaping** — any user-supplied content rendered into HTML must be escaped so that characters like `<`, `>`, `"` are rendered as literal text, not interpreted as markup (modern frameworks like React escape by default when you interpolate into JSX, which is a large part of why XSS became rarer with their adoption — the unsafe path, `dangerouslySetInnerHTML`, is deliberately named to stand out). **Content-Security-Policy (CSP)** headers add a second layer — they let a server declare, e.g., "only execute scripts loaded from this specific domain," so even if an attacker manages to inject a `<script>` tag, the browser refuses to execute it because it violates the declared policy.

**CSRF (Cross-Site Request Forgery) — concretely:** a user is logged into `bank.com` (their browser holds a valid session cookie for it). They then visit a malicious site, which contains a hidden form or auto-submitting request targeting `bank.com/transfer?to=attacker&amount=1000`. Because **cookies are attached automatically by the browser to any request to the domain they belong to, regardless of which site initiated the request**, that forged request arrives at `bank.com` carrying the user's legitimate session cookie — from the server's point of view, it looks exactly like a real, authenticated request from that user, because the authentication mechanism (the cookie) genuinely is valid. The attacker never sees or steals the cookie; they just get the victim's own browser to spend it on their behalf.

**CSRF mitigation:** **CSRF tokens** — the server embeds a random, unpredictable token in each form/page it serves, and requires that same token to be submitted back with any state-changing request; because the token is scoped per-session/per-form and an attacker's cross-origin page has no way to read it (same-origin policy again), the attacker can't forge a valid request even though the browser will still attach the cookie automatically. The modern complementary defense is the **`SameSite` cookie attribute** — setting a cookie to `SameSite=Strict` or `SameSite=Lax` tells the browser **not to send that cookie at all** on requests originating from a different site, which blocks the CSRF vector largely at the browser level without requiring per-form tokens (though CSRF tokens remain the more airtight, explicit defense and the two are often used together).

**SQL injection — concretely and the fix:** when user input is **concatenated directly into a query string** (`"SELECT * FROM users WHERE name = '" + userInput + "'"`), an attacker who controls `userInput` can inject their own SQL — classic example, submitting `' OR '1'='1` turns the query into one that matches every row, or a more aggressive payload can chain a `; DROP TABLE users; --` to execute a second destructive statement entirely. The fix is **parameterized queries / prepared statements**, which separate the query structure from the data **at the database driver level** — the query template is compiled first, and the user-supplied values are bound afterward as pure data, never as executable query syntax, so no amount of clever input can change what the query *does*, only what it matches against. This is meaningfully different from (and more robust than) trying to escape dangerous characters yourself — escaping is pattern-matching against known-dangerous sequences and it's easy to miss an edge case; parameterization structurally prevents the class of bug entirely.

**NoSQL injection — why NoSQL isn't automatically immune:** the underlying vulnerability (unsanitized user input being interpreted as query logic instead of pure data) isn't specific to SQL syntax — it's specific to *any* system that builds queries from untrusted input. MongoDB is the commonly cited example: if a query is built by directly passing a client-supplied JSON object into a query filter, and that object contains operators like `{"$gt": ""}` where a literal value was expected, an attacker can manipulate query logic (e.g., turning a password-equality check into "greater than empty string," which matches everything) purely through the shape of the JSON they submit, no traditional string-based injection required. The fix is analogous to SQL's — validate and sanitize input types strictly (don't trust a client-supplied filter object wholesale), and use query builders/ODMs that enforce expected shapes rather than passing raw client JSON straight into a database query.

**Rate limiting** (mechanisms covered in depth in Phase 5.6 — token bucket, leaky bucket, sliding window) is also a security control here, not just a fairness/cost control: it caps how fast an attacker can brute-force credentials, scrape data, or hammer an endpoint, turning what would otherwise be an unbounded attack surface into a bounded one.

**Firewalls vs WAFs:** a **firewall** filters traffic at the **network level** — rules based on IP address, port, and protocol ("block all inbound traffic except ports 80/443," "allow this IP range only"). A **WAF (Web Application Firewall)** filters at the **HTTP/application layer** specifically — it inspects the actual content of HTTP requests (headers, query params, body) looking for known attack patterns (SQL injection strings, XSS payloads, suspicious user agents), which a network-level firewall has no visibility into at all since it only sees packets, not parsed HTTP semantics. A firewall and a WAF are complementary layers, not substitutes for each other — a firewall can't stop a well-formed HTTPS request carrying a SQLi payload in its body, and a WAF isn't the tool for blocking raw port scans.

**VPN (Virtual Private Network):** an encrypted tunnel that extends a private network over a public one — traffic between a client and a VPN gateway is encrypted, letting a remote employee's laptop behave, from the network's perspective, as if it were physically sitting inside the corporate network, and letting traffic traverse the untrusted public internet without being readable in transit by anyone in between.

**Encryption in transit vs at rest:** **in transit** is TLS (Phase 1.2) — protecting data while it's moving across a network, between client and server or between services. **At rest** is encrypting data **on disk** — so that if the physical storage medium itself is stolen, improperly decommissioned, or accessed by someone who bypasses the application layer entirely (a rogue employee with raw disk access, a leaked backup file), the data is still unreadable without the decryption key. Real-world implementations: **Transparent Data Encryption (TDE)**, where the database engine itself encrypts data files on disk automatically, invisibly to application code — the app queries the database normally and never touches encryption logic directly. The more general enterprise pattern is **envelope encryption**: data is encrypted with a data encryption key (DEK), and the DEK itself is encrypted by a separate key encryption key (KEK) held in a dedicated **key management service (KMS)** — e.g., AWS KMS or Azure Key Vault — so the actual data-encrypting keys never need to be stored unencrypted anywhere, key rotation can happen without re-encrypting the entire dataset, and access to keys is centrally audited and controlled independent of where the encrypted data itself lives.

## 6.7 Data partitioning for compliance (GDPR-style regional data residency)

**Why this exists:** various jurisdictions legally require that certain categories of user data physically remain within specific geographic boundaries. The **EU's GDPR (General Data Protection Regulation)** is the most commonly referenced example, but it's far from the only one — many countries have their own **data localization laws** (Russia, China, India, and others have varying requirements that personal data of their citizens be stored, and sometimes processed, within national borders). The important framing for a system design interview: this is not a legal footnote that "someone in compliance handles later" — it's a real architectural constraint that shapes the data layer from day one, in the same category of design decision as consistency or partitioning strategy from Phase 3.

**Concrete architectural implications:**

- **Sharding strategy changes.** Instead of partitioning purely for load-balancing convenience (e.g., hashing a user ID uniformly across shards — Phase 3.3), you may be required to **partition by region/the user's home geography** — an EU user's data lives on EU-located infrastructure, a US user's on US infrastructure, and so on — regardless of which arrangement would otherwise be most balanced or efficient. This can create genuine hot-spot problems (if one region has disproportionately more users than others, that region's shard(s) carry disproportionate load) that a pure load-balancing partition scheme wouldn't have — compliance constraints and even load distribution can directly conflict, and the compliance requirement wins.
- **Cross-region replication design gets restricted.** Under a purely technical mindset, replicating every user's data to every region for disaster recovery and low-latency reads everywhere (Phase 3.1/3.2) is the obvious move. Under data residency law, you may be **legally prohibited from replicating certain fields across a border at all**, even for legitimate disaster-recovery purposes — meaning the DR strategy for regionally-restricted data has to be solved entirely *within* the permitted jurisdiction (e.g., multi-AZ redundancy within the EU, rather than cross-continental replication), which is a real constraint on how much resilience that data can achieve compared to data with no residency requirement.
- **"Right to be forgotten" is a genuine engineering problem, not just a policy one.** GDPR grants users the right to request their data be deleted, and the system has to be able to **actually and completely honor that** — which is much harder than it sounds in a real production system. Data doesn't live in one place: it's in the primary database, in read replicas, in caches (Redis, CDN edges), in search indexes, in analytics warehouses, in application logs, in **backups** (which are often immutable snapshots taken on a schedule, not something you can selectively edit after the fact), and — the hardest case — in **event-sourced or append-only log architectures** (Phase 4.3), where the entire design principle is that the log is immutable and the current state is *derived* by replaying it. In an event-sourced system, you fundamentally **cannot go back and edit or delete an old event without breaking the replay guarantee that makes the architecture work** — naive deletion just doesn't work there. Real solutions for that case include **crypto-shredding** (encrypt each user's data with a per-user key, and "delete" the data by simply destroying that one key — the ciphertext can remain in the immutable log forever, but it's permanently unreadable once the key is gone) or maintaining a separate, mutable "current state" projection that supports true deletion while leaving raw historical events encrypted-and-effectively-inert. The general lesson for an interview: **"can we actually delete this user's data everywhere it lives" is a question worth asking explicitly during the deep-dive of any design that touches personal data, backups, or event logs** — it's exactly the kind of non-functional requirement (Phase 0.3) that's easy to hand-wave and that a strong candidate calls out proactively.

## 6.8 Capacity planning & autoscaling strategies

**Reactive autoscaling:** scale the number of running instances based on a **live metric** crossing a threshold — CPU utilization above 70%, request queue depth exceeding some size, memory pressure, etc. This is the default mode most cloud autoscaling groups operate in (referenced already in Phase 1.4), and it's simple to set up and generically applicable — it doesn't require knowing anything about your specific traffic patterns in advance. The real weakness is **lag**: by the time a metric crosses its threshold, load is *already* elevated, and new instances take real time to provision, boot, and warm up (pull container images, warm caches, establish connection pools, JIT-warm a runtime) before they can usefully absorb traffic — meanwhile the existing fleet is straining under load that's already arrived. This lag window is exactly where cascading failures start (an overloaded instance gets slower, which makes its health checks start failing, which reduces effective capacity further, right as more capacity is needed) — reactive autoscaling is necessary but, by itself, always a step behind the actual traffic curve.

**Predictive/scheduled autoscaling:** scale **ahead of** a known or forecasted traffic pattern rather than waiting for a live metric to react to it — e.g., a retailer pre-scaling its fleet before a known daily peak (evenings, lunch hours), or explicitly before a known event (Black Friday, a product launch, a ticket on-sale). This eliminates the boot/warm-up lag problem entirely for *predictable* load, since new capacity is already online and warm by the time the traffic actually arrives, but it only works for load patterns that are actually predictable — it does nothing for genuinely unexpected spikes (a piece of content going viral, a competitor's outage driving traffic your way), which is why production systems generally run **both**: scheduled scaling for known patterns, reactive autoscaling layered on top to handle the residual unpredictability.

**Load testing:** the practical way to know your actual breaking point instead of guessing. Simulating expected peak traffic (and beyond) against a staging or shadow environment before it happens for real — tools like k6, Gatling, Locust, or JMeter generate synthetic load and measure where latency starts degrading, where error rates climb, and which specific component fails first (the database connection pool exhausting, a downstream dependency's rate limit being hit, a single-threaded bottleneck nobody had noticed). This matters because architectural bottlenecks are often *not* where anyone assumes — a team might scale the stateless web tier confidently, assuming that's the constraint, and discover under real load testing that the actual ceiling is a shared database connection pool or a third-party API's rate limit, neither of which more web server instances does anything to fix. Load testing before a known high-traffic event (a product launch, a sale) is the difference between finding that bottleneck in a controlled test versus finding it live, in production, in front of real users and real revenue on the line.

**Headroom / buffer capacity:** the practical rule that a system should never be planned to run at 100% of its known capacity under normal load — some slack (commonly discussed as running steady-state at something like 60-70% of max provisioned capacity, though the right number is workload-specific) has to be reserved deliberately. The reason ties directly back to reactive autoscaling's lag: if the fleet is already running at its ceiling, there is **no slack left to absorb a spike** while new capacity boots up and warms up in response — the system is guaranteed to degrade for however long that boot/warm-up window takes, precisely at the moment load is increasing. Headroom is what buys the *time* reactive autoscaling needs to actually work — without it, autoscaling is reacting to a fire that's already out of the room it started in.

**1.** You're designing a global e-commerce checkout system. During your deep-dive, the interviewer asks: "Your primary region just went completely dark — total power loss, no ETA on recovery. Walk me through what happens to a user mid-checkout, and what architectural choice determines how bad this actually is." What do you say, and what specific tradeoff are you highlighting?

<details>
<summary>Expand</summary>

The answer hinges on whether the system is **active-passive** or **active-active** across regions, and this is where you should show you understand the tradeoff rather than just naming both terms.

- If **active-passive**: the standby region has to be detected as needed, promoted, and traffic repointed (possibly via DNS, with the accompanying TTL-caching delay from 6.1) — this takes real time (seconds to minutes), during which checkout is degraded or fully down. Additionally, if replication to the standby was asynchronous (Phase 3.2), any writes accepted by the primary in the moments before it died — e.g., an order that was confirmed to the user but not yet replicated — may be **lost**, meaning some users mid-checkout could see their order simply vanish or double-charge on retry.
- If **active-active**: traffic simply stops being routed to the dead region and the remaining regions, assuming they were provisioned with headroom (6.8) to absorb the extra load, keep serving checkout with much less disruption — but this only works if the system already solved cross-region write consistency (Phase 3.1/3.12) for things like inventory counts and order records, since two regions were both accepting live writes the whole time.

The core tradeoff to name explicitly: active-active gives faster, less lossy failover, but it isn't free — it requires the harder multi-leader consistency work up front. Active-passive is simpler to build correctly but pays for that simplicity with slower, lossier failover. A strong answer also flags that regardless of which model, DNS-based rerouting alone is never instant because of client-side caching/TTL — something faster (anycast, or a smart client-side retry against a secondary endpoint) is needed if sub-second failover is a hard requirement.

**2.** A mobile banking app uses JWTs for authentication. A user reports their phone was stolen while logged in, and asks support to "log them out everywhere immediately." Why is this harder to do cleanly with JWTs than with traditional session-based auth, and what would you actually build to satisfy this requirement without giving up JWT's scalability benefits entirely?

<details>
<summary>Expand</summary>

With **session-based auth**, this is trivial: the server deletes the session record from the shared store (Redis), and the next request carrying that session ID immediately fails lookup — instant, centralized revocation, because the server was already checking a central source of truth on every request.

With **JWTs**, the whole design point is that servers verify the token's signature locally and **never** do a central lookup — that's where the scalability win comes from. This means a stolen-but-still-valid JWT **remains valid until it naturally expires**, no matter what support does on the backend, unless something changes that default behavior.

The practical fix used in real systems, consistent with 6.3/6.4: keep **access tokens short-lived** (minutes) specifically so any stolen access token has a small, bounded blast radius even with no revocation mechanism at all — and put the actual revocation control on the **refresh token**, which the system already tracks server-side (it has to, to issue new access tokens and support rotation). Revoking/deleting the specific refresh token(s) tied to that user's session immediately stops any future access-token renewal — the thief's current access token still works for its remaining few minutes, but no new ones can be issued after that, which for a stolen-phone scenario is an acceptable and fast-enough resolution. This is deliberately choosing to reintroduce a small amount of centralized state (refresh token tracking) rather than the full JWT blocklist approach, keeping the high-volume, per-request access-token checks fully stateless while still supporting real revocation on a bounded timescale.

</details>
