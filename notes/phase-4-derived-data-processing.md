# Phase 4 — Derived Data & Processing

Everything in Phase 2 and 3 was about the **system of record** — where truth lives and how it stays consistent. Phase 4 is about everything downstream of that: the caches, search indexes, analytics tables, recommendation models, and materialized views that get *derived* from the system of record by running data through some processing pipeline. The recurring question this phase answers is "given a huge (or endless) pile of data, how do you transform it into something more useful, and how do you keep that derived thing correct as the source keeps changing underneath it." Grounded in DDIA Part III (Kleppmann, Ch. 10–12).

## 4.1 Batch processing: MapReduce concepts, joins at scale

**The problem batch processing solves:** you have a fixed, bounded dataset — terabytes or petabytes sitting in files — and you need to run some computation over *all of it* (build a search index, compute recommendations, generate a report) in a way that finishes in reasonable time and survives individual machine failures along the way. A single machine can't hold or process this much data in a reasonable timeframe, so the computation has to be split across hundreds or thousands of machines — and that split has to happen in a way that's mechanical and predictable, not bespoke per job.

**The MapReduce model, precisely:**

MapReduce (Google's 2004 paper, later open-sourced as the core of Hadoop) structures every batch job as three phases:

1. **Map phase.** The input dataset is split into chunks ("splits" — typically aligned with the underlying distributed filesystem's block boundaries, e.g. HDFS blocks). A **mapper** task runs over each split *independently and in parallel*, with no communication between mappers. Each mapper reads its records and emits **key-value pairs** — the map function's whole job is a pure transformation: take one input record, produce zero or more `(key, value)` outputs. Because splits are independent, mappers can run on whichever machine already holds that block of data (**data locality** — moving the *computation* to the data instead of moving terabytes of data to the computation, since network bandwidth is far more precious than CPU at this scale).

2. **Shuffle/sort phase.** This is the part people gloss over but is genuinely where the interesting engineering is. Every key-value pair emitted by every mapper needs to end up grouped with all *other* pairs sharing the same key, and all pairs for a given key need to land on the *same* reducer. Since a key's pairs can come from any mapper, this phase requires an all-to-all network transfer: each mapper partitions its output by key (typically `hash(key) % num_reducers`) and writes a sorted file per reducer to local disk; each reducer then pulls its partition from every mapper across the network and merges the already-sorted per-mapper files into one fully sorted stream, grouped by key. This is why it's called shuffle *and* sort together — the sorting isn't incidental, it's the mechanism that turns "gather all values for this key from N machines" into a cheap sequential merge instead of a random-access hash lookup across the cluster.

3. **Reduce phase.** A **reducer** receives one key at a time along with the *complete* list of all values for that key (guaranteed complete because the shuffle phase already collected them from every mapper), and runs a reduce function that aggregates them — sum, count, join, whatever the job needs — emitting the final output, usually back to the distributed filesystem.

**Fault tolerance — re-execution, not checkpointing.** This is a deliberate and important design choice. MapReduce doesn't checkpoint in-progress task state the way, say, a long-running stream processor might. Instead, intermediate output (mapper output, in particular) is written to **local disk**, and if a task fails — a machine dies, a disk fails, the task hangs — the scheduler simply **re-runs that task from scratch** on a different machine. This works cleanly because map and reduce functions are expected to be **pure/deterministic**: given the same input split, a mapper produces the same output every time, so redoing the work is safe and produces an identical result — no risk of "wait, did that side effect already happen." The tradeoff is that a straggler task (one machine running unusually slowly, not failed, just slow) can hold up an entire job's completion; MapReduce frameworks address this with **speculative execution** — proactively launching a duplicate copy of a slow-running task on another machine and taking whichever copy finishes first.

**Joins at scale — the actual hard part of batch processing.** In a single-machine database, a join is trivial: index one table, look up matching rows for each row of the other. At MapReduce scale, you can't do random-lookup joins the same way — the data is too large to fit in memory on one machine, and a naive "for each record in dataset A, remote-query dataset B" approach means one network round trip per record, which is catastrophically slow at billions of records. Two real strategies:

- **Sort-merge join.** Both datasets are mapped so that the join key becomes the map output key. The shuffle/sort phase — which MapReduce is doing *anyway*, for every job, as its core mechanism — naturally groups and sorts both datasets' records by that join key and delivers them to the same reducer in sorted order. The reducer then does a simple **linear merge**: walk both sorted streams for a given key in lockstep, emit matches, advance whichever pointer is behind. This is exactly the same algorithm as merging two sorted arrays, and it's efficient precisely *because* the expensive part (sorting and routing by key) was already being done by the shuffle phase for free — this is the deeper reason sort-merge join is the natural fit for MapReduce rather than a bolted-on feature.

- **Broadcast hash join (a.k.a. map-side join).** If one of the two datasets is small enough to fit comfortably in memory (a "dimension table" — e.g., a lookup table of country codes to country names, tiny compared to a billion-row fact table of events), there's a much cheaper option: skip the shuffle phase for the join entirely. Load the small dataset into an in-memory hash table and **ship a full copy of it to every mapper** (broadcast it), then have each mapper join its split of the large dataset against that local in-memory hash table directly, emitting results with no reduce phase needed at all. This avoids the network cost of shuffling the *large* dataset across the cluster — instead you pay a one-time, much smaller cost of replicating the small dataset N times (once per mapper).

| | Sort-merge join | Broadcast hash join |
|---|---|---|
| When to use | Both datasets are large | One dataset is small enough to fit in memory |
| Mechanism | Shuffle both datasets by join key; merge sorted streams at reduce time | Broadcast small dataset to every mapper; hash-join locally, no shuffle |
| Network cost | Proportional to size of *both* large datasets | Proportional to size of the *small* dataset × number of mappers |
| Relies on | The shuffle/sort phase's grouping guarantee | Available memory per mapper node |

**Why this matters in interviews:** the "join at scale" question tests whether you understand that a distributed join isn't a scaled-up version of a database index lookup — it's fundamentally about *where the data physically has to move* to get matching rows co-located, and the right strategy depends entirely on whether one side of the join is small enough to avoid moving the big side at all.

## 4.2 Stream processing: message brokers (Kafka-style), log-based systems

**Batch processing assumes a bounded, finished dataset. Stream processing is the mirror image: the data is unbounded and arriving continuously, and you need to react to it with low latency instead of waiting to accumulate a full dataset first.** The mechanism that makes this practical at scale is the **log-based message broker**, and Kafka is the reference implementation worth understanding in mechanical detail.

**Kafka's model — a partitioned, append-only, ordered log.**

- A **topic** is a named stream of records (e.g., `order-events`). A topic is split into **partitions**, and each partition is, physically, an **append-only log file** — new records are always written to the end, never modified in place. This append-only structure is what makes Kafka's writes so fast: sequential disk writes (and reads, for consumers reading in order) are dramatically cheaper than random I/O, and Kafka leans on the OS page cache heavily rather than fighting it.
- Every record within a partition gets a monotonically increasing **offset** — its position in that log. Ordering is guaranteed **only within a single partition**, not across the whole topic — this is a deliberate tradeoff: strict global ordering across partitions would require coordination that kills throughput, so Kafka scopes the ordering guarantee to whatever unit you can afford to serialize (typically achieved by keying records — e.g., all events for a given user ID hash to the same partition, so *that user's* events stay in order even though the topic as a whole doesn't have one global order).
- **Producers** append records to a partition (choosing a partition directly, or by key-hash, or round-robin). **Consumers** don't get pushed data and don't have their read position tracked *by* the broker in a per-message sense — instead, each consumer tracks **its own offset** into each partition it reads, and simply asks the broker "give me records starting at offset N." This is the single most important mechanical difference from a traditional queue broker, and it has a huge consequence: because the broker retains the log (for a configured retention period, or forever if configured that way) rather than deleting a message once delivered, a consumer can **rewind and replay** from any earlier offset — reprocess yesterday's data, recover from a bug in consumer logic by re-running everything since the fix, or let a brand-new consumer read the entire history from offset 0. Multiple independent consumers (or consumer *groups*) can read the exact same partition at completely different offsets simultaneously without interfering with each other, because reading never removes anything.
- **Consumer groups** are how Kafka gets parallel, ordered-per-partition consumption: consumers that share a group ID split the partitions of a topic between them — each partition is assigned to exactly one consumer *within* that group at a time, so processing for a given partition stays strictly ordered, while different partitions are processed in parallel by different group members. If a topic has 12 partitions and a consumer group has 4 members, each consumer handles 3 partitions; add more consumers (up to 12) and Kafka rebalances partition assignment to spread the load further — beyond 12 consumers in that group, the extras simply sit idle since a partition can't be split between two consumers in the same group. Different consumer groups reading the same topic are fully independent of each other — this is how one event stream can simultaneously feed, say, a fraud-detection pipeline and a data-warehouse loader without either affecting the other's read position.

**Contrast with queue-based brokers (briefly, since this was covered in depth in Phase 1's protocol deep dive — 1.7 AMQP):** a RabbitMQ/AMQP-style broker tracks per-message delivery state and **deletes the message once a consumer acks it** — the queue is a to-do list that shrinks as work gets done, and once a message is gone, no one else can ever read it again. A log-based broker keeps the message around regardless of who's read it, for as long as retention allows, and treats "have I processed this" as state that belongs to the *consumer* (its offset), not the broker. This is exactly why queue brokers are the right fit for **task distribution** (each task should be done exactly once, by exactly one worker, then discarded) while log brokers are the right fit for **event streaming** (many independent systems may each need to see and reprocess the same history at their own pace).

**Real stream processing frameworks.** Reading raw records off a Kafka topic one at a time and hand-writing the logic works for simple cases, but real stream processing — aggregations, joins between streams, windowed computation — is handled by dedicated frameworks:
- **Kafka Streams** — a library (not a separate cluster) that runs embedded in your application, reading from and writing back to Kafka topics, with built-in support for stateful operations (aggregations, joins) backed by local state stores (typically RocksDB) that are themselves changelog-backed by a Kafka topic for fault tolerance.
- **Apache Flink** — a dedicated distributed stream processing engine built around true event-at-a-time processing with sophisticated state management, exactly-once processing semantics, and rich windowing/watermark support; widely considered the most technically complete general-purpose stream processor.
- **Spark Streaming (Structured Streaming)** — built on top of Spark's batch engine, historically using a **micro-batch** model (process small time-sliced batches of records in rapid succession rather than truly one record at a time) — simpler to reason about and reuses Spark's batch machinery, at the cost of slightly higher latency than a true event-at-a-time engine like Flink.

**The windowing problem.** A huge fraction of real stream processing questions ("average order value per minute," "count distinct users per 5-minute window") require grouping an unbounded stream into finite chunks — a window — before you can aggregate. Three window types come up constantly:

- **Tumbling windows** — fixed-size, non-overlapping, contiguous (e.g., every distinct 1-minute interval: `[0:00–0:01)`, `[0:01–0:02)`, ...). Every event belongs to exactly one window.
- **Sliding windows** — fixed-size but overlapping, advancing by some step smaller than the window size (e.g., a 5-minute window recomputed every 1 minute) — a single event can contribute to multiple overlapping windows. Used when you want a smoothed, continuously-updating metric rather than one that jumps at hard boundaries.
- **Session windows** — variable-length, defined not by clock time but by a gap of inactivity (e.g., "group a user's clicks into a session, where a session ends after 30 minutes with no activity") — window boundaries are data-driven, not fixed on a clock.

**Event-time vs. processing-time — the distinction that makes windowing genuinely hard.** **Processing time** is the wall-clock time when your stream processor actually handles a record. **Event time** is when the event actually happened out in the real world (a timestamp embedded in the record itself — e.g., "the sensor reading was taken at 10:03:12"). These are not the same thing, and the gap between them is the entire source of difficulty: a mobile client can buffer events while offline and upload a batch hours later; network delays and retries mean records don't arrive at the processor in the same order they were generated; a straggling event from 10:03 might not physically arrive at the stream processor until 10:09. If you window by *processing time*, your windows are simple to compute (just look at wall-clock time when a record shows up) but give you the wrong answer relative to when things actually happened, and the same computation re-run later would give different results. If you window by *event time* — the semantically correct choice for almost every real business question — you now face an unanswerable question: **when is a window "done" and safe to emit a final result, if a straggling event for that window might still show up?** You can't wait forever.

**Watermarks — the practical (imperfect) solution.** A watermark is a declared threshold, e.g. "I believe I have seen all events with event-time up to T, allowing for known network/buffering delay" — the stream processor uses this heuristic to decide when to close a window and emit results, accepting the risk that a small number of very late stragglers arriving after the watermark has passed will either be dropped or trigger a **late update**/correction to an already-emitted result. This is a fundamentally probabilistic tradeoff, not a solved problem: a tighter watermark (close windows sooner) gives lower latency results at the cost of more dropped/incorrect late data; a looser watermark gives more complete, correct results at the cost of higher latency before you can trust a window is final.

## 4.3 Change data capture, event sourcing

These two ideas get confused constantly because they both involve "a stream of change events," but they answer fundamentally different questions: **CDC extracts a stream of changes out of a system whose current state is the system of record. Event sourcing makes the stream of changes itself the system of record**, with current state being just a derived, disposable projection of it. Keep that distinction in your head through this whole section.

### Change Data Capture (CDC)

**The problem:** you have an existing relational database (say, Postgres, holding your orders table) that's the authoritative system of record, and you want other systems — a search index, a cache, a data warehouse, a downstream microservice — to stay in sync with every change made to it, ideally in near-real-time, without those systems having to poll the whole table repeatedly. CDC is the general term for capturing "what changed" as a stream.

Three approaches, in order of how commonly they go wrong:

- **Polling.** Periodically query the table for rows changed since the last check (e.g., `WHERE updated_at > last_poll_time`). This is the naive approach and has real, non-obvious failure modes: it **misses deletes** entirely (a `DELETE` doesn't leave a row behind with an updated timestamp to find — the row is just gone, and a poll-based system has no way to notice), and it's vulnerable to **race conditions** around the polling window (a row updated twice between polls only shows its final state, silently losing the intermediate change; a row updated exactly at the boundary of a poll window can be missed or double-counted depending on transaction visibility timing). Polling frequency is also a direct latency/load tradeoff — poll often for freshness and hammer the source database, or poll rarely and accept staleness.

- **Database triggers.** Attach a trigger to `INSERT`/`UPDATE`/`DELETE` that writes a corresponding change record to a separate table (or pushes it out directly). This does correctly capture every change, including deletes — but it adds real overhead and complexity directly on the **write path** of the source database: every write now does extra work synchronously, application-level trigger logic has to be maintained alongside schema migrations, and triggers are a notoriously awkward thing to debug and version-control compared to application code.

- **Log-based CDC — the most robust approach.** Every serious relational database already maintains an internal, append-only record of every write for its own crash-recovery purposes: MySQL's **binlog**, PostgreSQL's **write-ahead log (WAL)** (exposed for this purpose via **logical replication slots**), SQL Server's transaction log. Log-based CDC works by **tailing this internal log directly** — reading the exact same stream of changes the database's own replication mechanism uses — and turning it into a stream of change events for external consumers. **Debezium** is the standard open-source tool for this: it connects to MySQL's binlog (or Postgres logical replication, MongoDB's oplog, etc.) and publishes a structured change-event stream, typically into Kafka, for any number of downstream consumers to read. This is the most robust option specifically because it doesn't touch application code at all (no trigger logic to maintain) and adds essentially no overhead to the write path (the database was already writing this log regardless — CDC just reads a copy of something that already exists), while still correctly capturing every insert, update, and delete, in the exact order they were committed.

### Event Sourcing

**A genuinely different idea, not just "CDC but different plumbing."** In a conventional application, the database stores **current state** — an orders table has one row per order, and an `UPDATE` overwrites the previous values; the history of *how* that order reached its current state is gone unless you separately logged it. Event sourcing inverts this: instead of storing current state, you store the **full, immutable, ordered sequence of events that describe every state change** — `OrderPlaced`, `OrderPaymentReceived`, `OrderShipped`, `OrderCancelled` — as the actual system of record. Current state is never stored directly; it's **derived** by replaying all events for that entity, in order, applying each one's effect, from the beginning (or from a snapshot — see below).

**Benefits, and why they're not just nice-to-haves:**
- **A complete, intrinsic audit log.** Because the events *are* the data, you automatically have a full history of everything that ever happened — not a bolted-on audit table that might drift out of sync with the "real" data, since here there's no other "real" data to drift from.
- **Deriving new read models from history.** Since you retain every event, you can build a brand-new view of the data you never anticipated needing — e.g., "total revenue by region by day" — by writing a new projection and replaying the *entire* event history through it, even though that view didn't exist when the events were originally recorded. This is powerful in a way overwrite-based storage fundamentally cannot match: you can't retroactively compute a new report over data whose intermediate states were already discarded.
- **Temporal queries.** "What did this order look like at 3pm yesterday, before the cancellation?" is a natural question to answer — replay events up to that point in time — whereas in a conventional overwrite-based table, that state is simply gone the moment the next update lands, unless you separately maintained a history table for it.

**Costs:**
- **Replay cost.** Reconstructing current state by replaying the full event log from the beginning gets expensive as the log grows — an entity with millions of historical events shouldn't require millions of event applications just to answer "what's its current state." The standard mitigation is **snapshotting**: periodically persist a materialized "current state as of event N" snapshot, so a rebuild only needs to replay events *since* the last snapshot rather than from the dawn of time.
- **Schema evolution of events is genuinely harder than schema evolution of current-state tables.** In a conventional table, if a field's meaning changes, you migrate the existing rows once and move on. In event sourcing, **old events must remain interpretable forever**, because they're never rewritten — your event-replaying code has to be able to correctly apply an `OrderPlaced` event from five years ago in its old schema shape *and* today's shape, indefinitely, since replaying history is the whole mechanism the system depends on. This pushes real, permanent complexity into event versioning and upcasting logic that a plain CRUD system never has to deal with (this connects directly back to 2.7's discussion of schema evolution in encoding formats like Avro/Protobuf — event sourcing is the scenario where that concern is sharpest and most unavoidable).

**The distinction, stated plainly one more time since it's the thing people conflate:** CDC takes an *existing* system of record (usually a relational database storing current state) and derives a change stream from it as an add-on — the database rows remain the source of truth, and the change stream is a byproduct extracted from them (via triggers or, better, log-tailing). Event sourcing has no separate "current state" system of record at all — the **events themselves are the system of record**, full stop, and any "current state" table you see is itself just another derived, rebuildable projection, no different in kind from a search index or a cache.

## 4.4 Combining batch + stream (lambda/kappa architecture), keeping systems correct

**Why you'd ever want both batch and stream processing for the same problem.** Stream processing gives you low-latency, roughly-real-time results, but it typically has to make compromises to get that speed: watermark-based window closing that can produce slightly wrong or incomplete numbers for late-arriving data, or approximate algorithms (e.g., probabilistic distinct-count) traded for speed. Batch processing, run over a complete historical dataset with no time pressure, can be made fully correct and reprocess-from-scratch whenever logic changes — but it's inherently high-latency (it runs periodically, over what's already landed, hours or a full day behind). Many real analytics products want both: an approximate, fast, "here's roughly today's numbers" view *and* a fully accurate historical view, reconciled over time as the batch layer catches up.

**Lambda architecture — running both, then merging.** The classic approach (popularized by Nathan Marz) runs the *same underlying business logic* through two entirely separate systems in parallel:
- A **batch layer** that periodically (say, nightly) reprocesses the complete historical dataset from scratch and produces an accurate, complete batch view.
- A **speed/stream layer** that processes only recent data as it arrives, producing a fast but only-approximately-correct view that covers the gap since the last batch run completed.
- A **serving layer** merges the two — querying the batch view for anything the batch layer has already covered, and the speed layer's output only for the recent window the batch layer hasn't gotten to yet.

**The real-world pain of lambda architecture, and why it fell out of favor:** you're maintaining the **same business logic twice**, once written for a batch framework (e.g., Spark or Hadoop MapReduce) and once written for a stream framework (e.g., Storm or Flink) — different codebases, often different languages or at least meaningfully different APIs and execution models, that have to be kept semantically identical or the batch and speed views will silently diverge and disagree with each other. Every change to the business logic is a change that has to be made, tested, and deployed twice, correctly, in lockstep — a real and recurring maintenance tax, and a well-documented source of subtle bugs where the two implementations quietly drift apart.

**Kappa architecture — the proposed simplification.** The kappa architecture's core insight: **treat batch as nothing more than a special case of streaming** — specifically, a replay of the stream from the beginning. Instead of maintaining two separate processing codepaths, you maintain **one** stream processing pipeline, written once, in one framework. When you need to reprocess history (because business logic changed, or a bug is discovered, or you're building a brand-new view over old data), you don't run a separate batch job — you simply **replay the log from the start** (or from a retained snapshot point) through that same stream processing code, writing to a new output table, and cut traffic over once the replay has caught up to real-time. This directly leans on the log-based broker properties from 4.2: it's exactly Kafka's "consumers track their own offset and can replay from anywhere" model, applied at the scale of "replay everything."

**Why kappa is attractive but not always practical:** it requires the log to actually **retain full history** — which for a high-volume topic over a period of years can be a genuinely large amount of storage to keep sitting in Kafka (or whatever the broker is), or it requires some other mechanism to reload from a periodic snapshot instead of infinite retention, which reintroduces some of the batch-layer complexity kappa was trying to eliminate. Replaying a very large log start-to-finish is also not instantaneous — a full reprocess of years of history through a stream processor can itself take a long time, even if it's architecturally "just streaming." In practice, many real systems land somewhere in between: a single stream-processing codebase (kappa's simplification) but backed by a data lake or object store (S3, ADLS) as the durable, cheaply-retained historical source to replay from, rather than relying on the message broker itself to retain years of data.

**Keeping derived data correct — the general principle underneath all of this.** Every artifact this whole phase has been building — a cache, a search index, a materialized view, a stream-processed aggregate, a batch report, an event-sourced read model — is **derived data**: it doesn't hold information that doesn't exist anywhere else; it's a transformation of some upstream source of truth into a form that's faster or more convenient to query. The correct mental model is to treat derived data as **a projection you can always rebuild from the source of truth**, not as data you separately protect, back up, and worry about losing the way you'd worry about losing the source of truth itself. If a cache gets corrupted, the fix is "invalidate and rebuild it from the database," not "restore it from a cache backup" — and a system where that rebuild path doesn't actually work cleanly (some derived store that's quietly become authoritative for something, with no reliable way to regenerate it) is a system with a hidden architectural bug, whether or not anyone's noticed yet.

This is exactly why **idempotent writes and exactly-once (or effectively-once) processing semantics** matter so much here specifically. Reprocessing is not a rare edge case in this world — it's a routine, expected operation: a stream processor crashes mid-batch and has to resume from its last committed offset, replaying some records it may have already partially processed; a kappa-architecture reload replays the entire log from scratch to rebuild a view; a batch job gets re-run after a bug fix over data it already touched once. If applying an event twice produces a different (wrong) result than applying it once — e.g., a "charge the customer $10" event applied twice actually charges $20 — then every one of these completely normal recovery and reprocessing operations becomes dangerous instead of routine. The fix is to design derived-data updates to be **idempotent**: applying the same event N times produces the same result as applying it once (e.g., "set balance contribution for event ID X to $10," which is safe to redo, rather than "add $10 to balance," which is not), often implemented via deduplication on a unique event ID, or by making the write itself a deterministic overwrite of a keyed value rather than an incremental mutation. This is the same underlying idempotency concern flagged back in 1.2 and 1.7 for retried HTTP/RPC calls (and expanded further in 5.12) — it's a single recurring theme across the whole curriculum: **any operation that might be retried or replayed must be safe to apply more than once**, and derived-data pipelines, which replay by design, are where that requirement is least optional.

Which join strategy should this use, and why would the naive alternative be a bad idea at this scale?

<summary>Expand</summary>

Use a **broadcast hash join**: the 500-row campaign table is small enough to comfortably fit in memory, so it should be loaded into a hash table and broadcast to every mapper processing a split of the 2-billion-row click events table. Each mapper then joins its split against the small in-memory table locally, with no shuffle phase needed for the join at all.

The naive alternative — a sort-merge join, shuffling *both* datasets by join key through the reduce phase — would work correctly but is wasteful here: it forces the entire 2-billion-row click events dataset through a network shuffle just to co-locate it with a 500-row table, when that cost is completely avoidable. Sort-merge join earns its cost when *both* sides are too large to fit in memory anywhere; here, only one side is large, so broadcasting the small side is strictly cheaper.

**2.** Your team wants to add full-text search over a product catalog whose system of record is a Postgres table, and also wants a nightly data-warehouse export of the same catalog for BI reporting. A teammate suggests writing application code that updates the search index and the warehouse export directly, right after every Postgres write, inside the same request. Another teammate suggests polling the products table every 5 minutes for rows where `updated_at` changed. What's wrong with both, and what would you propose instead — and separately, is this scenario event sourcing or CDC?

<details>
<summary>Expand</summary>

Both proposals have real problems:
- **Dual writes in application code** (update Postgres, then update the search index and warehouse directly in the same request) risks the two writes going out of sync — if the process crashes or the second write fails after Postgres already committed, the search index and warehouse silently drift from the true state, with no mechanism to detect or repair the divergence.
- **Polling on `updated_at`** misses deletes entirely (a deleted row leaves nothing behind to poll for) and is vulnerable to races — a row updated twice within one 5-minute window only shows its final state, silently losing an intermediate change, and there's an inherent latency/DB-load tradeoff baked into the polling interval.

The better approach is **log-based CDC**: use a tool like Debezium to tail Postgres's write-ahead log via a logical replication slot, turning every insert/update/delete into a structured change event (typically published to Kafka), which both the search-index updater and the warehouse loader consume independently, each at their own pace, with deletes correctly captured and no extra load added to Postgres's write path.

This scenario is **CDC, not event sourcing** — Postgres's products table, storing current state, remains the actual system of record; the change stream is an extracted byproduct of it, not the thing itself. It would only be event sourcing if the events (`ProductCreated`, `ProductPriceChanged`, ...) were themselves the authoritative store and "current state" were just one more derived projection replayed from them.

</details>
